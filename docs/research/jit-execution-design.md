# JIT 执行与热重载：候选设计

状态：Windows 平台、最小源码前端、对象执行根/安全点、单绑定类型源码引用局部和单入口兼容方法体静止点发布均已通过开发/发布验收。通用记录值帧、通用方法分派/依赖失效、后台编译及布局迁移未实现。仅 JIT、编译成功后执行和首轮静止点发布范围已获确认，其余后续候选不自行成为语言语义。调查依据见[工业实现与研究证据](jit-industrial-research.md)，当前能力以[运行时说明](../runtime-model.md#已实现的最小业务执行协议)和[版本化源码规范](../language-contract.md#已实现的最小源码子集)为准。

## 结论与不做事项

首个实现增量建议采用：**一个 LLVM 后端、显式执行根帧、定型原生互调、静止点发布兼容方法体、受追踪的代码资源所有权**。

- 不造解释器，不先造字节码指令集，不把动态语言 VM 的分层设计原样搬来。
- 不在首轮引入 OSR、反优化、活动栈帧迁移、任意字段布局迁移或远端编译服务。
- 不让所有 JIT 调用经过动态反射/装箱；也不为了直接调用而绕开现有类型、引用、写屏障和生命周期责任。
- 不把 Windows 的链接、异常展开、源码定位、交互式调试混成一个“LLVM 支持”开关。

已落地的子集包括两类机器共用的源码编译/执行协议、借用外显式安全点、错误清理、活动调用代码持有与单入口兼容方法体发布/退休。原标量例保留两个宿主栈根；[v0.0.2](../../LANGUAGE-v0.0.2.md)按编译布局增加持有/观察局部及临时槽，并在执行前核对显式对象类型名。没有建立任意记录值帧、statepoint 管线、线程 GC mode 或通用方法版本分派服务。生成代码仍通过受控宿主 thunk 访问共享 Runtime，不把本例形状推广成通用跨 Runtime 或持久代码缓存。

## 1. 决策矩阵

| 议题 | 首轮建议 | 代价与限制 | 重新评估的触发条件 |
| --- | --- | --- | --- |
| 编译后端 | LLVM ORC/LLJIT，显式完成待发布单元的 materialization；不先采用 lazy compile 或自动优化晋升 | Windows 平台探针已通过；真实业务的首次和修改后编译成本仍需测量 | 同语义、同根/诊断条件下证明编译延迟是主要瓶颈，再比较 Cranelift 等 |
| 根报告 | 编译器提供明确的根区/位置描述，由同一 Runtime 追踪；先做显式帧根 | 根同步有执行成本；帧及槽位的销毁/复用必须与增量游标协作 | 已测出根同步为主要成本，且能证明新方案不降低安全性，再研究晚根放置或原生 stack maps |
| 发布时机 | 最外层同步语言调用已经退出、无原生借用、无正在执行的 GC 步或遍历回调时提交 | 长任务不返回时更新等待；不承诺替换执行到一半的函数 | 确有挂起任务跨更新恢复或不中断长任务更新的需求，再设计调用链版本快照 |
| 调用与内联 | 代码单元内直接定型调用/内联；可独立替换单元之间采用稳定定型入口，首轮不跨该边界内联 | 边界有一次间接调用的候选成本；粒度需测，不保证免费 | 跨单元调用成为真实热点时，合并单元或引入完整的内联依赖失效闭包 |
| 错误传播 | JIT 边界使用明确状态和结果存储，C++ 异常由原生适配层截获；生成语言级清理路径 | 错误检查和结果传递影响优化，需分别测标量/引用/记录 | 只有语言异常语义与 Windows 展开路径均验证后，才考虑让原生异常跨 JIT 栈 |
| 热更范围 | 先保留签名和类型布局的行为更新；不兼容变更明确拒绝 | 新增/修改成员、类型布局等不是自动支持项 | 有真实结构编辑用例后，单独定义迁移、重建及跨实例引用规则 |

LLVM 并非被认定为普遍最快，而是当前 C++ 工程、静态定型及优化需求下最合理的首个验证基线。Cranelift 后端与 Wasmtime 运行时不是同一层；采用前者不等于无成本获得后者的宿主、GC、trap 和调试设施。

## 2. 职责与所有权

这里描述职责，不要求为每一行新建透传类。

| 责任 | 拥有的东西 | 不得越权的事情 |
| --- | --- | --- |
| 编译器 | 源码快照、绑定/定型表示、依赖记录、根与诊断描述、候选代码产物 | 不创建另一套业务类型身份；后台编译不直接访问可变对象图 |
| 可执行程序管理 | 已发布入口、代码单元及其资源、更新候选、执行上下文和回调租约 | 不自行接管对象堆或重新定义 GC；不放出无人负责寿命的机器码指针 |
| 现有 Runtime | 权威类型/布局、对象身份/代际、值生命周期、根与收集器 | 不把 LLVM IR 或编译器分析结构当业务类型世界；不放松原生借用保护来“兼容 JIT” |

首轮产物绑定一个 Runtime 上下文及其类型/原生 ABI 指纹，不承诺跨 Runtime 或磁盘直接复用机器码。未来缓存可以使用符号化类型标识和指纹，但不能持久化进程内 `TypeId`、对象代际身份、裸地址或本次 JIT 符号位置。

执行上下文的最小职责是：关联 Runtime、执行深度/借用状态、执行根、当前代码所有权、错误与取消状态。它是协调数据，不是一个解释器，也不需要模拟全部本机调用栈。

## 3. 调用与原生边界

### 3.1 定型热路径与动态入口分工

动态发现仍使用已有类型/成员信息做校验；已知目标编译为定型调用。方法逻辑身份、参数描述、物理机器码地址和代码所有者分开保存。现有 `MethodId` 可以继续承担已发布方法身份，编译期符号和执行入口索引与它建立明确映射；具体结构扩展另行设计，不能另建语言业务类型表规避统一定义。

描述型字段的已验证布局可以降低为直接访问。原生字段应使用已验证的 C++ 定位/访问适配；不能把一次定位得到的地址差当作永久字段偏移。适配层应在借用有效期内完成读写或值交接，不把短命字段地址带过安全点。已证明布局稳定的原生字段可进一步优化，但不以绕过定位契约为代价。

JIT 与 C++ 之间使用明确的 Win64-compatible 定型接口或适配 thunk：固定宽度标量、受定义的引用表示、存储指针/长度及状态。不要依赖 `std::variant`、`std::expected`、`std::string` 或标准容器的隐式布局作为语言 ABI。原生 C++ 适配层可以继续使用这些类型，再将它们转换为规定的接口。

结果存储由谁准备、何时视为构造完成、失败时由谁清理必须写入签名契约。不能返回失败同时让调用方读取未初始化结果。纯标量/无失败路径可以由优化器简化，但首轮不预设所有调用都有相同成本。

### 3.2 两类原生调用

1. **借用原生对象存储的普通调用**：保留现有 `CallbackScope` 约束。借用期间不能通过 Runtime 创建/销毁对象或推进 GC，指针不得逃逸。
2. **执行器调用的受控运行时服务**：只在根状态完整且无不兼容借用时允许创建、收集等操作；以句柄与明确结果存储交互，不把未受保护的 `self` 裸指针跨服务保存。

原生借用范围内的语言重入不得通过临时减掉保护计数来放行。首轮只允许可验证的无 GC、无结构失效路径；其他同步重入明确拒绝。不能悄悄改成异步执行来改变调用语义。若业务确实需要能分配的原生回调，必须定义 GC-safe 的独立适配契约再开放。

“不会 GC”不等于“不会显式销毁目标”。解析得到的对象地址，不能跨越可能使存储失效的调用而继续无条件使用。非移动 GC 也不能取消代际校验。

### 3.3 错误与清理

语言的可诊断异常语义可以由显式状态、跳转到清理块和语言处理器实现，不等同于 C++ 异常 ABI。建议首轮原生 thunk 捕获 C++ 异常并转换；JIT 生成已构造临时值的逆序清理与帧根撤销，再返回错误。

分配失败的恢复能力不得超过现有 Runtime 保证；不能为了宣称 `noexcept` 而吞错。析构和根撤销路径不能隐式触发新一轮语言执行。无论选何种错误方案，都必须验证真实 Windows 栈回溯与代码卸载后的元数据清理。

## 4. 显式执行根：不是简单给局部变量套 Root

### 4.1 为什么先不用 statepoint 作为唯一根机制

本项目的引用首先是带运行时和代际的身份句柄，而不是指向可搬迁 GC 对象的原始指针。LLVM 的指针位置映射不会自动理解句柄的多字段表示、持有/观察区别、失效身份及原生隐藏引用。

首轮选择可审计的显式根帧：编译器描述帧中需要追踪的位置、对应的既有 `ValueDescription`/类型信息与活值状态；Runtime 仍使用权威类型机制追踪。帧描述属于执行元数据，不要求把每个执行帧注册成新的业务类型。值记录里的隐藏引用仍通过现有类型信息处理，不能只列出脚本公开字段。

Julia 的晚根放置说明优化根操作值得研究，同时也说明必须有优化器不可随意丢弃的引用语义。首轮先使用真实根区存储及正确内存效果的运行时调用，不把保活仅放进可丢弃 metadata，不给会观察根的调用错误地标注纯函数/无内存访问。

### 4.2 根生命周期协议

1. 入场前校验 Runtime、签名和接收者；准备帧存储、根描述和初始化状态。
2. 在任何可能 GC 或观察根的操作前，挂入共享根机制，并使所需引用可见。未经证明不观察根的原生调用应保守处理。
3. 假设 `h(f(), g())` 中 `f()` 先求值，则其引用结果必须在 `g()` 可能收集前得到保护。实际求值顺序仍由语言语义决定。
4. 帧中持有内容的增加/改写必须参与当前标记轮次；不能只修改一块内存而省略根变化通知。直接堆引用写入仍履行现有写屏障。
5. 根区的活值状态与存储分开。未构造、构造失败和已销毁槽位不能按完整值追踪；普通赋值与结束/重建值的生命周期不是同一操作。
6. **局部槽位结束或复用，以及整帧退出，都必须先取消对旧存储的排队或暂停借用，再销毁/释放/复用。** 不能只在整帧返回时处理；也不能仅凭相同栈地址认定是同一帧。
7. 返回引用或含引用记录时，在撤销生产者保护之前完成接收者保护，或证明整个交接区间不可能发生 GC/根观察。结果区构造完成状态必须随之移交。
8. 正常返回、错误和取消均清理构造完成的值，并撤销所有帧根。Runtime 必须比活动调用活得更久。

现有 `RootState::remove` 在槽位复用前通知 observer；`root_removing` 会移除队列并取消正在借用该根的追踪游标。`trace_one` 在原生定位回调后再次检查取消状态。这些都是 JIT 帧接入必须延续的不变量，而不是可省略的特殊补丁。

### 4.3 与增量收集协调

未来帧/槽位根变化需要接入同一个根新增、变化和撤销协议，而非旁挂一条 GC 看不见的栈。实现方式可以扩展根存储类别或增加受控的帧根入口，但不得复制第二套对象标记图。

首次安全实现允许较保守的根活期和同步；随后测量无引用函数、少量引用与高引用密度三种情况。无托管引用且无相关操作的函数不应无故分配根句柄。根同步和屏障的成本计入语言执行成本，不伪装为已经受到 `collect_step` 预算覆盖。

## 5. 三种“安全”不能混为一谈

| 位置/状态 | 允许做什么 | 不自动允许什么 |
| --- | --- | --- |
| GC 安全点 | 活跃引用完整可见，在现有纪律下推进收集 | 替换当前栈帧代码、迁移对象布局 |
| 代码发布静止点 | 没有活动语言调用和原生借用，可提交已准备好的兼容代码更新 | 重置业务状态、隐式重跑全部编辑器脚本 |
| 对象迁移条件 | 需要另外证明所有引用、借用、布局与清理都可处理 | 仅因非 Play 或当前没有 Tick 就认定可以迁移 |

循环回边和可收集调用是安全点候选。检查频率、对向量化的影响和取消响应需要实测，不承诺每条语句可停，也不强制中断任意原生函数。

分步 GC 处于暂停阶段与“一个 GC 步正在执行”不同。仅方法体更新不必概念上等待整个收集周期结束，但发布/回收不得使追踪器持有的任何类型、帧或代码元数据失效；这一组合要有专门验收。

## 6. 热重载：首轮静止点发布

### 6.1 为什么不立即做活动帧双版本

| 方案 | 一致性与成本 | 判断 |
| --- | --- | --- |
| 最外层调用结束后切换 | 一次调用链看到稳定程序；不用转换本机栈，不需要方法级 world-age 查找 | 首轮建议 |
| 进入调用链时捕获版本并保留旧代码 | 可支持更复杂的长任务，但依赖、回调、旧常量和类型元数据都需版本所有权，内存保留可能很长 | 确有跨更新挂起任务时再引入 |
| 修改执行中栈帧 / OSR / 反优化 | 需要局部值、异常区域、根和恢复点映射，明显增加编译器责任 | 当前不做 |

第一种并不要求停引擎或重启场景：可在 Tick/工具命令之间提交。代价是一个长期不返回的脚本会阻挡发布；应先提供明确的等待状态与协作取消，而不是偷偷换入新方法。

### 6.2 编译与发布事务

```text
捕获不可变源码/定义快照
  → 绑定、定型、生成及链接候选
  → 强制完成待发布入口的 materialization 与校验
  → 候选就绪，但不对运行中调用可见
  → 运行时线程到达发布静止点
  → 校验请求版本、Runtime 身份和类型/原生 ABI 指纹
  → 提交入口与资源所有权的变更集合
  → 后续调用使用新程序，退休不再被引用的旧单元
```

- 编译线程只读取受控快照；LLVM 支持并发编译，不代表现有 Runtime 可以被多线程访问。
- 最新请求是 N 时，较旧请求 M 的晚到成功结果不得覆盖 N。N 编译失败也不应擅自发布用户已放弃的 M；继续使用最后一次成功发布版本。
- 所需依赖未就绪、类型/ABI 指纹改变或请求已经过期时，不提交。准备阶段完成可能失败的分配与链接；单线程静止点提交不需要为每个业务字段新增锁。
- 提交前不执行可能修改游戏/编辑器状态的任意脚本初始化。首个行为更新不改变存量对象默认值或结构。
- 发布后的刷新/重建通知属于普通执行，失败不回滚已经发生的业务副作用。禁止以“编译事务”之名承诺整个世界可回滚。

### 6.3 直接调用与内联

源码文件、声明作用域、编译单元、发布单元必须分开；移动文件不能暗中改变名称语义。

初始小用例可以整组编译发布。扩展增量时，建议单元内直接调用与内联，跨可独立发布单元使用稳定的定型入口。编译器记录类型布局、签名和常量等依赖；首轮不跨该可替换边界内联。

如果以后开放跨单元内联或嵌入目标机器码地址，就必须重新编译受影响调用方闭包，或者把对应代码作为不可独立释放的共同单元。不能只替换被调用函数入口，却留下调用方内联的旧实现。纯直接调用方案与稳定入口方案必须在相同业务用例下比较成本，不能凭“间接调用总是慢”或“只多一跳无所谓”定案。

### 6.4 回调与资源退休

编辑器事件等长期绑定默认保存稳定函数身份、签名和接收者身份，而非裸 JIT 地址。必须交给外部原生 API 的函数地址，需要受追踪的适配器/租约，并明确注销；不能让其绕过代码寿命管理。

旧代码能回收的条件，不只是“当前未执行”：还包括没有已发布直接调用/内联依赖、原生回调租约、值操作/析构入口或 GC/调试设施仍需使用其资源。机器码、只读常量、重定位目标和元数据的生命周期必须有明确负责人。

卸载要撤销相关展开与调试登记后再释放内存；不能在已经发布新代码之后把退休资源清理失败伪装成发布回滚。诊断历史可以保留文本、版本标识或独立源码快照，不应为了日志永久持有全部旧机器码。

## 7. Windows 首个实验的准入门槛

依据锁定 LLVM 源码，x64/COFF 的 LLJIT 默认仍走 RTDyld 路径，而 `ExecutorNativePlatform` 的 COFF 路径要求相应 ObjectLinkingLayer 和 ORC runtime 配置。不能把新 JITLink 的插件直接接到默认层上。

COFF runtime 已有动态展开表登记与撤销实现，但其异常桥对无法归属到 JIT 区域的 `pThrowInfo` 仍有 `abort()` 分支。源码证据见[Windows 边界核查](jit-industrial-research.md#windows已从未知缩小到具体边界)。这是特定桥接路径的限制，不泛化成所有 Windows JIT 都不支持异常；首轮仍采用原生适配层截获与显式错误传播。

本机对照确认默认 LLJIT 没有为所生成函数登记 Windows 展开表。显式 JITLink + 完整 `ExecutorNativePlatform` 路径另遇私有 COMDAT 重定位、导入数据被跳转桩替代的问题；锁定源码 `COFFPlatform::notifyRemoving` 仍为 `llvm_unreachable("Not supported yet")`，不能作为当前资源退休路径。尝试过的 compiler-rt 独立构建已从正式构建移除，不保留第二条长期运行后端。

必须验证：

1. 与宿主开发/发布配置兼容的 LLVM 开发库、CRT、EH/RTTI 及跨边界分配释放纪律；不为了让二进制链接而擅改现有运行时契约。
2. 标量、混合参数、结果存储、记录对齐、较多参数和递归调用；用实际目标布局而非手写想象中的 ABI。
3. 宿主 EXE 和所需 DLL 符号解析、重定位及跨生成单元调用。
4. 展开元数据的登记/撤销与真实嵌套回溯；无 C++ 异常跨界不等于可丢弃 unwind 信息。
5. 代码发布后不可写/可执行页权限、更新产物的独立存储及资源释放；不手写一个永久 RWX 堆冒充 JIT 管理器。
6. 源码位置与代码版本定位；交互式源码单步和变量查看作为独立能力验证。锁定版本的通用 debugger helper 不支持 COFF，不能把它计作现成能力。

现采用原生 COFF 的 `ObjectLinkingLayer`，保留 LLVM 生成的展开信息，由 allocation actions 配对管理 Windows 函数表。选择 Large code model 解决实测的远距离宿主回调 PCRel32 越界；通过系统 `RtlVirtualUnwind` 逐帧验证，而非扫描栈猜测返回地址。完整通过范围及限制见 [README](../../README.md#windows-jit-平台验收)。本实验不载入任意 C++ 对象文件，不需要完整 COFF C++ 平台运行时；源码行映射、源码单步和变量查看尚未实现。

### 9.1 早退清理发射的单因素实验

2026-09-25 第一轮：完成隔离 A/B，**当时未合入生产编译器**；随后的小输入补测与正式晋升见第 9.2 节。A 为改动前实现，B 仅将每个 `return` 重复发射的用户槽清理汇入一个按需生成的 `cleanup.return` 块；仍先清用户槽，再进入原有快照路径。槽分配、词法生命期、清理顺序、错误清理、安全点、宿主适配与独立 LLJIT 所有权不变。不相交作用域的槽复用留作另一个因素，不与本次混合。

发布配置按 A/B/B/A 顺序运行四个独立进程，每进程 14 个源码场景 × 原生/描述型对象，各编译 5 次，总计 560 次；统计剔除每进程第一次编译。执行各预热 2 批，再采集 9 批，每批 128 次。下表为完整源码编译时间的中位数，每格各有 10 个样本；不是单独的 LLVM 优化阶段耗时。

| 早退点 | 强槽数（两版相同） | 静态 IR 清理调用 A → B | 原生编译 ms，A → B | 描述型编译 ms，A → B | 生成函数字节数（两版相同） |
| --- | --- | --- | --- | --- | --- |
| 1 | 3 | 8 → 8 | 3.64 → 4.07 | 4.06 → 3.66 | 564 |
| 16 | 18 | 308 → 68 | 11.44 → 7.51 | 13.46 → 7.09 | 1,780 |
| 64 | 66 | 4,292 → 260 | 121.39 → 19.54 | 131.83 → 18.01 | 5,572 |
| 256 | 258 | 66,308 → 1,028 | 3,851.83 → 69.20 | 4,146.63 → 73.10 | 21,124 |

**裁决：大规模早退的编译收益成立，不是执行或 GC 提速。** 重复清理的 IR 项由“早退数 × 用户槽数”变为单份用户槽清理；28 个场景的槽布局、静态 poll 数和最终函数大小均相同。64 早退原生场景的 128 次调用批次中位数为 235.00 → 234.65 μs，回收为 14.50 → 14.50 μs，退休为 60.40 → 67.50 μs；不能选取部分数字声称执行、回收或退休普遍改善。没有测量分配峰值或常驻内存，也不把 IR 缩小换算成内存收益。

语义与生命周期证据：开发/发布配置各运行两版正式 Business/JIT 验收，均 PASS；未改变的 Runtime 验收每配置运行一次，均 PASS。额外用真实对象覆盖首/中/末早退、正常落尾、原生失败、快照发布失败及合法安全点内完整收集，原生/描述型合计每版每配置 24 条路径、共 96 次。清理次数、槽顺序/根数/poll 的 64 位轨迹指纹和结果完全一致；没有保存完整事件数组，不把指纹称作形式证明。测量探针还逐次检查代码退休后的 Windows 展开表撤销及地址 `MEM_FREE`。

### 9.2 小输入交错对照与清理共享晋升

2026-09-25：用户批准继续补测并落地。`SourceLowering` 已在正式编译路径中采用第 9.1 节验证过的按需共享清理块，未带入实验统计、环境开关或兼容分支。改动局限于首次早退时生成清理块、后续早退跳入同一块，以及保存块指针；原槽分配、词法根、poll、错误处理、快照交接和 LLJIT 所有权不变。

补测让两版真实 DLL 在同一进程、同一线程中交错编译相同源码，每对交换 A/B 顺序、轮换场景；四进程加载顺序为 AB/BA/BA/AB。线程固定到许可的逻辑 CPU 31，未锁频。8 个小输入/中等规模场景 × 原生/描述型，共 16 组；每组每进程预热 5 对、测量 30 对，共 4,480 次编译、1,920 对正式样本。每组有 120 对样本，下表采用每对 B/A 比值的中位数，而不是两个边际中位数相除。

| 场景 | 原生 B/A | 描述型 B/A |
| --- | --- | --- |
| 空函数 | 0.9911 | 1.0052 |
| 无用户槽的直接早退 | 1.0072 | 1.0182 |
| 1 个引用槽、1 个早退 | 0.9964 | 0.9982 |
| 默认循环 | 1.0008 | 1.0045 |
| 强/弱引用、无早退 | 1.0065 | 1.0154 |
| 1 个顺序空引用块、无早退 | 1.0046 | 1.0180 |
| 16 个顺序空引用块、无早退 | 0.9903 | 1.0090 |
| 16 个引用槽、16 个早退 | 0.6073 | 0.6087 |

小输入/无早退对照的配对中位数变化为约 -1.0% 到 +1.8%；原先单早退约 +12% 的偏差没有在该控制下出现。没有稳定的明显小输入退化证据，16 早退的编译耗时则稳定减少约 39%。这支持晋升少量、保持语义的去重代码，不是“任何机器/输入绝不回退”的统计保证，也尚未区分频率、缓存和进程顺序各自的影响。两版始终独立拥有 LLJIT；DLL 分别通过自己的编译、查询、调用和销毁入口工作，不跨 DLL 删除不透明代码对象。每次编译均核对服务/槽布局、真实展开表及退休后的 `MEM_FREE`；计时外实际执行各组首尾样本，检查结果、poll 和显式清理。

正式验收增加 `verify_reference_returns`，每对象来源覆盖 4 个退出位置 × 3 种成功/故障模式。发布回调在结果交接前检查所有用户强/弱槽已空，随后验证正常发布或注入发布失败；原生失败、完整新 GC 周期和已经发生的副作用也一并检查。该验收在改动前实现上 PASS；一次性负对照故意省去早退清理，会以 `Return kept a user root until snapshot publication.` 失败，证明没有让发布后的最终清理或 RAII 掩盖错误。错误变体只留在 `out/`，不进入正式构建。

正式 `dev`、`release` 的 Runtime、Business execution、JIT 验收均 PASS；每配置新增 24 个退出/故障子路径，两配置合计 48 次。正式发布 DLL 另跑 28 场景、140 次编译/退休及执行/回收探针：原生 64/256 早退的编译中位数为 18.06/76.34 ms，描述型为 17.80/67.66 ms。此单进程复测用于确认优化已进入正式产物，不与前轮机器状态直接拼接计算新倍数；执行、GC、退休和内存收益仍不作承诺。

### 10.2 单入口兼容方法体发布协议

状态：已通过开发/发布配置，原生/描述型对象各执行 12 个隔离场景（含后续长源名诊断回归）；Runtime、Business execution 和 JIT 验收均为 PASS。语言语法保持 v0.0.2，v0.0.1/v0.0.2 文件字节均未改变，不另加版本选择指令。

本次发布单位是既有宿主绑定的单个源码入口及其完整编译资源。稳定入口由宿主程序所有者管理，不把裸 JIT 指针塞进原生 `Invoker`，也不把它声称为通用 `Runtime::MethodId` 分派或跨单元内联失效系统。

1. **固定合同**：绑定同一个 Runtime、确切对象类型/成员身份、不可变布局信息、入口名、固定签名及实际原生服务表。使用真实依赖快照，不以类型名相同或任意常数散列代替兼容性检查；本阶段的 Runtime 元数据仍不可原位修改。
2. **请求与候选**：请求拥有源码、源名和单调序号。候选完成解析、定型、生成、链接与入口物化后才可提交，不执行业务初始化。准备阶段只读所捕获的输入；首轮不建设后台编译调度器，乱序完成通过保留多个请求/候选确定性验收。
3. **最新请求优先**：后来的请求一旦接受，较早候选不再有发布资格；最新编译失败仍保持上次已发布版本，不复活较旧未提交候选。同一请求不能重复提交。
4. **Runtime 级静止点**：`ExecutionScope` 覆盖准入、生成执行及帧清理，跨同一 Runtime 的不同入口与嵌套调用计数。`check_code_publication` 还复用原生借用、遍历及执行中 GC 步的保护；仅 GC 周期暂停不阻止兼容发布。
5. **显式提交**：忙时返回 `busy` 并保留候选，宿主在外层调用退出后明确重试；不从安全点、析构或编译完成回调暗中提交。成功提交消费候选，失败不改变已发布入口；调用方仍负责其未提交候选的寿命。
6. **两种代码引用**：长期事件保存稳定弱入口与接收者身份，每次调用选择当时已发布版本，不顺便保活接收者。显式代码租约固定某一版本，通过同一受检查入口调用，直到最后一个持有者释放才允许退休；诊断地址不是自带寿命的调用句柄。
7. **关闭与退休**：所有者关闭后旧稳定入口拒绝新调用，但已捕获的活动版本及显式租约可按其合同结束/使用。提交后退休不再被持有的旧单元，展开表与机器码一同撤销；退休失败不能伪装成发布回滚。历史请求和错误文本不得间接持有旧机器码。

Runtime、宿主回调和承载代码的 DLL 必须覆盖使用它们的程序/调用/租约寿命。这里只更新行为，不重置接收者字段、对象身份、默认值或世界状态；不承诺编辑器 UI、文件监视、后台线程、活动帧迁移、任意字段布局迁移、一般源码调用图或完整资源故障恢复。

验收对应范围：R01/R02/R03 验证旧调用不换版、最新请求优先和真实失败保旧；R05 验证稳定工具事件与显式版本租约；R08 验证暂停 GC 中发布、变化的引用槽和后续完整收集。R06 只覆盖现有固定签名、入口、接收者、实际服务表与不可变元数据合同，不是任意字段布局迁移；R07 覆盖多次更新、历史源码/错误文本不保留代码，没有断点记录设施。没有跨源码单元调用/内联，R04 仍未实现；请求号与编译源位置不等于 W03 的机器码运行错误定位。

初始发布协议的本机证据保存在 `out/review/reload-dev-runtime-acceptance.log`、`reload-release-runtime-acceptance.log`、`reload-dev-jit-acceptance.log`、`reload-release-jit-acceptance.log` 和 `hot-reload-acceptance-evidence.json`，对应当时的11场景。后续长源名诊断回归及当前12场景的双配置完整证据见 `out/review/wave1-fixes/dev-acceptance-final.json`、`release-acceptance-final.json`。使用 README 的正式构建/验收目标可复现；这些本机记录不是新的性能基线，也不声称后台线程、无限规模或全面资源故障恢复已经验证。

### 10.3 后续标量调用增量

本节记录此前的源码标量调用阶段。后续共享函数签名与原生标量返回已落地，当前行为以[共同函数契约](../runtime-model.md#共享函数签名与结果)和 [README](../../README.md#jit-业务执行闭环) 为准；本节的“原生仍为 void、未改 Runtime”只描述当时范围。

在第 10.2 节既有发布协议上，源码入口已扩展为零个或多个 `float/uint` 参数和 `void/float/uint` 结果，当前语法集中在 [v0.0.2 的标量调用修订](../../LANGUAGE-v0.0.2.md#34-标量调用与返回)。第 10.2 节“语言文件未变化”描述的是当时发布增量，不是后续语法冻结。

私有 DLL 边界使用固定宽度参数数组及独立状态/结果存储；先校验再入场，成功结果在结束回调与生成清理之后提交。宿主绑定表来自 Runtime 元数据，前后端仅保留目录索引，机器快照全部移到宿主策略。空环境计算和非机器 UI 控制器共用此链路；原生 `Runtime::call` 仍返回 `void`，没有引入新的类型注册表或对象世界。

版本合同现在捕获并核对实际参数顺序/类型、结果类型和成员目录；不可变请求、最新请求优先、静止点发布、旧租约及代码退休规则不变。真实验收为 [typed_business.inl](../../acceptance/jit/typed_business.inl)，日志在 `out/review/typed-call-slice/`。未改 Runtime/GC、构建锁、RHI/布局；未引入 Task/CookSession、后台调度、完整节点/UI 系统、引用/记录返回或永久 ABI。本增量不沿用历史数据宣称性能改善。
