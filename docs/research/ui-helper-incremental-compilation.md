# ToolShelf 高度热更，从 Source 依赖到接受帧

在基线 `0acd3ca6` 上，只把 `shelf_expanded_height()` 的返回值从 `56.0d` 改为 `57.0d`，会重编编辑器的 44 个组件。临时原型用 Source 已有的调用分析做复用判断，实际只重编 ToolShelf，其余 43 个沿用原机器码。9 轮配对测量中，热编译中位耗时从 **1,176.0 ms 降至 41.8 ms**。新增一个未调用、返回类型错误的函数仍会拒绝整份候选。正式实现的独立复测及现有诊断能力见文末。

## 一行修改如何传到编辑器

| 层 | 这次修改实际经过的路径 | 对复用的意义 |
| --- | --- | --- |
| UI 语法与降低 | UI parser 扫描组件头，保存正文游标。解析每个组件时把文件开头的辅助函数按该组件环境改写，再生成自己的 `__ui_dispatch` 和源码映射。这个文件有 44 个组件、6 个文件级函数。ToolShelf 的高度和底部内边距读取高度函数。[UI 源文件](../../assets/editor.ui.source) · [降低实现](../../modules/gui/ui_language/src/declaration.cpp) | 44 份生成文本都含有这个数字。当前 UI 在调用 Source 前比较整份文本，44 个组件全部失效。 |
| Source parser 与类型检查 | parser 收集签名、记下正文游标、处理类型和常量，再回到每个函数体，检查名称、参数、返回值和效果。随后从指定入口沿已解析的 `source_call` 求传递可达集。[Source 前端](../../modules/execution/language/src/source.cpp) | “函数是否合法”和“这个入口是否调用它”各有答案。先保留前者，再消费后者。改动产生的新调用边要从候选版本取得。 |
| Runtime 类型环境 | 编辑器初始化 UI Runtime，注册 `ui.ComponentContext`。`Program::create` 绑定接收者和可见类型目录，`request` 收集 Source 类型声明，`prepare` 将字段、方法和类型布局传给后端。此次编辑没有引入类型声明。[类型绑定](../../modules/execution/source/src/detail/bridge.cpp) · [Source 组装与发布](../../modules/execution/source/src/program.cpp) | 这次换的是组件代码。已发布的类型身份、上下文对象和实例状态可继续使用。跨 Runtime 或类型环境变化时，须重新确认复用条件。 |
| LLVM / JIT | 现有后端已按可达集生成 IR，运行 O2，将模块加入 ORC，再首次查找入口以触发机器码生成、链接和物化。[LLVM 后端](../../modules/execution/jit/src/source_backend.cpp) | 正式实现已能排除单个编译单元内部的无用函数，仍为 43 个未受影响的分派入口走了一遍后端。省下的是这 43 次工作。 |
| 发布与执行 | 变更组件建立新 Program，检查并发布 Candidate，`pin` 后绑定 `Typed<void, uint32_t>`。复用组件共享不可变代码，各自持有本次的声明、子组件关联和作者源码位置。运行时按上下文对象和操作号调用。磁盘热更先准备已挂载区域，接受控件后才推进文档版本。[组件编译与执行](../../modules/gui/ui_language/src/component.cpp) · [热更事务](../../modules/gui/ui_language/src/live_document.cpp) | 代码版本、作者文件版本、Runtime 对象身份是三个独立量。只替换一个入口，旧实例仍可安全执行旧版；新报错要显示当前文件位置。 |

编辑器宿主给 ToolShelf 传入 12 个输入并绑定控件键，随后读取含工具架在内的三条固定高度，计算 dock 可用高度。工具架和独立属性组分别悬挂自己的实例。因此可同时检查布局是否变化、别的区域是否误刷新，以及热更前的本地状态能否保留。[编辑器宿主](../../modules/editor/application/src/editor/workspace.cpp)

## 时间花在哪里

Ryzen 9 3950X，固定一个逻辑处理器，Windows x64 Release，仓库锁定的 Clang/LLVM 23.1.5。两种路径使用同一份带分段计时的后端和真实编辑器文件。每轮各起新进程，先完整编译原文件，再对已接受的模块计时一次公开的 `Module::compile`，随机交错 9 轮。每次检查编译数和实际组件名。计时不含磁盘轮询、帧布局与绘制。

| 工具架热更，毫秒 | 正式路径 | 按 Source 可达集复用 |
| --- | ---: | ---: |
| 新增的完整 Source 前端检查，44 份 | — | 5.38 |
| 进入 JIT 的单元，其 Source 前端合计 | 7.56 | 0.14 |
| LLVM IR 生成及验证，扣除 O2 | 24.23 | 0.74 |
| LLVM O2 | 296.80 | 8.59 |
| ORC 首次入口查找，含物化与链接 | 830.84 | 23.79 |
| **完整热编译** | **1,176.02** | **41.77** |
| 完整热编译四分位区间 | 1,173.39–1,187.74 | 41.54–42.27 |

总耗时减少约 96.4%，加速 28.2 倍。各行取各自中位数，总耗时还包括 UI 降低、绑定、请求、发布及其他工作。ORC 这一项测的是首次入口可用前的整段等待，内部阶段未单独计时。原型对 44 份完整输入先检查，再让一个变化的组件走正常编译，所以该组件经过两次 Source 前端。

为区分 parser 内部的工作，另在后端的同一份 `Parser::parse` 中设三个连续计时区间，固定同一逻辑处理器交错 7 轮。每轮先按阶段累加本次热编译涉及的单元，再取中位数，单位毫秒。

| Source 前端阶段 | 正式路径的 44 份 | 原型预检的 44 份 | 原型随后编译的 ToolShelf |
| --- | ---: | ---: | ---: |
| 校验环境、登记声明与签名、扫描正文边界、解析常量 | 2.136 | 1.469 | 0.034 |
| 从游标解析并检查所有函数体，含返回路径检查 | 5.029 | 3.652 | 0.094 |
| 调用关系、效果传播及入口可达集 | 0.238 | 0.171 | 0.005 |

对这份文件，取得依赖信息的增量很小。预检中耗时最多的是完整函数体检查，但连同签名扫描在内只需数毫秒。这里优先省掉无关组件的 LLVM 工作，就可以保留未使用函数的错误诊断。

### 其他编辑是否变慢

另做 7 轮随机交错对照。每个进程全量编译一次，以该模块为共同基线，分别测 8 次注释移动、2 次末尾组件标签修改和 1 次高度修改。表中为每轮均值的中位数，单位毫秒。

| 编辑 | 正式路径 | 每次预检 44 份 | 复用上一接受版的检查结果 |
| --- | ---: | ---: | ---: |
| 首次全量编译 | 1,184.43 | 1,197.31 | 1,185.33 |
| 仅移动注释，44 个入口均可复用 | 2.00 | 7.97 | 2.13 |
| 改 ProjectOutput 的一个标签，重编 1 个 | 56.62 | 63.84 | 58.17 |
| 改工具架高度 | 1,171.96 | 41.84 | 42.06 |

第三列方案会让原本最快的编辑明显变慢。最后一列只复用上一接受版对应组件的检查结果，逐字节核对完整降低输入，核对 Runtime 和类型目录规模，并重新绑定本版源码映射。结果是注释编辑做 0 次完整前端预检，标签编辑做 1 次，高度编辑仍做 44 次。首次编译三组都生成 44 份机器码。该实验未测峰值内存；保存比较所需的字节与区间有持有成本。

**接受帧与对象身份。** 在磁盘副本上用 `LiveDocument::poll` 热更，挂载含两个真实 ShelfTool 子项的 ToolShelf 和一个已折叠的 PropertyGroup。两个根上下文的对象 ID 均保持不变，工具架三个作用域没有创建或销毁。该 UI Runtime 的类型数始终为 28，类型 ID 序列、接收者的 `TypeInfo*` 和 4 个存活对象的数量均保持一致。接收者描述含 0 个字段、50 个方法。下表是 56→57 这一轮累计计数的增量。

| 已挂载区域 | 正式路径的绑定求值 | 选择性复用的绑定求值 |
| --- | ---: | ---: |
| ToolShelf，含两个 ShelfTool 子项 | 51 | 39 |
| PropertyGroup，保持折叠 | 8 | 0 |

通过已接受帧中手柄的实际坐标送入指针按下和释放，Session 发出绑定的宿主操作。验收程序据此更新折叠输入，接受帧高度依次为 24、57。此处覆盖 Session 布局和动作路由，宿主输入由验收程序回送；未测完整编辑器窗口或 GPU 帧耗时。

**复用机器码时的源码位置。** 两个辅助函数依次为未使用的 `unused` 和会触发整数除零的 `divide`。把前者加长为多语句函数，后者及事件均未改。若把旧机器码记录的生成偏移 68 直接查新整份映射，会错误指向 `unused` 的 1:58。原型按同一组函数区间生成编译文本和映射，复用旧机器码后，事件实际报在当前版本 `divide` 的 **2:28**，正好指向除号，源码内容哈希也与新文件一致。56→57 两个字面量等宽，单靠工具架例子查不出这种错位。

**同一段辅助函数可能依赖组件环境。** 当前实现允许 `double extent(){return input.size;}`。两个组件的 `size` 在不同输入槽位，执行所得高度分别是 32 和 45。再加一个没有 `size`、也没有调用该函数的组件，UI 降低仍在 1:24 拒绝候选。只在任意一个组件环境里验证一次整段公共文本，会漏掉当前能发现的错误。只有证明降低结果与类型环境等价时，检查结果才能跨组件共享。

## 建议的落点

1. **Source 提供依赖事实。** 保留全量语义检查，由现有的 Source 前端返回所选入口的可达函数和源区间。parser 扫描正文时已经识别了结束位置，适合在那里记录。通过现有 Source 编译边界传递简单值，让 AST 及其分配仍留在原来的域。无需在 UI 再维护一套函数名扫描，也无需打开 JIT 调试信息。
2. **UI 决定复用。** 优先处理完整降低输入及环境均与已接受版一致的组件。其他组件先验证完整候选，再用入口和可达函数生成的确切内容判断可否复用；类型、常量等非函数声明先保守保留。比较要涵盖接收者、类型环境及影响代码生成的选项。类型目录增长时可先保守失效，对跨环境复用另行验证。仅保留上一接受版所需的信息即可。
3. **把机器码偏移、当版源码映射和候选事务一起验收。** 编译输入和映射必须使用同一坐标系。继续沿用现有 Program 版本、定型入口和文档接受流程。正式实现应同时复测表中的 1/43、未使用函数报错、连续两次改变调用边、当前版本定位、旧实例保活，以及纯注释和局部标签耗时。当前证据支持先实施这条编译链路，尚未显示改动 Runtime 类型布局、LLVM 优化级别或逐帧执行机制的收益。

## 正式实现与端到端验收

UI 先比较同一类型环境下的完整降低文本。文本变化时，`Program::prepare` 在一次解析中检查所有函数体，通过同步回调借出按声明顺序排列的函数字节区间及传递可达标记。UI 比较可达函数和非函数声明的实际内容。需要代码时，后端直接从刚检查过的程序进入 LLVM。类型目录增长时保守重编。每版持有自己的降低结果，声明及其映射从 parser 移入组件。机器码所属版本和当前版本只各保留需要的区间表，连续多次复用仍可从最初的故障偏移直接换算到当前作者文件。[Source 准备入口](../../modules/execution/source/src/program.cpp) · [UI 复用与错误定位](../../modules/gui/ui_language/src/component.cpp)

真实编辑器文件经过磁盘轮询、Source/JIT、实例更新和 Session 布局提交。全量检查 44 个组件各自的复用结果，确认高度 56→57 只编译 ToolShelf。随后给高度函数增加对 `rail_button_length` 的调用，接受帧高度变为 36；再改被调函数，只有 ToolShelf 和 PaneDivider 重编，高度变为 38。未调用函数返回字符串时在作者文件 1:32 拒绝热更，原接受版继续显示 57，保留的旧组件仍可执行出 56。另一份磁盘样本先加长无关函数，再只移动注释，两次都复用了最初的机器码，除零的字节偏移、行、列和文件版本均与当前除号一致。验收还覆盖组件捕获不同输入槽、共享常量变更和已注册类型目录增长。[编辑器依赖验收](../../acceptance/ui/entry_dependencies.cpp) · [热更与源码定位验收](../../acceptance/ui/hot_reload.cpp)

### 正式版本的配对复测

基线为 `0acd3ca6`。使用同一份真实编辑器文件、同一台 Ryzen 9 3950X 和锁定的 Release 工具链。两个可执行文件各自链接对应版本的正式库，关闭调试、诊断插桩和编译产物捕获。固定同一逻辑处理器，交错随机顺序运行 9 轮，每轮每版各用新进程。以冷编译得到的模块为共同基线，测 12 次注释移动、3 次 ProjectOutput 标签替换和 1 次高度替换。每次检查编译/复用总数，表中为每轮均值的中位数，单位毫秒。

| 场景 | 基线 | 正式实现 | 重编 / 复用（基线 → 正式） |
| --- | ---: | ---: | --- |
| 冷编译 | 1,189.81 | 1,175.84 | 44 / 0 → 44 / 0 |
| 纯注释热更 | 1.95 | 1.91 | 0 / 44 → 0 / 44 |
| 改 ProjectOutput 标签 | 56.68 | 56.87 | 1 / 43 → 1 / 43 |
| 改工具架高度 | **1,172.40** | **42.86** | **44 / 0 → 1 / 43** |

工具架热编译减少 **1,129.54 ms（96.34%，27.35 倍）**。前后四分位区间分别为 1,159.71–1,180.73 ms 与 42.47–43.50 ms。冷编译和标签编辑两组区间各自重叠。门禁在 dev、release 均通过 UI、Source 和 JIT 端到端验收；Release 编辑器窗口通过编辑、保存、撤销、接受帧及 Play 关闭，日志零错误。窗口冒烟与编译计时独立运行。

## 诊断信息能回答什么

| 需要判定的问题 | 套件中可取得的证据 | 采集成本与边界 |
| --- | --- | --- |
| 哪个组件重编、为何走复用路径 | `Module::compilation()` 给总数，`Component::compilation()` 分别标出重编、生成文本相同、依赖相同。Source 在语义检查结束后直接提供可达区间。 | 在编译时写入组件结果，调用方按需读取。正常执行不扫描函数、不输出逐帧日志。可达标记回答“这个入口是否用到它”；具体经过哪几个中间函数仍要查看调用表达式。 |

| LLVM 编了什么，能否在源码停下 | 对真实 ToolShelf 的同一份生成 Source 单独打开 `artifacts`，取得优化前 IR 98,887 B、优化后 IR 75,970 B、反汇编文本 153,803 B 和链接前 COFF 12,223 B。独立启用调试后，读到 98 个停点，分属 `__ui_dispatch`、`choose` 和 `shelf_expanded_height`。通过定型入口实际停下并继续一次，调用完成、执行资源清理成功。 | 普通编译仍能执行并定位错误。获取 IR/COFF 需要按选项重编，`Lease::artifacts()` 返回拥有的拷贝。调试回调同步暂停本次 Runtime 调用，调试版代码和采集耗时应与正常性能样本分别解释。这里用单独的 Source Program 观察 UI 生成文本，并未往编辑器帧中插断点。[产物和调用诊断](../source-diagnostics.md) · [调试器](../source-debugger.md) |
| 卡在编译、发布还是下一帧 | 用公开的编译入口和 Session 接受分开计时，可判定工具架这次慢在编译。编辑器状态栏显示接受版本；进程日志、窗口验收和 JSONL 可核对已报告的错误及退出情况。 | 原型的细分来自临时插桩。正式的按需测量现可从同一保存读取逐组件的 Source 前端、O2、ORC 与发布时间，见文末。日志采用有界可丢弃队列，需结合健康和丢弃计数解读；逐绑定打日志会改变被测工作量。[文档轮询和提交](../../modules/gui/ui_language/src/live_document.cpp) · [进程日志](../modules/logging/README.md) |

**文档提交和帧接受是两个时刻。** `Application` 在完成控件布局后提交候选文档，随后才等待渲染准入。只有渲染器返回匹配的帧 ID 和尺寸，且 `ui_.accept` 成功，新的几何才对输入生效。只观察文档版本会低估某些保存的可见延迟。[编辑器主循环](../../modules/editor/application/src/application/application.cpp)

## 真实编辑器从保存到接受帧

### 优化与线程边界

1. **先验证目标文件生成的代价。** 当前 IR 使用模块级 O2，机器码使用 `CodeGenOptLevel::Aggressive`，是两个独立设置。建议固定同一份 ToolShelf 输入、IR 管线和语义，对照目标代码生成的 Aggressive 与 Default，同时测保存到接受帧，以及热更后真实属性求值和事件执行。范围先限定在 UI 热更实验，选择级别要同时看编辑和执行成本。
2. **后台候选优先考虑从已检查程序到机器码的整段工作。** 输入应包含拥有生命周期的代码文本、接收者与类型绑定快照、源码映射所需信息。由工作线程独占本次编译的 LLVMContext、TargetMachine 和 LLJIT，执行 IR 构建、O2 及首次物化，再交回尚未发布的代码。只把 ORC 内部任务交给线程池、仍让 UI 线程同步等待首次查找，窗口依然要等结果。43 份语义检查也可在环境冻结后评估迁移；当前依赖选择回调直接读上版组件、写候选布局，迁移前要理清这些数据的所有权。
3. **Runtime 线程保留提交权。** 当前 `Program::prepare` 要求串行访问，本轮没有改线程契约。由所属线程取得类型环境、复核有效性、发布、绑定，并更新实例及接受帧。UI 每次重编组件会创建新 Program，同一个 Program 内的请求序号无法在两次文档保存之间仲裁；后台方案还须检查文档代次及 Runtime 身份、丢弃过期结果，并在文档关闭时收束在途任务。旧版本的退役也要走所属 Runtime。以上为下一轮设计边界，尚未实测异步延迟。

### 空白和注释经过哪一层

微软的 C# 编译器 Roslyn 构建可还原作者文本的语法树。普通空白、换行与注释存为 token 前后的 `SyntaxTrivia`，格式化和重构工具能取回原文。C# 语法规约用 token 组合表达式和语句。改动导致 token 分合、字面量内容或条件编译发生变化时，应重新判断语义。[Roslyn 语法树与 trivia](https://learn.microsoft.com/en-us/dotnet/csharp/roslyn-sdk/work-with-syntax#syntax-trivia) · [C# 词法规范](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/lexical-structure)

本项目的 Lexer 同样逐字符读过上述内容、推进字节偏移和行列，并会报告未闭合的块注释；返回给 parser 的是下一枚有效 token。UI 用原文及位置映射维护当版诊断，以 token 改写生成 Source。本次对照直接改在函数体内部，每次都经过 UI 降低；44 份生成文本均相同，全部走 `reused_source`，Source 类型检查与 JIT 均未启动。[Source 词法器](../../modules/execution/language/include/language/lexer.hpp) · [UI 改写和源码映射](../../modules/gui/ui_language/src/declaration.cpp)

## UI 机器码生成级别对照

**决定：UI 热更沿用 Aggressive。** 在这台机器上，两档为 ToolShelf 的两种高度、PropertyGroup 的两个事件版本各自产出了完全相同的机器码。切换到 Default 对目标文件生成的配对收益中位数为 0.41 ms，六对进程中有两对反向；窗口处理下一次输入仍要等约 83.3 ms。这个结论适用于当前编辑器和 LLVM 23.1.5。

### 执行和产物核验

保存计时完成后，修改 PropertyGroup 的折叠事件并还原，每次等待新版进入接受帧。ToolShelf 按钮通过宿主 ActionBinding 路由；PropertyGroup 的 `state.expanded = event.checked` 才会实际进入 Source 事件分派。在编辑器拥有的同一 Runtime 里，用已接受的组件建立独立实例，每个工具页各带一项。每进程预热后执行 12 批、交替先后次序。每批执行 1,025 次真实折叠切换，计入 6,150 次绑定求值；另投递 16,385 次交替选中与取消的事件，计时后提交并核对最终选中状态。[编辑器采样入口](../../acceptance/editor/ui_reload_profile.inl)

高度绑定单项另用 6 对进程测量。每进程先完成 56→57→56 的真实保存和帧接受，再交替测展开、折叠各 12 批。在正常脏绑定求值位置，对同一实例、真实输入和 `Row shelf.height` 的操作编号批量调用 `DefinitionState::invoke`，每批 32,768 次，批外读钟和检查结果。此项包含定型分派和宿主属性读写，完整更新在上表另列。单项耗时的配对差值范围为 −45.79 至 +67.94 ns，因此不能据两档各自的中位数判定执行快慢。这个单属性探针只用于实验。

另取两个独立进程，在计时之外各捕获 70 份优化后 IR 和 ORC 实际生成的 COFF（44 个初始组件、24 次高度重编、2 次事件重编）。两进程 IR 中嵌入的宿主函数指针相差同一个映像装载偏移，逐个核对该偏移后，70 对 IR 和可执行代码段全部一致。COFF 的其余差异是代码段的派生校验和。再将每种高度及每种事件版本各自的**同一份 IR 文件**交给锁定版本的 `llc`，使用 `-mcpu=native -relocation-model=pic -code-model=large -filetype=obj`，分别传 `-O=2` 与 `-O=3`。四对完整 COFF 均逐字节相同，指令段也与 ORC 实际产物一致。两种高度的目标文件各为 12,205 字节（指令段 9,433 字节），还原后的 PropertyGroup 为 4,153 字节（指令段 2,617 字节）。

**下一步优先验证编译期间窗口能否继续响应输入。** O2 和 COFF 生成合计仍约 51 ms。可先验证把已完成语义检查的候选交给后台生成机器码，旧版本继续出帧，由 Runtime 所属线程核对文档代次、发布并更新实例。验收同时测输入间隔与新版本接受延迟，并覆盖连续保存和候选编译失败。异步化的实际收益仍需这组场景验证。
