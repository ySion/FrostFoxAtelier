# Wave 1 双线研讨：主持裁决与推进顺序

日期：2026-09-25。对象是 [固定内容基线](baseline.json)，不是 Git diff。会议只做审查、研究、对抗、隔离实验和实施交接；**没有修生产代码，也没有实现两个新模块。** 实际实验与复现入口集中在 [证据表](evidence.md)。

**后续状态（用户授权修复后）**：A-F1成员取址与C-D1长源名诊断已修复，正式开发/发布验收及两个原始反例复跑均通过，证据见[verification.json](../../../out/review/wave1-fixes/verification.json)。下文“生产未修”等表述保留为会议当时的裁决记录；当前行为以[README](../../../README.md)为准。

## 1. 结论先行

1. **主线已有端到端闭环，但不能据此宣称正确性穷尽或性能定型。** 本轮五个意图各有探索/反方，两项真实缺陷已本机复现；若干原疑点被真实反例排除，另有明确的成本和能力边界。
2. **先修默认成员取址，再修宿主诊断保真。** 前者能写错另一实例并漏报强引用，后者使不同请求丢失身份、位置、原因。两者不是重建类型系统或发布系统的理由。
3. **性能不做一揽子重写。** 名字索引在4096宽声明场景约40.9→1.0ms，但小输入和独立块有回退；JIT的静态引用槽与早退清理规模更值得下一轮单因素实验。现阶段没有依据先共享LLJIT、削减poll或更换GC。
4. **支线正式入选 UI布局核心 + 单队列离屏RHI。** 两条实际库/SDK路径以及剔除Runtime/JIT库的独立链接均通过；下一session可以各自实施，不互相等待。正式模块、公共接口和CMake目标仍未实现。
5. 本轮19个实验可执行文件构建成功、46次进程运行有原始记录。其中取址缺陷基线退出2是预期复现，不掩饰为通过；长名诊断和混合分区实验的退出0也不能解释为产品没有缺陷。

## 2. Spec：已证实缺陷与能力边界

### A-F1：默认原生字段定位误址（P2，先修）

- 位置：`src/runtime/native.hpp:73–80`，默认locator用一元`&`，合法成员类型可重载它。
- 完整反例：实际Owner含Inner；Inner的`operator&`返回另一个仍活着的同型sentinel；只用默认NativeRegistration适配，不伪造布局、不写错误locator。
- 当前结果：应读17却读91；写73只改变sentinel，真实成员仍17；枚举强边为0、目标被GC回收。不是仅凭源码推断的潜在问题。
- 隔离修法：只在out头文件加入显式`<memory>`并改为`std::addressof`，共用原正式Runtime。读17、写后实际73/sentinel91、重载调用0、强边1且目标存活，全部通过。
- 裁决：后续生产小修应保持原类型/身份/GC机制，并把真实取址与强边反例纳入现有端到端验收。**本轮只是修法已验证，生产仍有缺陷。** 不选择禁止所有重载`&`类型的契约收缩。

### C-D1：长源名吞掉请求诊断核心（P2）

- 位置：`acceptance/jit/business.cpp:599–605`附近的prepare固定2048字节缓冲，以及后端先写完整源名的诊断格式。
- 当前真实request/prepare：源名2100字节，请求2和3分别得到完全相同的2047字节错误；请求身份、行列和原因全部丢失。
- 旧Entry仍正确执行；前端本身的Diagnostic完整。裁决限于**私有业务宿主诊断保真**，不是Parser定型、版本偏序或发布安全失效。
- 后续修法门槛：独立保留请求身份、位置和原因，对显示名作明确缩略或分离存储；不能只扩大固定缓冲。对不同请求、长短名字、parse/link失败和旧Entry继续可用做真实入口验收。本轮未试验或选定最终诊断ABI。

### D-B1：混合Standard/Finalize分区的低层能力边界

当前SDK/正式内存管理回补对象的真实SimpleSegmentAlloc实验：两个单分区对照成功；混合分区在同一reservation内自然遭遇系统释放拒绝，随后两个地址都为MEM_FREE。无mock、无OS函数替换。

这证实一个**低层不支持组合与失败清理边界**；没有证明当前业务COFF图会产出Finalize分区，探针也没有unwind action。因此不新增“当前业务泄漏”或“通用失败恢复完备”的结论，不在本轮扩修分配器。

## 3. Standards：成本裁决，不用风格盖过事实

本轮没有以文件长、容器名称或缺少抽象作为确定工程违规。A-F1同时违背默认适配内部应保证真实子对象地址的责任，但不重复统计为第三个缺陷。其余主要是成本、取舍或待证性能假设。

### C：名字索引方向有效，但当前候选不直接合入

只替换out副本的Parser名字查找；词法退出日志、Program索引、禁止shadow和诊断顺序不变。key借同步编译期的源码字节，不借会随locals扩容移动的string。

- 原41项性质A/B均通过；新增6条反方输入A/B均通过，成功Program的完整结构与错误位置/文字逐字一致。
- 4096个声明：宽声明40.8693→1.0115ms；旧参数查询57.0574→1.9374ms；最新局部查询39.0045→2.2114ms。
- 负结果不能隐去：4096独立标量块1.0851→1.1514ms，独立引用块1.5667→1.7020ms。小输入另测含编译及Program销毁，空函数约增加0.09μs（约20%）；8个独立引用块增加0.5275μs（约13%）。
- 决定：保留候选与全部数据，后续按真实源码分布决定索引策略；**不是全语言或JIT端到端40倍提速**。分配次数/字节尚未计量，也没有哈希最坏时间或沙箱保证。

### D：先研究静态槽与清理规模，不先共享LLJIT

实际16场景、80次编译/退休全部通过。顺序不相交的1/16/64个强局部仍分配3/18/66强槽；不可达声明也会增大槽布局。64块早退的编译aggregate中位约110ms，顺序块约13.5–13.7ms。此差异支持研究槽/清理IR规模，但没有内部阶段计时，不指定为LLVM某个pass、allocator或链接器造成。

下一轮优先做一个保持词法活期的非重叠槽复用或清理发射规模实验。必须保留strong/weak独立赋值、显式清理、弱取得/析构时机、旧身份拒绝、入口与实际回边poll和失败前副作用。不要把“最后一次使用”当成允许提前撤词法根；不要把host Release等同于JIT IR O2。

### B：高水位扫描与软预算是真成本，不是已证实泄漏

固定图下实测历史根/对象槽和宽深记录工作量吻合推导。N=10000：历史根10005 work；根槽均有高水位时20004；空堆历史对象槽10004。一个sweep work确实完整析构257个子记录。

20004相同work，用max_work=1需20004个poll，512需40个poll；1ns时间预算又改变每poll工作和读钟频次。探针wall同时含调用/采样成本，不能全归因collector。时间预算不是硬实时；单个原生回调、完整析构以及step外begin/屏障仍有成本。

先按真实Tick比例与已有预算做测量，不自动换collector。若未来改活跃索引，必须审查暂停游标、撤根/新根补记和work_done/死亡提交时机；直接swap-pop扫描会漏移到已扫前缀的根。跳过空洞也不是可观察时序完全不变的透明优化。

### E：版本持有转移退休成本，没有消灭它

八组合各16版本，真实prepare、publish、busy、失败与退休均通过。无旧pin时publish中位58.7–62.9μs；有pin时publish约1.7–1.9μs，但最后旧Lease释放另花54.7–61.8μs。逐行合计中位56.7–63.7μs：这是成本移动，不是优化收益。

保留32份Request与16份诊断会保留约9.6–9.7KB文本，但不阻止代码退休。进程private commit在所测后段不增长，结束仍高于起点约24.27MiB，归因未决；既不能据此判定泄漏，也不能宣称全进程无泄漏。当前数据不支持删除metadata检查、busy优先级或活动调用pin。

## 4. 支线选择与并行边界

比较了布局、离屏RHI、窗口/输入、资产、任务调度、数学/几何六类以及五种组合，保留取舍过程于 [依赖与组合报告](parallel-modules/map.md)。不是因为用户举例就直接选中。

| 入选方向 | 已证明路径 | 下一session首里程碑 | 不包含 |
| --- | --- | --- | --- |
| UI布局核心 | 固定Yoga求解、真实DirectWrite测量、修改/失效/冷树一致、DPI共享边；去除Runtime/JIT库后仍通过 | 受支持树/样式/约束→唯一求解权威→有效几何结果→销毁，封闭身份/失效/失败发布 | 控件系统、事件/焦点/IME、绘制、完整文本系统、窗口、业务绑定 |
| 单DIRECT队列离屏RHI | RX6800XT硬件、debug layer开，两次37×19精确读回、fence后释放；去除Runtime/JIT库后仍通过 | 模块自己的录制持有/取消→提交移交→Device持有in-flight→完成读回/退休→关停 | shader/PSO/draw/Present、swapchain、frame graph、多队列、通用渲染器 |

共同规则：

- 两模块不直接依赖对方，不要求Runtime/GC/JIT先扩语言能力；私有资源/布局标识不是第二套业务类型世界。
- 未来Widget/RenderComponent若属于业务对象仍接入同一Runtime。布局几何/命令描述按值，不能因为可编辑就逐个堆对象化。
- Yoga是内部求解实现，逻辑几何不重复舍入；DPI/目标像素转换由composition/output adapter单点负责，RHI不重算布局。
- GPU完成不是GC可达性。Recording先持有、submit后由Device持有in-flight；丢ticket不提前释放，未提交取消须释放录制持有，显式关停须处理在飞资源。
- **根CMake、唯一依赖锁、正式验收接线由主集成session串行负责。** 各module session拥有局部源码/验收/文档，不自行并行改共享入口。精简链接实验没有消除当前顶层CMake配置对LLVM的要求。
- 两个方向都仍有要在实现前明确的Interface细节；各模块contract/decisions区分基线约束、候选签名和未决事项，不借会议将未实现API宣称冻结。
