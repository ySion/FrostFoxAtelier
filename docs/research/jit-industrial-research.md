# JIT-only：工业实现与编译研究证据

核查日期：2026-09-24。本文记录已读的一手材料与对本项目的推论；不宣称穷尽所有论文，不把外部测量当成本项目收益。当前语言路线仍是仅 JIT、编译成功后执行、共享类型/对象/生命周期。本文不是实施完成报告，也不自动改变[语言契约](../language-contract.md)。

## 证据规则

- 工业机制以官方源码、规范和实现者文档为依据；研究工作同时核对作者版本、正式发表信息和实现范围。
- LLVM 接入结论优先对照项目锁文件对应的 `llvmorg-23.1.1`，而非把滚动 `main` 或旧 MCJIT 教程当作该版本行为。版本配置仍以 `cmake/toolchain-lock.json` 为唯一权威。
- Julia world-age 手册明确适用于 1.12+；OTP 页面当前标为 29.1.1。Roslyn 的 Supported Edits 页面仍自标 .NET 8，因此仅用于该范围，不将其称作所有新 .NET 版本的支持表。
- 源码存在某项机制只证明有实现路径，不证明配置正确。研究阶段未做 JIT 性能测量；后续独立 Windows 平台功能实验的实际范围见 [README](../../README.md#windows-jit-平台验收)，不把它扩张为所有研究方案已经落地。

本页保留调研和随后实验的历史证据，语句中的“当前/下一步”指各自记录时间。现行模块、所有权和执行合同分别见[结构说明](../runtime-structure.md)与[Runtime 协议](../runtime-model.md)；旧实施计划已经完成或被后续增量替代。

## 工业实现比较

| 实现 | 一手证实的机制 | 对我们的启发 | 不能照搬或据此推定的内容 |
| --- | --- | --- | --- |
| LLVM ORC / LLJIT | 代码生成、符号解析和链接分层；资源由 tracker 管理；锁定版本对 COFF 的默认链接层与 ELF 不同。[I1] [I2] | 复用机器码后端和链接资源管理；宿主定义代码版本所有者及发布条件。 | `remove()` 不会替我们证明没有返回地址、直接调用或缓存指针仍指向旧代码。LLVM 不是现成的语言运行时。 |
| Julia | 优化后进行 GC 根放置；用专门的 IR 表示保留 GC 相关性；普通函数执行中 world age 不自动改变。[I3] [I4] | 先规定执行中可见定义的一致性；优化不能破坏引用活性信息。 | Julia 的追踪指针、动态分派、全局绑定版本和类型重定义不是我们的代际句柄模型。不能复制地址空间编号就算完成 GC 接入。 |
| CoreCLR / Roslyn | JIT 与 GC 协作描述安全位置和根；原生与托管执行转换有状态纪律。Hot Reload 与断点态 EnC 分开处理，更新不只是改一个入口。[I5] [I6] | 明确允许收集的执行状态、根保护和原生互调；调试映射与版本应同时更新。 | 多线程挂起、移动 GC、IL/元数据 delta 不是当前 kit 的必需前提；BotR 的历史描述不是现行 API 支持清单。 |
| Erlang/OTP | 模块 current/old 版本并存；限定调用切到 current；旧代码有明确清除语义；`on_load` 失败可保留已有 current。[I7] | “新版本可调用”与“旧版本可释放”分开；初始化失败和发布成功必须有明确分界。 | 不照搬仅两版上限，也不照搬清除旧代码时终止进程的策略。BEAM 的替换规则不等于优化本机调用的依赖处理。 |
| Cranelift / Wasmtime | Cranelift 是独立的 Rust 编译后端；Wasmtime 提供更完整的 Wasm 运行环境，支持 Windows。当前官方文档明确 Winch 与 Cranelift 不自动分层晋升。[I8] [I9] | Cranelift 是真实候选，不是玩具；可以用它比较代码生成取向与工程边界。 | 采用 Cranelift 不等于免费获得 Wasmtime 的 GC、trap、调试和宿主协议；采用 Wasmtime 也不是与自有对象模型零成本等价。 |
| Unreal Engine Live Coding | 运行中补丁与 Object Reinstancing 是不同机制；结构修改涉及实例替换、指针/缓存刷新及析构寿命。[I13] | 行为修改、对象结构迁移和编辑器刷新应分别定义；已有实例不会仅因函数替换而自动完成状态迁移。 | C++ 二进制补丁不是本项目语言 JIT；不能把 UE 的宏、对象替换或析构限制直接当成自有运行时语义。 |

### 比“选哪个 JIT”更重要的共同点

以上实现各不相同，但都需要定义：执行中的引用如何可见、宿主调用怎样转换、当前调用可见哪个定义、代码资源何时不再被使用。把这些职责全部交给 LLVM，或者把它们隐藏在一个通用反射函数中，都不是从这些成熟实现得出的结论。

这是本项目的设计推论，而不是声称各实现具有相同架构。我们保留已有的单线程、非移动对象与显式根机制，不为模仿工业系统新增并发收集、动态类型世界或解释器。

## Windows：已从未知缩小到具体边界

锁定版本的 `enableDebuggerSupport(LLJIT&)` 要求 JITLink，并且只处理 ELF 和 Mach-O；COFF 进入不支持分支。[I10] 因此，不能承诺“调用这个 helper 后 Windows 源码调试就完成”。这也不能推导为“Windows 上不可能调试 JIT”。

Windows x64 对动态代码的栈展开有单独的函数表要求；调用约定也包括参数分类、栈对齐及非易失寄存器等约束。[I11] [I12] 首个接入实验必须把四件事拆开验证：执行与原生互调、展开元数据、源码/版本诊断、交互式调试器。

锁定版本的 COFF runtime 在 `registerSEHFrames` / `deregisterSEHFrames` 中调用 `RtlAddFunctionTable` / `RtlDeleteFunctionTable`，证明有登记与撤销实现路径；不证明默认 LLJIT 配置已经启用它。[I14]

同文件的 `__orc_rt_coff_cxx_throw_exception` 在无法把 `pThrowInfo` 归属到已登记 JIT 区域时报告尚不支持的回调异常路径并 `abort()`。[I14] 这是该桥接实现的具体限制，不代表所有 Windows JIT 或全部原生异常场景都失败。首轮建议在原生适配层转换 C++ 异常，不承诺任意异常跨 JIT 栈互通。

这里明确拒绝一种捷径：为了让链接成功就删除 `.pdata` / `.xdata`，再把“算术函数能返回”当作运行时已可靠。即便首版通过显式状态传递语言错误，仍不能因此放弃真实栈回溯的验证。

后续本机实验进一步发现：完整 COFF 平台有私有 COMDAT 与导入数据寻址问题，且锁定 `COFFPlatform::notifyRemoving` 尚未实现。因此最终不依赖该完整平台：保留原生 COFF/JITLink，由 allocation actions 维护系统展开表，已通过开发/发布平台验收。该结论不改变其他语言机制仍待实现的状态，详见[现行模块与取舍](../runtime-structure.md)。

## 论文与研究原型

### P1：World Age in Julia（OOPSLA 2020；扩展版 v1：2020-10-15，v2：2020-10-16）

论文对 world age 给出形式语义，核心是限制执行期间可见的方法变化，使内联等优化与动态定义共存。[P1] 它支持的设计判断是“必须定义版本可见性”，并不要求每个引擎都实现 Julia 的全部机制。

对本项目，先在最外层同步调用结束后发布，是比活动栈跨版本共存更小的候选。若以后确需挂起任务跨更新恢复，再引入相应版本持有；不能先实现复杂 world-age 调度而没有该需求。

### P2：Copy-and-Patch（预印本 2020-11-26；OOPSLA 2021）

将预先编译的机器码 stencil 拼接并修补常量和目标地址，降低运行时生成成本；论文评测了 C-like 元编程与 Wasm 用例。[P2] 它证明快速编译有别于“减少 LLVM 优化开关”的路径，但需要模板生成、ABI、目标架构及运行时协议配套。

当前不自研这一后端。其主要启发是拆解生成成本，以及把能提前完成的工作移出交互关键路径；不能把原论文的相对性能视作本项目预期收益。

### P3：TPDE（预印本 2025；CGO 2026 正式论文）

适配既有 SSA IR，以分析加单次代码生成结合指令选择、寄存器分配与编码。正式论文 §V-B 在 Linux x86-64 / AArch64、SPEC CPU2017 integer/refspeed 子集、Clang/LLVM 20.1.7 上报告：未优化 IR 的后端生成比 LLVM -O0 快 8–26 倍，包含前端的总体编译改进为 9–24%。后端计时排除了前端和必需的 LLVM-IR passes；总体数字也只覆盖论文所测编译流程，不是本项目编辑—加载—发布的总反馈延迟。[P3]

上述未优化 IR 的加速与代码质量相近结论以 LLVM -O0 为基线。论文 §V-B3 另有优化后 -O1 IR 与 LLVM -O1 后端的比较，不能将整篇论文说成只比较 -O0，也不能据前述倍数声称达到了优化后端的代码质量。[P3]

论文 §IV/§V 将 Linux/ELF 以外的平台、目标文件格式及 ABI，以及 GC 值位置追踪列为需进一步工程支持的范围；其 LLVM-IR 案例后端当时尚不支持 GC 等特性。[P3] 这些是论文所述实现的边界，不是不可改进的固有限制，也不是 TPDE 当前版本的完整能力清单。本项目据此保留关注，不把论文中的实现视为 Windows kit 的即插即用首选；后端倍数不能直接换算成编辑体验。

### P4：Deegen（PACMPL 10 OOPSLA1，2026 年 4 月）

作者页面及正式发表信息说明，它从 C++ 描述的动态语言字节码语义生成解释器、Copy-and-Patch baseline JIT 及层间切换逻辑。[P4] 统一语义生产多条执行路径的工程思想有价值，但其核心问题与本项目静态类型、JIT-only 的已确认方向不同。

不为了采用 Deegen 而重新引入解释器与动态值世界。也不把其 VM 基准直接当作原生对象互调、GC、热重载和 Windows 工具链已经完整验证的证据。

## 当前取舍

- **优先验证**：LLVM ORC 接入、定型调用、显式执行根、代码资源所有权及受控发布。
- **借鉴机制而非移植系统**：Julia 的可见性与根放置原则、CoreCLR 的执行转换纪律、OTP 的发布/清除分离。
- **保留可比较候选**：Cranelift；在本项目实际编译延迟成为问题时，再进行相同 ABI/根/诊断条件下的对比。
- **暂不采用**：自研 copy-and-patch 后端、Deegen 双层 VM、为追求论文倍数直接替换 LLVM、自动多层 JIT 晋升、OSR 和通用对象迁移。

## 平台测量（2026-09-24）

平台探针的本机测量，不等同于完整业务语言或行为热重载。实现入口为 [backend.cpp](../../acceptance/jit/backend.cpp)。

### 测量方法与结果

一次性驱动直接复用 `backend.cpp`，链接正式 Release 目标的 LLVM 库、回移内存管理器、共享 mimalloc 和真实原生 DLL；LLVM 侧保持 `/O2`、`/MT`、Large/PIC。没有新增正式基准工程。三个新进程顺序运行，各保留一个可调用单元：先退休 3,000 个唯一命名单元，再复用同名退休 3,000 个单元；过程中交错两类登记后失败注入，并验证旧代码仍可调用。每个退休地址立即检查 `MEM_FREE`，尚未进行下一次分配，避免地址复用混淆结果。

每个微型单元含三个生成函数以及常量、可变状态。物化计时包括构造 IR、代码生成、链接/登记和五次符号查询，不是纯 LLVM 编译器耗时。退休计时覆盖 `ResourceTracker::remove`，不包含后续断言。热调用为已缓存入口的成功路径，含混合参数、真实 DLL 调用、宿主回调、状态更新、循环和结果累加；每进程 15 组、每组一百万次，组后核对结果与计数。以下范围是三个进程各自统计量的范围，不是置信区间，亦未控制处理器频率或后台调度。

| 项目 | 本机实测 |
| --- | --- |
| 热调用组均值的中位数 | 15.4–15.8 ns/次；不能当作任意业务方法成本 |
| 单元物化中位数 | 2.68–3.06 ms；各组 P95 为 3.82–4.43 ms |
| 单元退休中位数 | 28.7–36.5 μs；各组 P95 为 47.8–64.6 μs |
| 长会话退休 | 三进程累计 18,000 个单元；每个分配均通过释放检查 |
| 同时存活单元 | 分别为 1、16、128、512，全部能查展开表、执行并退休 |
| 512 单元的展开表查询 | 每进程十万次，均值 77.5–90.6 ns，含地址选择与结果检查 |
| 512 单元新增私有可执行页 | 2 MiB；全进程私有提交增量约 36.7 MiB，二者不能混称代码大小 |

长期退休阶段私有可执行页始终回到唯一保留单元的 4 KiB；JIT 退出后为零，没有残留 RWX 私有页。**不等于全进程零内存增长**：整个驱动结束时私有提交约 32.5 MiB，高于进入长会话前约 27.8 MiB，仍含 LLVM、分配器和元数据存储。唯一命名阶段第 1,000/2,000/3,000 次后的私有提交约为 31.9/28.8/28.5 MiB，未呈线性增长；有限样本不能证明所有长期内存路径均无泄漏。显式 `clearDeadEntries` 并未立即降低进程提交量，不把它包装成已经验证的通用降内存方案。

另外，正式 DLL 入口连续执行 128 轮完整验收，退出码为零；冷轮 166.25 ms，后续中位数 41.53 ms、P95 52.39 ms，结束时私有可执行页和 RWX 私有页均为零。早期轮次没有后来增加的失败与大栈场景，**不能把前后整轮时长当作等负载优化对照**。

### 结论

新增/替换循环的主要成本在物化，不在简单定型调用或已测规模的 Windows 展开表查询。小单元有明显的页粒度与元数据开销，编译粒度应按真实业务的共同发布/退休边界选择，而不是为每个小函数建立独立单元或重写可执行内存堆。是否更换编译后端、增加多层 JIT 或扩大内联，需要相同业务契约下的对照，不能由微型样例或论文倍数直接决定。

## 业务贯通的调查与取舍

核查了现有根/回调/GC 实现、机器业务与 CRT seam，以及 LLVM/Julia 和 AngelScript/CoreCLR 一手资料，并以根生命周期、ABI/代码寿命、业务真实性与复杂度进行对抗分析。最终实现没有复制外部运行时体系，当前行为的权威说明在[最小业务执行协议](../runtime-model.md#业务执行协议)。

- LLVM/Julia 的资料用来检查安全点活引用可见性、调用中间值与返回交接，不能直接推导本项目必须采用 statepoint、stack map 或 Julia 的对象表示。[I3][I15][I16][I17] 本例只有两个对象引用槽，复用现有 `ObjectRoot` 足够；通用含引用值帧仍按实际业务需求另做。
- AngelScript 的宿主收集入口与 CoreCLR 的原生执行协调用于交叉检查“哪里可收集”，不是引入线程 GC mode 的理由。[I5][I18] 本项目只增加只读执行准入，保留普通 `Runtime::call` 的借用保护，并在其返回后轮询现有收集器。
- 对抗反例一：把完整 JIT 方法注册成旧 `Invoker`，外层 `CallbackScope` 会一直存在，内部 GC 必定 `busy`；不能暂时减保护计数。反例二：撤返回根、收集、再 `hold(ObjectReference)` 可能只登记一个 stale 身份；必须移交已有根。反例三：回调撤销外层代码 owner 会让未返回的机器码悬空；调用局部 pin 到返回后才释放，不需要先造热重载服务。
- 复杂度裁决：只保留现有 progress/heat/cycles 与 advance，不新增配方、阈值、库存或另一类“脚本业务对象”；循环、正值分支、计数与快照操作确实由 IR 驱动；桥接在绑定时缓存元数据。
- 验收反例要求快照先出生、再经历完整新 GC 周期，并有无根死亡对照；晚根场景必须在旧周期结束后再开新周期，不能把“新对象本轮被补标”冒充执行根有效。IR 显式清理在 host RAII 之前验空，另行验证 RAII，以免兜底掩盖生成代码漏清理。

## 源码执行链测量基线

### 测量方法

硬件为本机 Ryzen 9 3950X、32 个逻辑处理器、约 64 GiB 内存，Windows 构建 26200。使用锁文件对应的 Release 工具链、正式 Runtime/JIT DLL 和共享 mimalloc。三个新进程**串行**运行，主测量线程固定在逻辑 CPU 2；未锁处理器频率、未隔离其他系统活动。每个批量场景预热 3 批、记录 21 批；下表范围是三个进程各自统计量的最小/最大值，不是置信区间，也不是 P99 保证。

场景包含 1,000/10,000 个真实存活机器、每次 1/16 个业务步骤、原生/描述型类型，以及两种收集策略。源函数编译在批量计时之外，每批每台机器调用一次，参数为 `amount=0.25`。

- **调用区间**包括真实执行准入、根登记、快照创建/同步/移交、源码机器码、服务桥接和安全点；接收者初始化、编译及逐个结果断言不计时。
- **收集策略**一是不在调用中提出新请求；二是每批首台机器提出请求，生成安全点以工作预算 1 推进。后者不意味着所有轮询都处于 GC 活动状态。
- **回收区间**计时释放所有输出根、结束未完成周期，并以工作预算 256 完成一个新周期。每批验证根数与存活对象数精确回到接收者数量，不把未回收快照当成根泄漏，也不把其成本留到未计时的未来。
- “总计”是调用与回收两个计时间隔相加，不含中间结果核对；它仍不是完整游戏 Tick。记录各阶段中位数/P95、每机器调用摊销和进程私有提交采样，未做分配次数归因或高频峰值采样。
- 前端规模实验在单独链接的同一份源码上运行，采用宿主 Release `/MD`，包含 AST 销毁；业务 DLL 自身为 `/MT`，因此该实验不是 DLL 内部各阶段耗时的直接分解。

### 编译与规模结果

| 场景 | 三进程实测范围 |
| --- | --- |
| 首次编译默认 409 字节源码 | 8.35–9.96 ms；每进程一次，不含启动/加载 DLL 和读文件 |
| 后续编译，仍每次新建 LLJIT | 中位数 4.52–4.66 ms；P95 5.82–7.05 ms |
| 对应代码及 LLJIT 销毁 | 中位数 0.0547–0.0608 ms |
| 前端：100 个局部，2,027 字节 | 中位数 0.0524–0.0536 ms |
| 前端：500 个局部，10,427 字节 | 中位数 0.802–0.974 ms |
| 前端：2,000 个局部，42,927 字节 | 中位数 9.51–10.19 ms |
| 前端：8,000 个局部，174,927 字节 | 中位数 219.11–221.99 ms |

局部声明查重逐次扫描可见名字，重复声明检查也存在；从代码可推导同一大作用域的累计平方级工作，规模实验呈现明显的非线性增长。这是大函数输入的实测扩展性风险，不等于小型业务函数的前端已成为主要延迟来源。

### 真实批量调用结果

以下为 **10,000 台机器、不在调用中提出 GC 请求**；单位均为 ms/批。每批结束仍执行并计量回收。

| 类型 | 每台步骤 | 调用中位数 | 调用 P95 | 回收中位数 | 总计中位数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 原生 | 1 | 10.03–10.22 | 11.45–12.09 | 0.408–0.463 | 10.43–10.69 |
| 描述型 | 1 | 12.09–12.79 | 14.68–17.44 | 0.426–0.441 | 12.52–13.37 |
| 原生 | 16 | 65.81–68.48 | 70.62–81.79 | 0.450–0.484 | 66.25–69.06 |
| 描述型 | 16 | 77.62–81.21 | 83.05–102.21 | 0.442–0.489 | 78.21–81.82 |

另测相同宿主协议下 **1,000 台机器**的空函数、仅计数循环和完整业务，均不在调用中请求 GC；后两者循环 16 次。调用中位数为：

| 类型 | 空函数 | 仅计数循环 | 完整业务 |
| --- | ---: | ---: | ---: |
| 原生 | 0.603–0.644 | 3.848–4.092 | 5.644–5.908 |
| 描述型 | 0.748–0.873 | 4.783–4.938 | 7.740–8.394 |

**不能把“仅计数循环”称为纯算术基准。** 它仍执行每回边安全点和快照同步。静态计数显示默认正值业务执行 N 步包含 `10N+17` 次宿主服务调用，其中快照读写为 `6N+12`；这些是路径计数，不是耗时占比。对照证明业务推进之外的协议成本不可忽略，但还不能把全部差值归给快照或某个 Runtime 检查。

## 快照、字段桥接与安全点单因素实验

### 范围与不变量

三个变体均未进入正式执行路径。实验使用独立的实验源文件和驱动、既有 Release Runtime、共享 mimalloc、原生客户端和同一源码用例；不改正式前端、Runtime/GC 或源码可观察规则。

| 变体 | 唯一机制变化 | 保留的语义 |
| --- | --- | --- |
| B：基线 | 复用正式业务适配器与后端 | 原有执行协议 |
| S：快照合并 | 同一同步位置的六次 JIT→宿主服务调用，改为一次宿主 `copy_snapshot`；内部仍执行原六次 Runtime 读写 | 原顺序、每项状态短路、首错、已完成的部分写入和原生定位回调顺序；不是原子复制，不减少同步次数 |
| F：固定字段选择器 | progress/heat 的四个专用桥接入口固定选择器，仍进入原有读写服务及 Runtime API | 类型/身份/存活检查不减少；不缓存对象裸地址，不改为直接字段访问 |
| P：轮询同单元内联 | 把相同的 `ExecutionFrame::poll` 函数体放入宿主桥接编译单元并强制内联，其他帧方法仍分离编译 | 入口及实际回边轮询次数、预算验证、请求合并、GC 工作和 Hook 顺序不变；不是删除安全点或内联整个 Runtime |

### 语义检查

四个版本分别通过原业务验收及源码扩展驱动的 `--check`。另以相同场景采集 **448 条场景记录、59,976 对标记/值观测事件**：检查原生定位回调、每次安全点/原生动作所见的接收者与快照、根与清理、错误及确定性的 GC 轨迹。Hook 可改字段及下一次预算；合法的定位回调可撤销帧根，用于检查首错与部分写入，不靠非法空地址制造错误。

S/F/P 与 B 的场景记录和事件序列逐项相同，无差异。差分不比较耗时，GC 轨迹对照采用工作预算 1、时间预算 0；不能据此保证带时钟分支的外部观察者在所有运行中产生相同结果。补测驱动重编译后再次运行四个 `--trace`，仍与最初基线完全一致。COFF 导入表另确认 S/F 实际加载各自的实验 JIT DLL，B/P 加载正式业务 JIT DLL，避免把错连基线误判为变体等价。

### 计时与判定

先对 B/S/F/P 各运行三个串行进程，轮换顺序，覆盖上一节全部批量场景。10,000 台机器、每台 16 步、不在调用中请求 GC 的基线调用中位数，原生为 64.74–78.70 ms，描述型为 81.71–88.94 ms；变体相对收益方向随轮次变化，不能从这组三轮直接挑选最快版本。

随后补测同一重点场景：仍固定主线程到逻辑 CPU 2，每进程预热 3 批、记录 21 批，同时记录墙钟与 `QueryThreadCycleTime` 差值。三个轮次分别采用 B/S/F/P/P/F/S/B、B/F/P/S/S/P/F/B、B/P/S/F/F/S/P/B，共 24 个串行进程。每轮以首尾两个 B 的中位数均值为基线，以两个相同变体的中位数均值为候选，计算 `100 × (1 − 候选 / 基线)`。下表是三个轮次该指标的范围，**正数表示减少，负数表示增加，不是置信区间**。

| 变体 | 类型 | 调用墙钟减少 | 线程周期计数减少 |
| --- | --- | ---: | ---: |
| S：快照合并 | 原生 | −2.67% ～ −0.76% | −2.03% ～ −0.39% |
| S：快照合并 | 描述型 | +0.00% ～ +1.68% | −0.47% ～ +0.98% |
| F：固定选择器 | 原生 | −3.29% ～ +1.87% | −2.21% ～ +1.75% |
| F：固定选择器 | 描述型 | +0.15% ～ +1.79% | −0.06% ～ +1.13% |
| P：轮询内联 | 原生 | −1.38% ～ +3.29% | −1.05% ～ +3.25% |
| P：轮询内联 | 描述型 | −0.38% ～ +2.31% | −0.51% ～ +2.69% |

`QueryThreadCycleTime` 计数包含用户态和内核态，不能直接换算成墙钟时间；此处也不把它当作退休指令数。[I19] 未锁定 CPU 频率、隔离系统活动或控制不同二进制的所有代码布局因素；交错顺序和第二种计数只用于补充对照，不消除这些限制。

**决策：没有足够稳定、跨类型一致的收益，暂不合入任何一个变体，也不叠加三项冒充已验证的组合优化。** S 原生场景还持续出现小幅回退，F/P 的方向也有翻转。共同的 Runtime 读写与验证并未减少，因此调用数量下降本身不是耗时同比下降的证据；未做内部采样，不能进一步断言某项检查占主导。此结论针对本机、当前代码与以上场景，不等于证明桥接永远无法优化。
