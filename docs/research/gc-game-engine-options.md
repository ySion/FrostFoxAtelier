# 非移动 GC 与游戏引擎 stage：方案比较

核查日期：2026-09-21。通过 Exa 与官方网页/论文检索；本轮是方案研究，没有实现 GC 或测量游戏性能。已确认的项目契约见[语言契约](../language-contract.md#所有权与销毁)：自动回收不可达环、随 Tick 渐进推进、GC 不移动存活对象。stage 是否覆盖所有访问业务对象的任务仍未确定。

## 最值得进一步验证的机制

| 方向 | 来源及成熟度 | 对项目的意义 | 边界 |
| --- | --- | --- | --- |
| CPT/CDPT：部分追踪与阶段协作 | [PLDI 2026 官方论文页](https://pldi26.sigplan.org/details/pldi-2026-papers/67/Revisiting-Partial-Tracing-for-Safe-Efficient-and-Concurrent-Garbage-Collection-in-)；研究型库 | 精确保护根、追踪堆处理循环；phase consensus 协调收集阶段，CDPT 用带 phase barrier 的本地保护槽降低根更新代价。与原生互操作、显式协作点高度相关 | 作者评估并发数据结构与 Moka 缓存，未证明游戏帧预算；论文中的 GC phase 不自动等于引擎 stage，需要保持其进入/退出与引用保护协议 |
| Nofl：精确回收对象间空隙 | [Nofl: A Precise Immix，2025 预印本](https://arxiv.org/abs/2503.16971)；早期评估 | 将 Immix 的空间回收精度细化到最小分配粒度，固定 non-compacting 配置后可保持地址稳定 | 论文 collector 仍是 STW，评测含可选搬迁；lazy sweep 会把工作放进分配路径。空间管理可借鉴，跨 Tick 的收集调度仍需另做 |
| LXR：合并引用更新的混合 GC | [PLDI 2022](https://www.steveblackburn.org/pubs/papers/lxr-pldi-2022.pdf)、[OOPSLA 2025 后续](https://www.steveblackburn.org/pubs/papers/prod-oopsla-2025.pdf)；研究/产品化探索 | 同一字段在一个 GC epoch 中多次修改，只为其最初旧值与最终新值结算 RC；结合追踪处理循环，适合研究阶段内引用更新的批量记账 | 原算法复制年轻存活对象并搬迁碎片 block，不符合硬约束；只能借用机制，非移动变体是新 collector，不能继承原论文性能 |
| MMU 与周期性工作配额 | [Metronome，POPL 2003](https://research.ibm.com/publications/a-real-time-garbage-collector-with-low-overhead-and-consistent-utilization--2)；经典实时 GC 研究 | 除单次暂停外，考察任意时间窗口内业务线程至少获得多少执行时间，适合分析密集小暂停导致的帧抖动 | 只借调度思想；原 collector 的有限搬迁不适用，硬实时结论也不能直接移植到任意 C++/Windows 工作负载 |

CPT/CDPT 的“根计数、堆追踪”仍然是 GC，可以处理循环，并非要求业务手动拆环。我们拥有类型描述和未来编译器，因此应比较论文的本地保护槽与显式根表/精确栈图，不必照搬为缺少编译器支持而承担的全部成本。LLVM 官方提供根、栈图及 safepoint 的编译器接入机制，但不提供 collector；非移动回收仍需要正确报告活引用。[LLVM GC 文档](https://llvm.org/docs/GarbageCollection.html)

CDPT 仍有 Yuasa 删除屏障：覆写引用时保留被删边所需的标记信息；phase barrier 负责另一部分根一致性问题，二者不能互相替代。它与 LXR 的计数对象、屏障及周期规则不同，应作为两条备选主线分析，不把所有优化叠加为一个未经证明的算法。论文机制及实现限制详见[近期论文核查](gc-recent-papers.md)。

ZGC/Shenandoah 的并发搬迁不是候选。可以研究它们的阶段协调、分代记录及开销分布，但本项目无需为搬迁引入转发表、重映射和相关读屏障。根一致性、引用更新及后台工作的 CPU/带宽竞争仍需处理。详见[工业方案核查](gc-industrial-low-latency.md)。

## stage 能提供的实际优势

以下是项目设计推论，不是论文对游戏引擎的性能承诺。

建议将 stage 当作**根及引用改动的发布点、GC 工作的调度点**：

```text
业务任务执行 → 按协议发布根/引用改动 → 推进一段 GC 工作 → 下一业务阶段
                     ↑                        │
                     └── 同一轮收集可跨越多个阶段 ┘
```

- 若所有参与任务在边界都报告根并协作静止，可集中处理根快照、标记终止确认和日志排空；纯数据计算任务不必因为游戏主线程进入 GC stage 就一律停下，前提是它们确实不访问被收集的对象图。
- 若只有主线程轮询，worker 的引用和修改仍需独立纳入协议。主线程结束一次 Tick 不证明整个对象图处于安全状态。
- 完整收集若在对象图始终静止期间完成，可以免去维持增量可达性的堆写屏障；收集跨多个 stage、期间业务恢复修改时，仍需写屏障或等效保护。阶段末扫描最终字段值并不足以自动证明安全。
- 可以探索同一阶段内对同一字段的多次引用修改合并记账，但必须保存所选算法要求的旧/新信息，并保护阶段内短暂存在的引用。不能直接把日志去重当作正确的 GC 算法。
- 非移动允许保持现有原生地址，但对象销毁与回收仍会使借用失效。能跨越 stage 的持有关系必须可见，不能因地址不搬迁就无限期缓存未登记指针。

全局 stage 与论文中的 phase-critical section 是不同层次的约束：前者是任务调度位置，后者规定哪些引用操作能发生、何时可以推进 GC。可以在任务入口/出口接入后者，但需要完整遵守协议；也要处理长任务、不轮询的原生调用和阻塞。

## 对我们当前架构的建议

1. **保留一个简单的精确、非移动追踪基线。** 不提前冻结为永久单线程或某个清扫布局，用它衡量进一步机制是否有收益。
2. **优先验证阶段协作和根管理。** CPT/CDPT 是本轮最有针对性的前沿阅读对象；将其正确性条件映射到 C++ 持有者、任务临时引用、语言栈与世界根，再决定采用多少机制。
3. **独立评估分配与回收布局。** Nofl/Immix 的空间管理并不自动提供低延迟调度。使用专门 block/line 布局需要真实分配器接入，不能仅改标记循环；它也不是对现有 mimalloc 默认分配约定的自动替换。
4. **利用已知生命周期减少追踪负担。** 可证明不逃逸的程序化计算临时数据可随批次释放；含持有引用的临时数据仍要报告引用与执行值销毁。不能把所有业务对象粗略按关卡或帧成批释放。

这些机制不意味着把数种论文算法直接拼在一起。根协议、引用写入、循环判定和回收提交必须满足一套完整不变量；堆布局与调度可以分别比较，替换主算法后要重新验证组合。

## 后续如何判断收益

非移动能确定消除存活对象复制、地址修复及专为搬迁设置的屏障/转发工作，但不保证 GC 总成本大幅下降。仍需付出根处理、可达性追踪、引用更新保护、析构和内存复用的成本；碎片及寻找可用空间可能增加分配慢路径成本。长期存活图很大时，减少重复追踪的收益可能比取消复制更重要。GC 时间、业务热路径、分配延迟和内存占用需要合计评估，不能只统计 `gc_step` 的耗时。[Nofl 的算法取舍分析](https://arxiv.org/html/2503.16971)；[JEP 439：减少重复收集长寿命对象的动机](https://openjdk.org/jeps/439)

选择与游戏相关的工作负载：长期存活对象图中的频繁连接修改、带引用环的分区卸载，以及程序化批次产生的短命数据。记录帧/stage 时间分位数、安全点到达延迟、GC 总 CPU、引用写入成本、分配慢路径、峰值内存和待回收积压。客户端与专用服务器可以采用不同预算策略，保持同一引用语义。

本轮没有用 JVM、Scheme 或缓存基准推算本项目速度。最新论文的价值是提供可验证的机制和取舍，是否优于简单基线仍取决于上述实测。
