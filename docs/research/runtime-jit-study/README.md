# Runtime 字段路径、Remap bitcode 与 mimalloc

2026-11-22，Windows x64、Ryzen 9 3950X、clang-cl / LLVM 23.1.5、Release。三个实验分开改变变量。百分比先按同轮配对，再取中位数。工程使用既有的 Source、Runtime、Editor 和构建入口。

## mimalloc 3.5.3 → 3.7.0

升级的依据是上游修复。3.6 系列修正了堆遍历漏页、复用堆地址时的销毁问题，调整了超大分配清退与跨线程页回收，并增加了分配剖析能力。3.7.0 修复 arena purge 遗漏，改善资源统计样本，并新增面向支持硬件的内存标记。Windows x64 本次使用普通发布配置。构建继续从官方源码包编译共享 DLL、使用 Windows redirect，并将原 stderr 补丁迁到上游的新文件位置。下载的 SHA-256 与官方 release 资产 digest 一致。[上游变更记录](https://github.com/microsoft/mimalloc/blob/v3.7.0/readme.md#releases) · [锁文件](../../../cmake/dependencies-lock.json)

同一个 Foundation/Runtime 回放可执行文件，分别加载各自的 allocator 和 redirect DLL，固定逻辑处理器 18，交替运行 18 对独立进程。46 类型注册 118.92 → 119.38 µs，配对 +0.08%。Procedural 网格导入 135.51 → 136.48 µs，+0.59%。注册后存活分配均为 772 块，占用 238,096 → 237,968 B。此处的吞吐差异不足以作为升级理由。

## Clang bitcode 在真实 LLJIT 中的执行

用工程的 Release clang-cl 为 Windows MSVC x64 编译两个 C++ 叶函数，直接调用 `Array<float>` 和 `Array<bool>` 的 `data()` / `size()`。实验 DLL 在可识别的 Remap 输入上以具名声明取代已有序列投影回调，在同一 LLVMContext 读取 4,476 B 的 bitcode，用 `LinkOnlyNeeded` 链入并内化，继续走原有 O2、ORC COFF 链接与 Windows unwind 注册。宿主通过真实 `Program::entry("procedural.Remap.process")` 执行，检查带组和不带组的全部输出。这个映射只用于已知原生表示的实验输入。生产 JIT 保留现有回调协议。[Remap](../../../assets/engine/procedural/remap.source) · [现有投影](../../../modules/execution/jit/src/source_backend.cpp)

对照组的三个序列投影调用都在定型入口。引入 bitcode 后，三个调用均被内联，COFF 的 .text 从 1,497 B 降为 1,417 B。两条并行 worker 的机器码逐字节相同，默认布局下分别占 208 和 233 B（按反汇编标签区间，含对齐填充）。每个元素的计算、范围检查和失败传播均保持原样。

最终测量在同一研究 DLL、同一进程内同时保活两个独立 Runtime 和各自的 Remap 机器码，在同一工作线程池和同一组缓冲区上交替调用。固定 16 个逻辑处理器，交换两版本创建次序。此实验两端使用 mimalloc 3.5.3。每种控制条件 8 个进程，每种输入每进程保留 16 组成对采样。额外比较两个普通 JIT 实例作为对照，并单独固定 worker 的 64 B 对齐。两个独立可执行映像初测出的明显增益未在这一控制下复现。

| 调用规模 | 普通投影 | bitcode | 配对变化 |
| --- | ---: | ---: | ---: |
| 64 项，全选 | 726 ns | 716 ns | −1.60% |
| 64 项，交替选中 | 694 ns | 678 ns | −2.04% |
| 1,048,576 项，全选 | 241.61 µs | 241.17 µs | +0.15% |
| 1,048,576 项，交替选中 | 136.47 µs | 138.07 µs | +1.33% |

64 B 对齐后两项百万元素指标为 0.00% 和 +0.57%。标准工具链可以实现这套方案。在本内核里，三次调用属于每次调度的固定开销，增加生产 bitcode 构建与 ABI 维护的收益有限。

## 两级字段路径

原 Runtime 已能直接遍历纯偏移路径。在同一入口比较两种直接映射缓存。4 槽对照按末级字段选槽，最终 16 槽方案按两级字段索引共同选槽，使相邻向量的相同轴可以共存。命中必须同时匹配实际根类型和两个完整 FieldId。成功解析才写入缓存，保留合成字节偏移、叶类型及沿路径生效的硬范围。对象地址与对象身份均不进入缓存。新对象每次从已验证的活槽取基址，动态数组和原生寻址回调继续使用原解析逻辑。缓存固定占用每个 Runtime 1,280 B，独立于对象数，无额外堆分配。冲突只替换一项。[实现](../../../modules/execution/runtime/src/runtime.cpp) · [现有对象与嵌套字段验收](../../../acceptance/runtime/main.cpp)

用真实 Editor Session 新建带 Transform 的 Entity，轮询位置三个轴、轮询位置/旋转/缩放十条路径、枚举完整属性面板，再通过 begin/preview/commit 连续提交单轴改动并读回结果。两端均使用同版分配器，固定逻辑处理器 18，以进程为单位交替先后。另一项候选仅快速匹配声明类型，在最初 30 对进程里未改善位置读取。

在全套依赖完成 3.7.0 重编之后，再使用同一份驱动对象、相同归档成员顺序和相同链接位置做 48 轮三方对照。4 槽方案在十路径轮询慢 1.01%，完整 Inspector 慢 0.90%。16 槽使二者分别快 1.78% 和 0.54%，连续拖动近似持平（+0.12%）。这组数据是选择 16 槽的依据。此前另链 Runtime 对象得到的“面板快约 5%”没有在同条件下复现。

将 16 槽版本放回常规产品构建后，再交替运行 36 对进程。两端均使用最后一轮宿主库及 mimalloc 3.7.0，对照只换回原字段解析实现。表内为进程中位数及同轮配对变化。

| 真实调用 | 原路径 | 最终版 | 配对变化 |
| --- | ---: | ---: | ---: |
| Runtime 读取位置轴 | 21.61 ns | 18.68 ns | −13.94% |
| Session 读取位置轴 | 196.12 ns | 193.40 ns | −1.20% |
| Session 轮询十个 Transform 分量，每次读取 | 195.85 ns | 191.99 ns | −2.21% |
| 一次完整 Inspector 属性枚举 | 6.051 µs | 6.004 µs | −0.66% |
| 拖动期间一次 `preview_edit` | 825.98 ns | 818.16 ns | −1.33% |

这里的面板枚举不含窗口绘制。每个 Runtime 为缓存付费一次，完整面板的绝对差距约 47 ns。保留这项内部优化，公开字段读写入口和错误合同沿用原实现。[各轮原始数据](samples.csv.gz)

## 验收

分配器升级后 dev、release 各通过全部 15 项无窗口与 5 项窗口验收。最终 16 槽实现随两个配置重新全量编译，并各自通过 Runtime、Source、World、Procedural 和编辑器文档验收。嵌套字段验收覆盖同叶不同父路径、不同对象的存储基址、声明类型错误、硬范围及退役对象。设置 `MIMALLOC_VERBOSE=1` 的独立进程核对了加载版本 30700、stderr 为空。
