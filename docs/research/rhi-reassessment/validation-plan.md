# RHI 路径验证方案（待讨论批准）

本文件承接 [研究约定](research-brief.md) 与 [评估框架](evaluation-framework.md)，把调研问题转成可失败的真实实验。**以下实验尚未执行，不存在本轮 build/GPU/PASS 或性能结论。** 候选差异来自各专项报告，未形成生产选型。

## 1. 进入验证前必须明确的输入

1. 首个真实消费者及最重要的一条工作链。图形、编辑器/UI、程序化计算的优先级不能由旧离屏 demo 代替。
2. 硬件与平台支持边界，以及近期是否真的需要第二后端。当前 Windows x64 背景不足以替代 GPU/驱动/Shader 能力要求。
3. 产品故障策略：允许诊断后结束渲染会话/进程，还是必须在同进程重建设备与资源。不能在不知道要求时把“无透明恢复”当作淘汰条件。
4. 引擎必须自己拥有的语义：是否有确定的线程/提交模型、外部 GPU 互操作、资源分配身份或 Shader 资产 ABI。未确定的部分不应为排除库而反向制造。

这些是产品与架构输入。容器选择、方法拼写、是否把内部辅助类拆成文件不是此阶段的用户决策门槛。

后续讨论已明确：首个背景消费者是 3D 视口，当前交付只做 RHI；Mesh Shader 为最低硬件要求，不做旧 GPU 回退；Vertex、Mesh、Compute 都是正式能力。仍需收敛的是绑定、状态与提交权威、并发需求和故障终态，不再把三类管线是否需要列作未决问题。

## 2. 候选如何进入实验

- **原生后端基线**：只实现与比较负载相关的必要机制，不先造完整“自研 RHI”再证明它有必要。
- **NVRHI / DiligentCore**：作为低层机制复用候选。前者重点验证录制实例、tracker/GC、状态交接与错误出口；后者重点验证 deferred 提交前持有、SRB 更新、FinishFrame/Flush 周期与构建闭包。
- **gfx**：固定版本与证据见 [源码核对](gfx.md)。三类管线及 interop 已有实现；重点验证状态交接、帧推进与退休责任，以及完成/失败能否符合目标契约。不可仅凭原型定位排除，也不可仅凭能力清单批准。
- **bgfx / SDL GPU / wgpu-native**：当产品愿意接受其调度、绑定、线程或安全模型时，可作为应用级 GPU 基础进入同等负载比较；不能只因 Interface 形状不同淘汰。
- **Unreal / Godot / Filament**：本轮作为机制参照，不作为已经批准的可抽取底层库。
- **论文与演讲**：提出布局、调度和层次的反例；不是自动添加 render graph、CUDA 或 shader 编译器的需求来源。

建议先选少量能回答当前决策的路线。此建议是控制实验变量，不是给未选择候选作能力否定。

## 3. 实验顺序与停止条件

### V0：固定证据与可重现构建

- 为参与实验的实际版本固定源码提交、依赖提交/归档 hash、构建选项、Shader 工具及产物、运行库和许可/notice 清单。
- 不能把本轮 DiligentCore v2.5.6、Godot 4.4-stable、Filament v1.56.0 样本或滚动文档当作“当前最新版”的比较。若改用其他版本，先复核决定性差异；不能用旧快照淘汰新版本。
- 使用项目锁定工具链及既有构建入口；实验目标由统一构建规则表达，不为每个候选建立永久平行构建系统。所有输出留在本 worktree，禁止共用主工作区的 `out/`。
- 验证开始时检查本 worktree 的工具缓存与 SDK 就绪状态，不从其他工作区的结果推定成功。可规划复用已验证的锁定 SDK 目录，但不未经说明复制 SDK、建立目录链接或改变全局环境。
- 编译所需目标并实际启动 dev/release 消费者；区分配置失败、编译失败、链接失败和运行缺件，不以配置成功作为接入成功。

**停止条件**：无法固定真实依赖或最小目标闭包；必须引入未批准的重大工具链/运行库变更；许可证/分发工件信息不足。停止并记录缺口，不靠删除检查或换未锁定依赖继续。

### V1：同一消费者，比较职责而非函数形状

结合已确认需求，建议同一最小消费者用 Compute 写数据和间接参数，再分别通过 Vertex 与 Mesh 路径消费并输出颜色/深度，最后回读核对。先查询实际 Mesh Shader 能力并编译 shader，不以设备型号推定支持；间接参数须真实来自 GPU。资源访问与状态交接按拟定 RDG/RHI 边界表达，但不为验证搭建完整 Renderer、场景系统或程序化建模系统。该负载是下一阶段验证提案，尚未执行。

每个候选用其合法、惯用的公开 Interface 表达同一语义；原生路径、library 路径可以调用不同数量的函数。比较结果、责任分配及适配工作，不要求所有候选先模仿我们臆定的 CommandList 类。

**记录**：实际来源/依赖、输入、编译产物、命令、退出码、adapter/driver、验证层配置、GPU 输出校验、调用方承担的资源/状态/呈现责任。

**停止条件**：必需语义只能通过不受支持的原生逃生口、侵入库或第二套相互矛盾的状态管理来表达。缺少尚未批准的可选高级功能不是停止条件。

### V2：录制、提交和数据版本的生命链

- 覆盖未提交录制、取消/放弃、提交后调用方释放、较晚批次仍引用资源、多个在飞数据版本、最终排空与物理回收。
- 普通 binding、动态更新、显式 staging、原生 import/escape 分别验证；不把普通路径的自动保护推广到退出保护的特殊路径。
- 按候选契约进行合法操作。若库要求调用方保留 deferred 资源，则让适配路径明确保留并记录其代价；不能故意违反契约后宣称库有缺陷。
- 如需确定性 pending，只使用获准的真实同步/完成机制；不靠固定睡眠、延迟若干帧、伪造完成值或大量 GPU 工作碰时序。

**通过依据**：可预测输出、真实完成证据、可解释的持有/释放关系与回收到稳定基线。没有崩溃、CPU 引用归零或命令已排队均不足以替代。

### V3：Shader、绑定与热更新边界

- 由真实 shader/参数数据验证布局、offset、stride、资源种类与绑定位置；不假定自有语言/原生业务类型字节布局自动等于 GPU ABI。
- 验证动态数据更新与 binding 实例更新的区别；旧提交在飞时，按契约版本化或等待后覆盖。
- 仅在产品需要时加入 shader/管线热更新；布局改变必须与仅行为改变分开验证。
- wgpu-native 必须使用固定 C ABI 和实际二进制，不能以另一版本 Rust 示例通过替代；SDL 的 binding remap、bgfx shaderc 等记入资产链代价。

**停止条件**：必需数据语义无法保持，或适配者无法检测布局不兼容与旧绑定在飞覆盖。不同 shader 工具本身不是失败。

### V4：按需验证线程、调度与呈现

先保持等语义串行基线，再按已批准需求增加并行录制、独立提交线程或多队列。分别记录 CPU 准备、原生命令录制、GPU 队列行为，不把它们都叫“并行”。

若涉及窗口，覆盖 resize、最小化、恢复、停止 present 后的资源回收和退出。SDL GPU 必须遵守获取/使用/提交的线程契约及窗口线程的获取规则；bgfx 的 view/frame 调度不能被假装消失。

**停止条件**：合法线程安排无法表达实际任务关系；结果依赖非契约时序；不呈现时回收不能前进；普通更新只能依赖每次全设备 idle。若数据只证明某方案无收益，不将其写成普遍慢。

### V5：产品认可的故障终态

- 分开参数拒绝、准备失败、提交后不确定、超时、surface 变化与 device loss，核对 API 返回和诊断回调共同提供的证据。
- 验证 release 配置下是否仍能观察必须处理的故障；调试断言或日志存在不等于可交付的错误协议。
- 真正设备失效实验必须单独批准并隔离进程、有限退出、避免影响其他 GPU 使用者；不默认修改 TDR、提交故意挂死的 shader 或注入虚假 driver 成功结果。
- 允许诊断退出的产品与要求恢复的产品使用不同验收门槛；若要求恢复，还需 CPU/资产重建来源和旧设备世代隔离，不能只重建 device。

**停止条件**：不能区分完成与失效、停止新工作后仍无法说明存量持有责任、只可无限等待，或必须吞掉故障维持“成功”。

## 4. 统一结果模板

每条实验记录：

`实验问题 → 候选/固定版本 → 目标契约 → 环境与命令 → 观察结果 → PASS/FAIL/BLOCKED/UNSUPPORTED → 原因 → 能外推和不能外推的范围`。

性能仅在相同语义与正确性都通过后记录，并分离首次编译/加载、稳态CPU/GPU时间、内存与同步等待。不得把论文作者的数字、示例启动时间或 feature 列表作为本项目收益。

## 5. 进入落地的门槛

- 首个真实消费者及硬件/故障范围已确认。
- 至少完成会决定路线选择的真实实验，未把 blocked/unsupported 计作成功。
- 明确自有语义与复用机制分别由谁负责，没有重复而矛盾的状态/退休权威。
- 工具链、依赖、许可、生产构建和部署工件可重现。
- 公共 Interface、失败/失效规则与实际消费者相符，才实施完整最小增量；未被需求证明的图调度、多后端或高级资源体系不随研究清单自动开工。
