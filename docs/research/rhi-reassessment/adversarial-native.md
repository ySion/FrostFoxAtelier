# 自研低层 RHI／原生后端必要性与范围：独立对抗评估

## 评估边界与总判断

本评估已只读阅读 `research-brief.md`、`evaluation-framework.md` 及六份共同证据报告。以下事实引用来自这些报告中已保存的原文核验记录；本轮没有重新审计全部上游源码，没有修改文件，也没有运行配置、构建、测试、GPU 或性能命令。**接入可用性和性能优势目前均无项目实测。** 文中的实验都是后续待批准方案，不记为通过。

现有证据不足以支持“共享业务类型／需要可控性／工业引擎拥有 RHI，因此现在必须自研全部低层机制”。但它同样不足以支持“成熟库一定满足项目，所以禁止自研”。应竞争的是：**在同一个已确认消费者上，哪些不可替代的语义必须由项目拥有，哪些执行机制值得委托，哪里存在经验证而非假定的边界冲突。**

本报告中的严重性表示把有关主张用作选型依据时的决策风险，不是宣称发现了本项目运行故障。六项异议均为条件性挑战，没有加权总分或候选排名。

## 先公平陈述：自研何时真正有价值

自研路线的最强版本不是“把 D3D12 改成自己的函数名”，而是以下条件的组合：

1. **存在不可替代的、已确认的产品语义。** 例如必须保留的资源身份、绑定更新时序、外部 GPU 互操作或故障出口，在选定成熟候选的真实生产接口中不能合法表达；小适配仍不足，必须侵入候选内部的状态或寿命权威。这里列举的是可能的成立条件，不是为项目增补需求。
2. **绑定、内存或调度控制本身产生可验证收益。** 真实消费者暴露了特定瓶颈或预算冲突；候选的显式路径也无法消除它，而最小原生对照能够在相同正确性、在途上限和输出语义下改善。收益可以是必须能力、可解释的失败协议或维护边界，不必只有帧率。
3. **工作负载的差异足以抵偿重复实现。** 针对已确认的窄能力集合，自研能够删除成熟抽象中实质冲突的机制，而不是先承诺通用多后端、多队列、通用图和完整 Shader 系统，再把它们当作自研收益。
4. **团队明确接受长期维护责任。** 有持续维护上传、绑定、状态、并发、退休、故障和平台差异的能力与安排，而不只是能完成第一次绘制。具体维护投入和产品取舍需要用户决定，本报告不编造人力、周期或权重。

这些条件与 `native-baseline.md` 的“采用条件与反对条件”、`nvrhi.md` §10、`diligent.md` §8 一致。成立时应保留自研；尚未成立时，不应把“潜在自由度”直接转换为整个原生后端的实施承诺。

## 核心异议一：统一业务类型不等于必须自己持有所有原生机制

**被挑战主张：** 使用第三方低层资源对象会引入另一套业务世界；只有自研 RHI 才能保持自有语言与 C++ 的类型权威。

**主张的最强成立条件：** 实际接入确实要求复制实体、材质业务身份或语言类型注册，并持续双向同步；或者候选的对象、借用、回调和释放契约无法与已确认的语言运行时约束组合。若出现这种实质冲突，“只加一层 wrapper”不是充分答案。

**依据与反例：**

- `diligent.md` §7.1–7.2 明确区分共享业务对象、渲染数据、GPU 句柄／绑定投影和 Core 接口。已核对的创建入口接收描述与数据，未要求业务对象继承其场景类型；§4.1 所需的 deferred 提交前 GPU 引用集合也是命令寿命管理，不是第二套业务实体系统。[O1]
- `nvrhi.md` §3、§4.1、§10 允许外层业务句柄持有一个 NVRHI 强引用：业务句柄失效与底层 GPU 使用期结束可以是不同事件。两种事件不等于两个业务权威；真正危险的是又增加一套猜测 GPU 退休时间的适配层。
- `papers-and-talks.md` §3/S1 及 §4 指出参数布局由编译目标和特化决定。**CPU 业务类型统一不会自动消除 GPU 字节布局、绑定布局和版本投影；原生自研也必须解决这些边界。** Slang 论文的 `ParameterBlock<T>` 甚至不要求各平台采用相同底层表示。[O2]

**严重性与适用条件：高。** 如果它被当作不经接入验证就排除全部复用路线的首要理由，存在类别混淆；若真实语言 ABI／finalizer 约束尚未确认，目前只能记为未知。

**判断：否定“类型统一必然推出原生自研”；保留实际 FFI、借用和身份冲突；接入兼容性待实测。**

**最小真实实验及停止条件：** 从首个真实消费者中选一个实际共享类型和它确需的资源，经过项目语言桥／C++ 边界、候选生产接口、真实 Shader 读取及可核对输出完成一条路径。业务身份只保留一处；明确 GPU wrapper、数据布局、借用和提交持有。使用实际运行时释放机制，不以另一门语言的例子替代。若额外状态仅是原生路线同样需要的 GPU 投影及完成凭据，停止以“另一套业务世界”为由扩大自研；若必须复制业务身份或无法合法表达释放／借用，记录具体冲突，再比较解决该冲突所需的局部原生边界，而非直接建设完整 RHI。

## 核心异议二：“薄原生层”若省掉上传、绑定与寿命责任，就不是等语义替代品

**被挑战主张：** 项目只需要少量资源创建和 draw／dispatch 接口，自研会明显更小；成熟库的引用、上传和回收机制属于可省略重量。

**主张的最强成立条件：** 真实消费者的资源、更新和录制模式足够窄，项目确实能以较小且完整的专用实现满足所有已确认不变量；它不需要承诺候选库提供的其他机制。小范围自研并非必须复制整个成熟库。

**依据与反例：**

- `native-baseline.md`“已核对事实”说明 D3D12 command list 不替调用者保持所引用对象；allocator Reset 与 list Reset 的复用条件不同。RTV／DSV 非 shader-visible 槽位又可在录制消费后复用，不能把所有描述符统一成“延迟 N 帧释放”。这些不是换名字就能完成的责任。[O3]
- `nvrhi.md` §4.1–4.4、§6.2–6.3 已核对录制实例保活、提交实例退休、普通 binding set 传递引用、上传 chunk 版本和 volatile constants。它同时列出明确例外：descriptor table、外部 native owner、GPU instance 中的 BLAS 引用不自动获得相同保护；上传池高水位也不等于 GC 后立即归还。应问哪些已存在机制值得重复，而不是把它们计为没有价值的包装。[O4]
- `diligent.md` §4.1–4.4 则采用不同切分：应用必须保证 deferred 资源到执行前有效，之后库按队列和 fence 延迟释放原生对象；动态页受 `FinishFrame` 约束，mutable SRB 的覆盖仍需应用防止 GPU 在途访问。不能把它误说成全自动，也不能因需要提交前引用就断言它复制了业务世界。[O5]

**严重性与适用条件：高。** 只要真实消费者存在异步更新或在途工作，省略这些保证会让“小而快”的对照失去可比性。具体 bindless、缓存命令和多队列责任只有确认需要时才进入范围。

**判断：否定省略责任后的体量比较；保留真实窄场景的专用实现；两条路线的维护净收益待验证。**

**最小真实实验及停止条件：** 不先造通用资源系统，只在同一消费者的资源上完成连续更新、实际允许的多个在途提交、CPU owner 退出、一次未提交录制的取消／重录，以及完成后的输出读取与回收。动态绑定变化只加入消费者实际需要的那一种。分别记录业务失效、录制持有、提交、GPU 完成、引用退休和池内存保留，禁止按固定帧数或每次全局 idle 掩盖。NVRHI 使用普通 tracked 路径并显式驱动相应 GC；Diligent 保留契约要求的提交前引用并正确驱动 Flush／FinishFrame／回收。若可清楚委托这些机制且无需重复状态权威，停止为同一需求重写它们；若合法路径仍不能满足已确认的寿命或内存边界，才为该机制制作有限原生对照。违规丢弃必要引用不构成否决候选的证据。

## 核心异议三：拥有源码和原生调用权不等于已证明可控或高性能

**被挑战主张：** 自研天然更可控、更快；第三方的自动状态、引用计数或动态派发迟早会阻碍绑定和调度，因此应现在绕开。

**主张的最强成立条件：** 已确认消费者需要某种候选无法合法表达的调度／绑定／内存策略，或者有可靠测量证明候选的不可绕过机制超出产品预算；减少这项机制的原生实现保持相同语义并确有收益。

**依据与反例：**

- `nvrhi.md` §5 区分显式边界状态、`keepInitialState` 和 permanent state；§6.3 同时存在自动上传和显式 staging 路径。因此“使用它就失去所有状态／上传控制”不成立。但关闭自动 barrier 不等于取消 `keepInitialState` 的出口恢复，也不能把两种机制混成一个开关。[O4]
- `diligent.md` §4.3 提供手动状态路径，同时要求共享资源并行管理时明确 unknown 状态、实际 old／new state 和队列依赖。存在显式入口并不证明任意组合安全，但足以反驳“只能接受完整隐式调度”。[O5]
- `nvrhi.md` §7 已核对每提交线程／每队列 tracker 的公开接口，也列出同队列与原生 semaphore 组合的未核验边界。不能引用旧印象称其只能单线程提交，也不能反向承诺任意多 producer 安全。
- `portable-libraries.md` §3 的限制是真实而异质的：bgfx 的 view／frame 调度、SDL GPU 的录制／提交线程契约、wgpu 的安全状态模型不能被当作所有低层库的共同限制。某一应用级抽象不匹配，不推出必须自研全部后端。
- 六份报告均明确没有项目性能测量。函数数量、barrier 数量、间接调用存在与“本项目更慢”之间仍缺负载和关键路径证据。

**严重性与适用条件：高。** 若据此提前承诺多队列、并行录制、descriptor allocator 或 aliasing，可能把尚未存在的瓶颈写进正式架构。

**判断：否定未经测量的性能优越性；保留特定不可替代控制；原生／复用的效率差异待实测。**

**最小真实实验及停止条件：** 先在最匹配候选中表达真实消费者，只比较它提供的合法自动／显式策略。仅当明确识别出一个不可满足的控制点或实际瓶颈，再为该段写一次性原生对照片段，不建立可复用 RHI 框架。固定输出、Shader 语义、数据量、更新频率、在途上限、有效绑定和同步保证；正确性检查与性能采样分阶段，不能以删除某路线的必需安全语义制造优势。记录端到端延迟、CPU 关键路径、GPU 时间、内存高水位，并用分配、拷贝、锁和 barrier 记录解释原因。候选满足全部已确认硬约束时，对这些需求的“必须原生”已被反证；没有事先认可预算时只能报告观测值，不能宣称差异不可接受。只有可归因、可重复且超出已定门槛的损失，才支持扩大相应自研范围。

## 核心异议四：平台、故障和关停仍需自有，不代表底层机制也必须全部自有

**被挑战主张：** 即使用库，窗口、设备创建、呈现、错误处理和退出仍要自己做；因此复用收益有限，不如整套原生自研，故障也会更可控。

**主张的最强成立条件：** 产品确需的失败协议无法从候选错误入口可靠实现，或外部呈现／队列交接必须绕过其不可分割的状态和完成权威；为修补这些边界而维护的内部 fork 比局部原生机制更难解释。

**依据与反例：**

- `nvrhi.md` §8.1 明确 device／queue 由应用提供，swapchain 和 present 不由 NVRHI 创建；这是其交付边界，不抵消其保活、上传、绑定和提交实例管理。相反，`diligent.md` §5.2 的 swapchain 已包含提交、帧维护及回收动作。两者应按责任分配比较，而非把“第三方库”当同一包交付。[O4][O6]
- `nvrhi.md` §8.2 记录 D3D12／Vulkan 某些失败路径仍返回提交编号，故编号不是成功或设备健康证明。`diligent.md` §3、§9.4 记录 null／status／日志和部分等待边界，但没有完整恢复核验。结论应是需要验证项目错误协议，不能写成“库完全不支持设备丢失”。
- 原生路线也有明确陷阱：`native-baseline.md`“已核对事实”中 `GetCompletedValue()==UINT64_MAX` 表示 device removed，不能先按普通完成值判断成功。拥有原生 fence 不自动带来正确故障语义。[O7]
- `diligent.md` §4.2 区分 Flush、FinishFrame、context WaitForIdle 与 device IdleGPU；`nvrhi.md` §4.3 区分等待与 tracker GC。若停止 present 后没有推进必要维护，不能把人为遗漏当成复用必然泄漏。

**严重性与适用条件：高，但受产品故障策略限制。** “诊断后有限退出”与“原进程恢复资源和继续运行”是不同产品承诺；尚未选择前，不能擅自用透明恢复淘汰候选，也不能替自研承诺透明恢复。

**判断：保留平台与失败策略自有的理由；否定它自动推出全原生后端；关键错误出口和关停前进性待实测。**

**最小真实实验及停止条件：** 复用前面的真实消费者，观察创建失败的合法错误入口、正常结束、在途结束，以及不再呈现时仍能排空和回收的路径；只有实际需要窗口才加入 resize／最小化／恢复。记录谁停止新提交、谁观察失败、谁唤醒等待、哪些对象仍有合法持有者。真实设备失效另行批准，在隔离、有限退出的环境中验证；软件错误传播测试不等于真实 GPU loss 恢复，不通过挂死 GPU 或改 TDR 制造证据。若小平台／错误适配即可满足已选失败终态，停止因这项理由重写资源和绑定层；若所需故障不可观察或等待无法收敛，定位具体边界，再评估补丁、局部原生替代或候选否决。有限退出通过不构成恢复通过。

## 核心异议五：引擎和论文证明机制有用，不证明这些机制必须进入自研 RHI

**被挑战主张：** UE／Godot／Filament 都有自己的底层图形层，FrameGraph、Slang 和 GPU 调度研究也展示优势，所以项目应自研 RHI，并预置 graph、Shader 系统、多队列和 GPU 任务调度。

**主张的最强成立条件：** 项目具有与这些系统相近的已确认依赖规模、资产复用、内存压力或不规则 GPU 任务，而且需要的图编译结果、绑定布局或执行原语无法落到成熟候选。此时自有高层策略乃至部分低层原语可能合理。

**依据与反例：**

- `industrial-engines.md` §3–4：UE RDG 从 Shader 参数声明推导 pass 依赖，再录制 RHI 命令；Godot RDGraph 在设备层推导依赖，RDD 执行底层映射；Filament FrameGraph 的 pass／寿命组织与 Vulkan 后端的真实 layout／barrier 分开。三者本身就不是同一种 graph／RHI 划界。[O8][O9]
- 同报告 §4.2–4.3：Godot 所读标签 secondary command buffer 数为 0；Filament 所读 FrameGraph 路径是顺序 pass 执行，CommandStream 为单写者。它们不能为“必须从首版采用通用并行录制／专用 RHI 线程”背书。
- `papers-and-talks.md` §3/S1：Slang 研究参数块、布局与特化，实验还同时重构材质／光照组织；不能把结果归因于自研底层后端。§3/S2 的 Whippletree 研究 GPU kernel 内任务调度，不是 CPU command list 或 Vulkan／D3D queue 调度。[O2][O10]
- 同报告 §3/S3–S5、§5：显式 API 演讲说明应用责任，并不要求该应用亲自实现每项机制；Frostbite 只取得会议简介，不能补写其 allocator／同步算法；图内 first／last use 也不等于 GPU 完成或物理别名安全。

**严重性与适用条件：高。** 这会把渲染器、着色编译、图调度、GPU 算法和平台职责集中进一个尚无消费者验证的“RHI”，从参考实践越级成为需求。

**判断：否定跨层推导的必然性；保留 binding schema、明确访问和完成条件等不变量；是否需要 graph／并行／别名／GPU 任务系统待真实需求。**

**最小真实实验及停止条件：** 只取首个消费者实际存在的 pass／资源链，先用顺序显式依赖执行。若确有图管理需求，再用最小访问描述生成同一候选可执行的计划；不先复制 UE RDG 或 Godot 隐式图。若着色布局是疑点，单独验证真实布局与绑定复用；若 GPU 内任务才是疑点，单独验证真实 indirect／compute 原语。图或 Shader 策略在候选上可合法落地，即停止用该高层需求证明原生后端必要。只有查明必需的低层原语缺口，才把对应边界提交为自研理由；“想做自己的图”不算缺口。对于未确认的 temporal、别名和 GPU 内动态任务，不为实验自行添加。

## 核心异议六：候选的依赖与版本未知不能被转换成自研的确定收益

**被挑战主张：** 成熟库太重、版本难控、功能可能不够；原生 SDK 路线没有这些成本，所以长期更轻、更稳。

**主张的最强成立条件：** 锁定版本与最小工件后，候选确有不可裁剪的工具链、硬件、分发、升级或许可约束，违反了已经确认的产品条件；而等语义原生切片没有相同障碍，团队也接受取回维护责任。

**依据与反例：**

- `diligent.md` §6：Core 不要求采用完整 Engine／Samples；纯 D3D12 许多工具链可关闭。但本体仍有 ShaderTools、Python、fxc／SDK／ATL 等真实成本。GraphicsTools 被顶层加入、xxHash 参与配置，并不等于它们必然全部链接进最终产品。配置、构建、链接和分发闭包不能混算。[O11]
- `nvrhi.md` §9：后端、NVAPI、RTXMU、Aftermath 等有条件开关，可外部供给 headers 并关闭自动 fetch。它也不是只锁一个库 SHA 就消除全部依赖。应比较实际启用闭包，不以整个仓库或可选 SDK 的总量定性。[O12]
- `native-baseline.md`“当前 worktree 集成条件”说明原生路线仍受现有工具链和所选 Shader 编译产物约束；“SDK 原生”不证明完整绘制路径零新增依赖。
- `diligent.md` §2／§9 只核验了 v2.5.6，并未声称最新；`nvrhi.md` §11.4 记录 Guide 的 sparse 说法与同快照头文件／实现不一致，不能据旧说明判为不支持；`portable-libraries.md` §1／§6 也未完成 native C ABI 的固定发布组合核验。**未知应驱动缩小核验范围，而不是自动给自研加分。**

**严重性与适用条件：中；若确实触及硬件或分发硬约束则升为高。** 没有产品约束和真实工件清单时，不足以作路线淘汰依据。

**判断：保留实际依赖／维护障碍；否定零依赖和未知即不支持的比较；接入成本与长期维护优势待验证。**

**最小真实实验及停止条件：** 需求确认后，只选结构上最接近的一条成熟路线，锁定源码、headers、Shader 工具和 options，在独立目录构建前述消费者，记录所需源码、生成工具、实际链接库、运行时 DLL／分发工件及许可来源；不接入无关样例框架。必要的原生对照只构建同一消费者片段，不先建设完整后端。若最小闭包满足既定硬约束，停止以仓库体量或滚动文档不确定性淘汰它；若确有无法裁剪的冲突，则保留该路线否决证据。版本未固定、首次获取失败或缺少某个运行证据只意味着尚未完成验证，不意味着产品不支持。

## 建议的验证顺序：先证伪必要性，再扩大自研

以下是上述六项异议共享的验证切片，不是要求建立六套工程，更不是同时验证所有候选。

### 门槛 0：先确认能改变决策的产品输入

需要用户决定：

- 首个真实消费者及其可核对结果；目标硬件和必须能力，而非旧占位接口。
- 是否必须近期具有第二后端；是否确需多队列、特定录制／提交并发或长期缓存命令。
- 允许的窗口／平台接入边界；设备失效后要求诊断退出还是恢复继续运行。
- 自有语言与原生边界不可改变的语义，以及可接受的依赖、分发和长期维护投入。
- 如需以效率淘汰路线，先给出相关产品预算与测量口径；本报告不代填数值或权重。

消费者与关键语义未确定时，**停止架构胜负裁决**，但保留现有机制证据；不拿人工编造的重负载为自研制造必要性。

### 切片 A：一个消费者、一个最接近的成熟候选、一个窄边界

把类型／Shader 投影、真实执行、更新与退休、最小构建闭包放入同一个可核对切片。若消费者需要图形，包含其实际 Shader／绑定／纹理或几何路径；若它是计算消费者，使用其真实 dispatch 与输出。不要为研究齐全强加 copy→compute→graphics 或窗口。

**通过后能排除的主张：** 针对此切片已确认需求，“必须拥有原生实现才能保持类型权威／完成正确执行”不成立。它不证明全项目永远无需自研，也不证明另一候选更差。

**停止／转向条件：** 真实生产接口缺少必须语义、必须侵入内部权威或实际闭包违反硬约束。明确失败属于哪一层，再选局部替代或第二候选，不直接把问题扩写为整套 RHI。

### 切片 B：只为剩余争议增加一次性原生对照

仅针对已发现的布局、上传、绑定、提交、内存或故障边界制作原生片段；复用相同输入、输出 oracle 与所需安全保证。无需通用句柄体系、插件后端接口、通用图或完整分配器才能进行这项反证。

**支持自研的证据：** 最小原生片段能完成候选无法合法表达的必须语义；或同语义比较中，候选不可消除的机制确实违反已定预算，而原生片段满足它。

**反对扩大自研的证据：** 候选合法路径已满足约束；原生“优势”来自漏做持有／同步／错误处理；差异不在真实关键路径；或原生片段没有消除任何真实重复责任。此时停止扩大范围，不用已有原生样例倒推正式架构。

### 切片 C：产品需要时才补呈现、并发和真实故障

它们复用 A／B 的消费者，而不是默认都变成首版范围。真实设备失效实验需单独批准。不能用创建 device 成功、一次图像正确、软件注入错误传播成功，分别冒充接入闭环、长期寿命正确或真实设备恢复通过。

### 哪些只是实现细节，不应被伪装成用户需求

在既定语义下，某个 wrapper 保存哪一种拥有引用、NVRHI 自定义 tracker 如何驱动 GC、Diligent 提交前引用如何交还、Shader binding remap 如何生成、在哪个合法完成点复用上传存储等，首先是实现验证问题。不能把现有实现习惯升级为产品必须接口；反过来，若细节暴露出无法满足的语言借用、线程亲和或失败语义，才回到产品边界讨论。

## 结论

**条件性保留自研，但目前不支持把整套原生后端设为默认前提。** 最先值得拥有的是项目业务语义、可解释的 GPU 边界和产品失败策略；是否同时拥有所有低层实现，必须由等语义消费者、真实机制缺口与维护责任共同决定。

优先采用“成熟候选能否完成真实切片”的单侧反证：它若成立，就可以推翻该切片的自研必要性，不需要先造完整自研 RHI。它若不成立，再把原生实验限制在失败边界。成功的局部自研只授权已证明有价值的范围，不自动授权 graph、Shader 系统、多队列和所有后端一并自研。
