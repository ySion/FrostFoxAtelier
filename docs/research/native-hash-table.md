# 原生 Map / Set 哈希表的自研取舍

资料核对至 2026-11-22。研究对象是能动态增删、扩容、持有 C++ 资源并支持异构查询的字典。当前公共入口是 `atelier::Map` 和 `atelier::Set`，最初的对照后端为 ankerl v5.3.0，现已切换到 Foundation 自有索引。[退役对照与接入结果](small-table-experiment/retirement/README.md) · [基础库合同](../foundation.md#mapset-与哈希) · [依赖锁](../../cmake/dependencies-lock.json)

## 已经付出的成本与可替换的部分

ankerl v5.3.0 将实际条目紧密存放在数组中。默认索引的每组 88 字节含 16 个指纹、8 个溢出计数和 16 个 32 位值下标。查询先成组筛选指纹，再按值下标访问候选键。分类溢出计数为零可结束未命中查询。删除中间条目时，末条目填洞，还要找到该条目的索引槽并修正下标。紧凑值区同时让全表遍历只扫描活元素。项目的公开遍历器只持有一个条目指针，结构修改即失效；单键查询没有登记活跃遍历器的写入成本。[v5.3.0 设计与删除过程](https://github.com/martinus/unordered_dense/blob/v5.3.0/doc/design.md) · [Map 入口](../../modules/core/foundation/include/foundation/map.hpp)

有一个直接对应“维护还是重查”的实验。ankerl 作者给条目增加指回槽位的记录，消除了删除时的第二次查找。在其 Linux / clang 基准中，按字符串键删除快了 9%–11%，每次插入新增的写入抵消了收益，该方案最终被舍弃。这个数字描述作者的操作组合，项目的删插比、键长和缓存工作集会改变结果。[作者的发布记录](https://github.com/martinus/unordered_dense/releases/tag/v5.0.0)

## 可以分别验证的设计

| 设计 | 关键机制 | 在引擎里值得检验的代价 |
| --- | --- | --- |
| Abseil SwissTable | 每槽一个控制字节，保存状态和 7 位指纹；x86 成组筛选 16 个候选，完整相等性判定只用于指纹命中项。空槽允许结束搜索，删除标记要求继续探测。[Abseil 设计](https://abseil.io/about/design/swisstables) | 将键值直接放在槽内可以省掉 ankerl 的值下标读取。空闲槽仍占一整份键值空间，删除标记会影响后续未命中查询。 |
| Boost.Unordered FOA | 每组 15 个数据槽，对应 15 个指纹字节和一个溢出字节。一次 SIMD 比较筛选整组，按哈希类别查看溢出位即可判定能否结束未命中查询。[Boost 实现说明](https://www.boost.org/doc/libs/1_88_0/libs/unordered/doc/html/unordered/structures.html) | 适合验证槽内直接存值对点查的作用。连续删插后的探测组数和扩容成本，需要与新建表分别测量。 |
| Go 的小表表示 | Go 1.24 对一直容纳于单组的小表直接指向 8 槽组，省去目录与跨组探测。单组允许填满，删除也无须留下墓碑。[Go 1.24 源码](https://github.com/golang/go/blob/go1.24.0/src/internal/runtime/maps/map.go) | 若项目有大量短命小表，可以试验首组大小、首次分配字节和首次增长。大值使每个预留槽都更贵，把槽内嵌进表对象还会放大空表。 |

## 论文的结论与适用条件

- **Böther 等，PVLDB 2023。** 在四台服务器上比较向量线性探测、向量指纹与分桶比较。论文图 1 在 90% 负载下报告分桶比较相对其标量 Robin Hood 的查询吞吐提升，覆盖多种命中率和体系结构。实验使用固定容量，支持在相同键值和容量下比较候选过滤方式。相对已经执行 SIMD 分组过滤的 ankerl，还须单独量出载荷布局的收益。[论文 §1、§5](https://hpi.de/fileadmin/user_upload/fachgebiete/rabl/publications/2023/vectorized_hash_tables_vldb23.pdf) · [作者实验代码](https://github.com/hpides/vectorized-hash-tables)
- **Nicaud、Rotondo，2026-10 预印本。** 在均匀哈希、随机探测模型下，作者分析了桶宽、每组溢出位数与未命中多探测几组的关系。论文未建模删除或扩容，也明确区分实际二次探测和理论随机探测。因此可以用它选择要观察的指标，例如每次未命中访问几组；长期删插和耗时仍要在引擎里测。[论文 §1、§4–5](https://arxiv.org/html/2610.02385v1)
- **Tiny Pointer Hash Tables，PVLDB 2026。** 作者通过短指针和可还原的键编码压缩索引，分别评估偏空间、偏查询延迟的两种布局，支持删除和在线扩容。单核空间实验从 1,600 万元组容量起测，多线程实验包括 16 线程 YCSB。实现直接面向 64 位键值，对变长键值提出间接存储。这条路径适合特大整数索引有明确内存瓶颈时作对照；`String` 的拥有关系及 `StringView` 查询需要单独解决。[论文 §4、§8](https://arxiv.org/html/2607.28892v1)

跨库对照应统一哈希函数与相等判定，同时保留各自默认配置的结果。ankerl 作者在同机对照中发现，改变字符串哈希就能翻转两种索引的命中结果，容量翻倍前后也会出现明显的耗时锯齿。项目测量因而需要包含自然增长和预留容量，并把查询结果纳入真实消费路径。[作者的跨实现实验与测量条件](https://martin.ankerl.com/2026/09/09/hash-map-index-structures/)

## 本项目的两组 Release 对照

本机为 Ryzen 9 3950X，使用项目锁定的 clang-cl、Release 编译选项及 mimalloc。实验将 16 槽直接存值的原型与当前 Map 同场比较：每槽一个控制字节，7 位指纹，SSE2 同时比较 16 个标签，按三角数跨组探测。两端用相同的项目哈希和相等判定，按元素数预留容量。原型只实现本次负载需要的建表、插入和查找。耗时取九轮交错运行的中位数。[项目工具链](../../cmake/toolchain-lock.json) · [Hash/Equal](../../modules/core/foundation/include/foundation/hash.hpp)

**反射字段点查。** 用真实 Runtime 注册 World 和 Presentation，共 46 个类型。27 个非空字段表合计 143 个字段条目，其中 19 张表有 1–4 项。12 个非空方法表也都在 1–4 项区间，方法表只计数。字段查询按组内类型均匀抽样，命中与未命中各半；未命中名称来自目录中其他真实字段。每组固定随机顺序的 16,384 个请求，每轮回放 32 次，核对全部返回的 FieldId。这里测的是字段索引查询和核对的均摊时间，访问频率由实验指定。[字段索引构建与查找](../../modules/execution/runtime/src/runtime.cpp)

| 字段表规模 | ankerl Map | 16 槽直接存值 | 紧凑键值对顺序扫描 |
| --- | ---: | ---: | ---: |
| 1–4 项，19 张表 | 20.29 ns | 21.25 ns | **16.14 ns** |
| 5 项及以上，8 张表 | **20.77 ns** | 22.40 ns | 26.34 ns |

27 张表的键值与索引缓冲容量折合分别为 15,224 B、19,680 B 和 5,720 B，均不含表对象、字符串正文及分配器取整。这里每个键值对占 40 B，ankerl 的索引合计 9,504 B，正好是每表 352 B。若保留同一紧凑值区并仅省掉 19 张小表的索引，可少请求 6,688 B；这是按容量推算，尚未计入任何新增状态或切换路径。在 Runtime 直接扫描已有的较大 FieldInfo 记录也需要另外测量，本实验扫描的是紧凑键值对。

**网格焊点。** 同一份 `import_mesh` 函数体仅替换位置去重表，输入为真实 OBJ 导入后的 6,144 个顶点，生成 1,089 个唯一点。原型与公开入口逐项核对了点坐标和顶点到点的映射。每轮转换 128 次，计入表创建、焊点、几何与属性输出、销毁；文件读取与 OBJ 解析在计时外。ankerl 为 **153.41 µs**，直接存槽为 **148.10 µs**；九轮中后者七轮更快。这个样本给出约 3.5% 的转换耗时差异，只覆盖预留容量后反复插入或命中的一个网格。[焊点路径](../../modules/engine/procedural/src/operations.cpp) · [TerrainGrid 输入](../../examples/Content/Procedural/Meshes/TerrainGrid.obj)

## 候选方案与约束

本轮选定的候选保留 `Map/Set` 两个现有入口，验证**小表只有紧凑条目，增长后才建立索引**。这能直接检验首次索引分配成本，也允许 Set 延续公开的 `const T*` 遍历。条目继续只存一份，提升时一次建索引；需要测跨阈值的插入尖峰、较大表每次查找多出的分支和整个 Runtime 注册/查询时间。4 项只是本次分组边界，阈值取决于键比较成本和负载。直接存槽在网格样本的收益值得复核，但在字段表有相反结果，尚不足以成为全库默认。[Map](../../modules/core/foundation/include/foundation/map.hpp) · [Set](../../modules/core/foundation/include/foundation/set.hpp)

若继续验证完整自研后端，Map 和 Set 共享一套私有探测、删除及增长逻辑，各自保有值与键的访问规则。用 AssetBrowser 的拥有型 String / 借用 StringView、程序化求值器的删插与全表遍历，以及 World 身份键补足本次样本。把删除后的未命中、等价键和哈希碰撞、预留后增长、复制和自别名资源操作跑通；按调用链同时比较内存峰值、增长停顿、完整业务耗时。仅当这些对照支持替换时，才迁移产品后端。[异构键](../../modules/editor/application/src/editor/asset_browser.cpp) · [求值器](../../modules/engine/procedural/src/evaluator.cpp) · [World 索引](../../modules/engine/world/internal/world/detail.hpp)

**替换表后端和移除 ankerl 依赖是两个交付范围。** `hash.hpp` 的整数、字节串与复合身份哈希仍来自 ankerl；Renderer 还直接构造携带顶点数组指针的有状态 Hash/Equal，并用顶点异构查询去重后的下标。若目标包含移除依赖，需接通这个真实策略实例以及字节哈希，保留全部身份与相等规则。仅替换基础 Map 的存储无法完成这部分。[哈希策略](../../modules/core/foundation/include/foundation/hash.hpp) · [Renderer 顶点去重](../../modules/render/renderer/src/renderer.cpp)

## 72 B 候选的实验结果

首轮 72 B 候选未接入。该方案通过两个现有入口实现并测量同一套私有存储。小表顺序扫描紧凑条目，第一个超过阈值的不同键使 ankerl 接管原来的 vector 并建索引。重复键不触发升格，超阈值的 `reserve` 提前建索引。升格后删除和 clear 保留索引容量，release 恢复空小表。默认策略对象随条目转移，Set 继续借出只读连续元素。用阈值 2 和 4 分别编译了实际调用方。[首轮候选补丁](small-table-experiment/candidate.patch)

### Runtime 注册与实际查询入口

小表组在三种构建中统一指 1–4 项的表。字段与方法分别通过 `Runtime::find_field/find_method` 查询，成功时核对具体 ID，缺失时核对错误码，耗时包含 Runtime 构造错误结果的成本。每组从实际成员条目抽取 4,096 个请求并回放 20 次。“其他成员名”来自同一注册目录，并在计时前确认目标类型没有该成员。缺失样本的构成显著影响结果，表内不是编辑器请求频率。阈值 4 的方法命中有 17/18 轮更快，同长度末字节不同的字段、方法查询则各有 18/18 轮更慢。阈值 4 的注册时间在 11/18 轮更快，总存活字节持平；上一节按首组索引推算的节省没有转化成整个注册目录的净节省。[完整指标与配对差值](small-table-experiment/summary.csv)

这个抵消量可以由对象布局复算。每个 Runtime 类型内嵌字段表和方法表，编译器给出的 `sizeof(Runtime::Impl::Type)` 从 1,016 B 增至 1,032 B。锁定的 mimalloc 对这两种大小分别配 1,024 B 和 1,280 B 的块。46 个类型因跨档合计多用 11,776 B；外层 `Runtime::Impl` 从 632 B 增至 648 B，对应块从 640 B 增至 768 B，再多 128 B。两者合计 **11,904 B**，恰好抵消 31 个 352 B 索引按每块 384 B 计算的 **11,904 B**。阈值 2 只省 11 个块，按同一算式净增 7,680 B，与实测相符。[Runtime 存储](../../modules/execution/runtime/src/runtime.cpp)

## 64 B 小表的接入结果

## 自有大表索引与引擎特化

已实现并验收一套自有连续条目区与分组索引，沿用原有 Map/Set 入口和哈希。与当前四指纹后端对照，64K 打散整数 Map 点查快 6.62%，真实网格焊点快 1.84%，预留后的 64K 整数表少占 128 KiB。较大字段表的同长度缺失在 36/36 轮中变慢，配对中位数为 +7.46%。保留默认后端，自研候选和复测入口存放在研究目录。[设计、完整数据与复现方法](small-table-experiment/owned-index/README.md)
