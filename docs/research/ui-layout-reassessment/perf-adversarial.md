# 性能对抗评估：先固定工作，再比较成本

范围：四份候选报告与 `probe-plan.md`。本次只读报告，并经 Exa 复核其固定版本主源；未构建、测试或测量。**机制事实大体可靠，但仍有一处过强措辞及若干必须落实的公平性条件。以下不构成性能排名，也不要求浏览器全量一致。**

## 1. clean 根命中与 dirty 重算必须分开

**证据位置：**`yoga.md:53–55`、`taffy.md` §5、`probe-plan.md` §3。

**核实事实：**Yoga 完全 clean 且根缓存命中时跳过像素后处理；实际重算进入后处理后，scale=0 仍递归 children。Taffy 默认 rounding 即使根命中也遍历；`disable_rounding()` 确实去掉该遍历，`layout(node)` 直接读取未取整结果，不隐含全量导出。[Y1][Y2][T1][T2]

**风险与反论据：**不能把两者都简称“热缓存 O(N)”，也不能由失效传播 O(depth) 推出整次更新同阶。以上分支证明访问结构，不证明哪个实现更快。

**修正及待测反例：**同一棵树分别跑跳过调用、clean compute、固定盒内单叶更新、根宽变化；分记 solver、后处理及宿主读取节点数。统一逻辑坐标与最终像素政策，保留默认配置作另一组。若 clean 路径仍有全量成本，先定位消费层；若局部变更已经满足预算，也不能仅凭全树后处理淘汰 Yoga。

## 2. Clay 应比较工作量向量，而非节点数口号

**证据位置：**`clay.md:60–63` 及 §7 probe 1。

**核实事实：**固定 M 版有容量桶扫描；roots 排序每次执行作 `R(R−1)/2` 次比较；动态文字按内容散列。报告对此基本正确。[C]

**风险与反论据：**无 malloc 不等于低总成本；反过来，少量 overlay 的 HUD 也不因存在平方项就成为高成本负载。局部源码项不能拼成整条路径的紧确复杂度，更不能替代实测。

**修正及待测反例：**分别记录活跃 N、配置容量 C、roots R、文本字节 B、词数 W、命令数及布局执行次数。固定 N 改 C；再分别测试“多根短文本”与“少根长动态文本”，transition 单列。容量富余策略和内存一起公开；多 overlay 必须是各候选完成相同叠层任务，而不是只给 Clay 人造大量 roots。两组均可能推翻单一变量主导的判断。

## 3. “异步必须拥有快照”应改为寿命合同

**被质疑说法：**`clay.md:24` 称跨帧或异步渲染“必须建立拥有数据的快照”；`probe-plan.md:54` 已允许稳定存储与局部发布。

**事实与风险：**Clay 的 Begin 会复用临时 arena，浅拷贝命令不能延长外部文字及资源寿命。[C] 但这是存储复用约束，不证明必须逐帧深复制。

**反论据与修正：**同步消费后再 Begin，或让存储与资源保持有效且不可修改直到消费完成，原则上也能满足合同。应改为“必须保证整个消费期的数据有效性和同步；复制只是可选实现”。是否可用仍取决于真实消费模型，不能据此假定任意并发安全。

**待测反例：**同一内容流分别让消费者当帧完成、落后两帧，同时修改文字、删除节点。对各候选比较拥有快照、延迟复用等合法方案的复制字节、峰值内存、等待时间和旧结果正确性。不得让一个借用读取、另一个承担全量快照后直接排名。

## 4. solver 与 FFI 分项不能重复计费

**证据位置：**`probe-plan.md:60–62、89`；`taffy.md` §6。

**明确无误条件：**方案已提醒 inclusive/exclusive，且没有把 Rust 接入等同运行时慢；方向正确。

**剩余风险：**C++→Rust 布局调用包含 Rust→C++ 测量回调；把这两个完整调用时长再加到 solver 上仍会重复计数。一次批量提交也不代表整帧只跨边界一次。全量导出会掩盖根命中的收益，但那是 adapter 成本，不能反推求解器必然全遍历。[T1][T2]

**修正及待测反例：**端到端墙钟独立测；分项采用嵌套区间及互斥 self time，另报双向调用次数、输入/输出字节和输出消费量。用同一内容运行“测量缓存热的频繁回调”和“真实字体冷测量”两组；空回调只能诊断边界开销，不作为产品排名。若真实字体主导，不能把微小边界差异包装成选择依据。

## 5. 共享轨道的全局依赖不能罚给单一候选

**证据位置：**`native-alternatives.md` §7 P1 的“每帧手工扫描所有标签”；`yoga.md:41`；`probe-plan.md` P1/P4。

**成立条件：**该扫描确可反驳“subgrid 原生自然满足需求”，但不能升级成所有宿主组合方案的退出条件。报告原句应保持这一窄边界。

**反论据：**若列宽由全部逻辑行决定，离屏最长标签变化会影响可见行；单 Grid 也不能免除输入发现与依赖维护。专门容器或最大值索引可能比通用算法更合适，成本必须计入，而不是因其位于宿主就否决。

**修正及待测反例：**统一为例如 50k 逻辑行、约 100 个实例，并明确 overscan；分别执行增加及删除唯一最宽离屏标签、滚动和收窄窗口。并列记录逻辑项、实例、可见项、扫描/测量及变更数量。精确全数据列宽与渐进估计列宽分组；不能用裁剪全树对比真正窗口化，再归因于 solver。

## 6. 同一字体提供者不等于同一排版工作

**证据位置：**`probe-plan.md:79`；`clay.md` §3；`yoga.md` §3–4；`taffy.md` §4。

**事实与风险：**Clay 测词段并自行换行；Yoga/Taffy 的约束查询可要求提供者处理宽度相关尺寸。同一字体仍可能产生不同调用粒度和缓存覆盖；Clay 动态文本在缓存命中前仍可散列字节。[C] 少回调也可能只是遗漏失效，不能直接算优化。

**修正及待测反例：**分开标记求解缓存与文字提供者缓存的冷热状态；分别计调用数、实际 shaping 次数、处理字节，并以正确结果为计时前提。宽度在断行阈值两侧交替，输入无空格中文、长 URL，再保持字体 ID 不变更新字体版本；每步比较 warm 与 fresh 的行高、行边界及 baseline。若产品仅要求较窄文本语义，可据此限定共同路径，不能强迫全浏览器排版，也不能把少做工作计成胜利。

## 验证优先级

1. **先锁定可比合同：**文本与共享轨道语义、逻辑/实例规模、结果寿命及像素政策。
2. **再验证正确性与执行范围：**warm/fresh 差分、clean/dirty 分支、离屏最长标签、延迟消费；错误结果不进入性能排名。
3. **最后测成本：**发布配置下端到端与 solver-only、FFI/复制/分配、N/C/R/B/W 敏感性；原始样本和尾延迟共同呈现。

当前证据只能确定哪些条件值得测，不能给出本机性能赢家；最终选型保留到真实路径验证之后。
