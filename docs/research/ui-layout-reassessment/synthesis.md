# 布局引擎第一阶段结论与验证裁决

状态：**第一阶段调研与对抗的历史快照。** 当时没有运行新候选或冻结生产 Interface；后续真实运行、成本和反例统一见 [验证结果](validation-results.md)，不回改本页历史裁决制造预先知晓的结论。

## 1. 结论先行

**建议验证“可组合的布局协议 + 有边界的容器算法”，而不是现在押注一个包办所有控件的 solver。** 这是待验证的架构方向，不是提前决定自研一切，也不是先造三后端工厂。

用户要求的是高性能、较强表达灵活度、游戏 UI 与复杂编辑器控件，不是完整浏览器。旧 `row/column + fixed/intrinsic/fill_equal` 子集不足以直接充当新需求终点；但这也不意味着必须实现完整 CSS Grid/subgrid、任意约束图或浏览器样式系统。

真正需要同时成立的能力：

- 普通行列、流式换行与重复格；约束与自然尺寸、基线及宽度依赖高度。
- 共享尺寸的表单/表格、锚定与覆盖，以及可定义尺寸依赖的专门容器。
- 逻辑数据、实例节点与可见窗口分离；可变行高、content extent 和滚动锚点有明确拥有者。
- 失效不遗漏真实依赖，也不把所有变化都升级成全树测量；失败与结果寿命可验证。

这些是本轮场景提炼，不是未经用户确认的完整产品功能清单。具体语义以 [probe-plan.md](probe-plan.md) 的场景参数验证，不能凭“控件复杂”无限扩张范围。

工业依据见 [游戏 UI](industry-game-ui.md) 与 [编辑器 UI](industry-editor-ui.md)：成熟系统把测量/安排、共享轨道、集合视图、失效和渲染缓存分层；它们也仍有宽高反馈、离屏信息与变高虚拟化成本。借鉴这些协议，不移植一整套业务对象体系。

## 2. 下一阶段的三条主要候选路径

顺序是验证优先级，不是性能排名；三条路径均由同一套真实产品场景检验。

| 路径 | 为什么值得验证 | 第一反例 / 淘汰条件 |
|---|---|---|
| **Taffy + C++ 批量消费层** | 同一算法库提供 Flex/Grid/Block，低层 traits 保留自有存储的可能；适合先检验复杂编辑器表达 | 共享列＋变高文本＋虚拟化能否在统一尺寸依赖下工作；同步、测量往返、缓存失效和输出消费是否抵消收益 |
| **Yoga + 原生专门容器** | 原生接入直接，普通 flex、文本叶和 HUD 覆盖是有实据的基础；不必因没有 Grid 就淘汰完整组合 | 将表单/共享轨道作为真实补充机制，不让应用逐行修补；外部容器在 measure 被跳过时仍正确 arrange；饱和 min/max 的具体分配语义须验证 |
| **Clay + 宿主调度/测量适配** | 为即时声明的 HUD/菜单提供不同成本与所有权模型，不能仅因小众或即时式排除 | 文本断行与真实提供者是否完成同一工作；静态跳帧、重建、容量/浮动根与输出寿命计入成本；复杂表单需要的外部机制是否仍合理 |

第一轮 Taffy 先用 **Rust 拥有布局树、C++ 批量提交与消费** 的最短可维护路径。低层自有树不是已否决，但只有初测显示镜像/同步确实重要，才增加第二条适配对照；不以“零拷贝”口号提前建设逐字段跨语言接口。

自有表单、split 或虚拟视口算法属于真实容器需求的候选实现，不预设重写完整 Flex/Grid。若组合后复杂性和成本明显不合适，应允许选取更完整的方案或重开自研路径，而不是维护名义统一、实际不可用的包装层。

## 3. 其他实现的定位

- **Slate/UMG、UI Toolkit、Godot、Qt、ImGui、Flutter：**主要借鉴可定制容器、失效边界、共享轨道与集合视图协议；不因某产品采用某算法就宣布算法适合本项目。
- **LVGL：**保留显式轨道、最小尺寸/安排扩展机制的有界对照；当前框架对象路径并不等于可无成本抽取的独立 solver。
- **RmlUi 与 Slint：**若考虑由成熟 toolkit 拥有完整 UI 子树，让两者竞争一个系统级对照名额。完整系统须按其提供的文本、控件、视图与宿主集成价值评价，不能用裸 solver 的门槛永久排除。
- **Slint 旧排除已撤回：**当前固定源码已支持动态 Grid 和新的 C++ ListView 路径；旧版文档限制不得用于筛除当前版本。private solver、运行时/发行边界仍要按具体接法评估，许可结论不能代替发行方案审查。

版本修正及一手证据见 [原生候选附录 A](native-alternatives.md)。这一轮不再增加更多名字；优先把已识别的关键反例跑通。

## 4. 对抗意见与主裁决

完整原始反驳保存在 [性能评估](perf-adversarial.md) 与 [架构评估](architecture-adversarial.md)，以下是已接受的修正。

| 被质疑判断 | 裁决及落地位置 |
|---|---|
| 多棵树就是双权威 | **不成立。**允许业务树到布局树的单向、版本化投影；禁止的是同一状态多个独立写入者与不可控双向反馈。已修正验证退出条件 |
| 复杂编辑器必须一个全能 Grid solver | **不成立。**专门表单/轨道容器可满足共享列需求；组合算法必须真的实现，并计入其全部成本 |
| 跨帧消费必须全量深拷贝快照 | **过强。**核心要求是消费期有效性与同步；稳定存储、延迟复用、局部发布及拥有式快照可比较。已修正 Clay 报告 |
| dirty/cache 命中就代表端到端增量 | **不成立。**分开 clean、dirty、后处理、结果导出及文本缓存；已补入公平计时条件 |
| 同一个字体提供者就完成相同文字工作 | **不成立。**词段测量、自行换行与整段受约束排版不同；先验行边界/基线，再计回调、shaping 和字节 |
| 虚拟化让全局自然列宽免费 | **不成立。**精确全数据列宽与可见项估计分组；增删离屏最长项必须计索引或扫描成本 |
| 丢弃失败输出就完成恢复 | **不成立。**必须处理被写过的缓存、dirty 状态及身份映射；失败后与 fresh 对照，或明确实例不可继续使用 |
| 任意 measure/arrange 回调可以无限扩展 | **不成立。**先用固定外框与内容决定高度两类容器证明约束和尺寸依赖；明确循环拒绝/终止策略，不以“两遍”保证普遍收敛 |
| 旧版缺少某功能可永久排除库 | **不成立。**已补核 RmlUi/LVGL/Slint 当前可证版本；Slint 动态 Grid 旧排除撤回，文档与固定源码冲突显式保留 |

所有反例仍须真实运行；接受修正不是声称候选已经通过。

## 5. 下一阶段先跑什么

### 第一关：表达与安全

将以下三类组合输入作为首批否决实验，而不是先跑只含矩形的分配基准：

1. **共享列 Inspector＋本地化文本回流**：跨组包装、折叠、离屏最长标签增删、面板收窄；分别检验精确列宽与估计列宽政策。
2. **变高树表/列表＋字体/列宽更新**：可见窗口化、横向裁剪、滚动锚点与 extent；logical/instantiated/visible 分别计数。
3. **测量失败＋重入＋恢复＋延迟消费**：旧结果与身份映射保持一致，失败不得冒充成功，重试不复用污染缓存，合法存储寿命不强迫全量深复制。

### 第二关：成本与接入

只有共同语义正确后，才比较冷启动、静态跳过、clean compute、单叶变化、祖先 resize、结构更新和高变化帧。记录端到端墙钟及互斥分项、两向 FFI 调用/字节、分配与峰值、solver/字体缓存、布局和消费访问量。Clay 额外记录容量、roots、文字字节与词数；不把人工最坏输入只施加给一个候选。

固定 C++/Rust 版本、CRT、依赖源码、真实字体和参数；开发/发布都做正确性，性能主比较用发布配置。串行测量，避免其他席位负载干扰。**没有已确认的帧预算，本阶段不虚构毫秒门槛或节点上限。**

### 第三关：生产裁决

路径结果必须能回答：共享尺寸语义、custom 容器 seam、测量与失效、数据写入权威、失败恢复、结果寿命，以及 Rust/外部依赖的收益是否值得。然后再冻结小而完整的 Interface、依赖接入与验收范围。主项目 CMake/锁/全仓验收仍协调串行集成，不因研究需要顺手升级工具链。
