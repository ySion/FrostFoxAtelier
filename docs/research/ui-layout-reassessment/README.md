# 布局引擎重新评估

状态：**六席调研、两席独立对抗、三候选真实路径及自研首步探索均已完成；后续自研生产首增量已落地。** 当前使用入口见[布局模块](../../modules/ui-layout/README.md)，具体合同与17项双配置正式验收见[contract.md](../../modules/ui-layout/contract.md) / [acceptance.md](../../modules/ui-layout/acceptance.md)。本目录继续保存研究阶段证据；第三方路径和12项隔离实验不替代生产验收。

## 本轮授权与目标

用户明确：旧布局实现只是临时占位，不是必须兼容的权威；可以重新审视 Yoga 选型及旧布局合同。按「多席位 Exa 调研 → 对抗评估 → 真实路径验证 → 落地」分阶段推进。

已确认的产品目标：

- 主要面向游戏 UI，同时足以支撑编辑器复杂控件的表达。
- 具有较强布局灵活度，不要求完整浏览器兼容。
- 重视高性能；尚未给定节点规模、刷新率或毫秒预算，不自行把示例规模写成产品承诺。
- 搜索和外部文档研究统一使用 Exa，所有参与席位遵循相同要求。

旧布局选型、窄规则和合同只作为历史候选资料；`docs/modules/ui-layout/README.md` 与 `decisions.md` 现承接自研方向，其余旧候选文档明确保留为历史对照。旧探针 PASS 只证明其固定输入，不抵扣自研验收。共享 Runtime 的业务身份与生命周期不因布局自研而重定义。

## 共用问题与证据格式

每个席位必须回答：

- 实际是布局求解器、布局协议、控件框架还是完整 UI 系统？不能把完整框架能力全算给其布局核心。
- 支持哪些组合：约束/自然尺寸、伸缩、换行、网格或共享轨道、基线、锚定/覆盖、嵌套滚动、宽度依赖的文本高度？不假设所有机制必须在同一求解器内。
- 输入树、样式、缓存和输出由谁拥有？能否接入自有存储，代价是什么？
- 静态帧、局部内容变更、祖先宽度变更、结构编辑如何失效？复杂度必须说明成立条件。
- 文本测量约束、回调重复、字体/内容版本、失败与重入如何处理？
- 布局是否与绘制、输入、窗口、字体绑定？当前 Windows x64/C++23 接入需要什么工具链与 ABI？
- 分配、访问局部性、递归深度、栈与容量限制、线程模型如何？性能数据的负载和测量边界是什么？
- 版本、来源 commit/tag、许可、维护状态有哪些可核实证据？访问日期不等于发布日期。
- 最有力的支持理由和反对理由各是什么？哪一个具体输入足以推翻推荐？

报告统一标记：`事实`（一手来源）、`上游自报`（未在本机验证）、`推断`、`待验证`。外部事实附直接来源 URL；仓库源码尽量固定 commit 和具体符号。不能用搜索摘要替代关键源码或官方文档。

## 共同场景编号（验证候选，尚非冻结产品合同）

| 编号 | 真实场景 | 要暴露的问题 |
|---|---|---|
| S1 | 游戏 HUD：角落锚定、叠层、缩放与安全区 | 锚定/定位是否适合核心或上层组合；逻辑坐标与像素转换 |
| S2 | 物品格、技能条、自动换行标签 | 固定格与自适应轨道/换行是否可表达，不能仅凭“支持 flex”回答 |
| S3 | Inspector 属性面板：标签/编辑器对齐、展开折叠、错误提示 | 跨行共享列宽、自然尺寸与最小尺寸、多行文本重排 |
| S4 | 可拖动 splitter/docking 布局及浮动 popup | 外部交互改变约束；覆盖定位；不把 docking 交互归给求解器 |
| S5 | 大型层级树/表格/日志列表 | 逻辑项数与已实例化布局节点数分别计数；固定/可变行高虚拟化 |
| S6 | 本地化文本、图标+文字与混合字号 | 宽度影响高度、基线、内容/字体失效；shaping 属于真实测量提供者 |
| S7 | 嵌套滚动区域及内容变化 | viewport/content extent、裁剪归属、滚动是否必须重算全部几何 |
| S8 | 静态帧、叶更新、祖先 resize、结构增删 | 冷/热路径区分，访问节点、测量调用、分配和布局时间分别记录 |
| S9 | 失败与边界 | 非法/极端输入、过深树、测量失败、旧结果、生命周期和容量策略 |

性能验证若采用 1k/10k/50k 等数量，仅是实验分档；必须同时记录实际布局节点、逻辑数据项、可见项以及变更数量，不由实验档位推定产品上限。完整遍历复制结果也计入端到端成本，不只计 solver 内部时间。
