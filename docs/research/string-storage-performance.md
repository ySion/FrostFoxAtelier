# String 存储与性能取舍

> **现状对齐说明**：当前生产 `atelier::String` 已在本文 2026-09-30 基线（15 字节 SSO）之上演进为 **32 字节对象、8 字节对齐、30 字节短字符串内联存储（SSO）**，支持编译期静态字面量零拷贝借用，堆缓冲统一经 `mi_malloc/mi_realloc/mi_free_size` 原地扩容管理；现行权威契约见[基础库合同](../foundation.md#string-与-stringview)。下文保留工业标准库/引擎布局推导与早期 15 字节 SSO 对照采样依据。

## 早期 15 字节 SSO 基线（2026-09-30）

String 采用独占所有权、32 字节对象、15 字节短字符串内联存储（SSO），堆字符串按约 1.5 倍扩容，支持预留容量和赋值复用。有效 UTF-8、字节长度与索引、内嵌 NUL、结尾 NUL、深复制和移动后为空是共同合同；原生注册、Runtime 和源码沿同一 String 的生命周期操作接线。

布局为一个堆指针、一个 `size_t` 长度，以及容量与 16 字节内联缓冲的 union。Windows x64 下三部分占 8 + 8 + 16 字节。堆指针为空表示内联，访问数据时统一解析，不存指向自身缓冲的指针，也不用长度判别存储方式。`reserve` 或短值赋入已有堆缓冲后，长度可以很短而存储仍在堆上。这是项目自己的布局，并非标准库 ABI。

## STL：短字符串与固定体积

**官方事实。** 对照 Microsoft STL 的 `vs-2022-17.14` 版本：`_String_val` 有 16 字节缓冲/指针 union、长度、容量；`char` 的内联容量为 15，不包含终止符，以容量判断是否在堆上。在 64 位指针、默认空分配器和关闭迭代器调试的条件下可推导 32 字节对象；调试配置与分配器状态可能改变总大小。该版本的扩容取请求值经掩码上取整与旧容量加其一半的较大值，包含溢出检查；按长度赋值在容量足够时搬移数据并保留缓冲。[Microsoft STL 源码](https://github.com/microsoft/STL/blob/vs-2022-17.14/stl/inc/xstring)

LLVM libc++ 对照版本为 `llvmorg-20.1.8`。它将短、长表示放进 union，使用长短标记位、短长度位域、容量位域，并处理大小端及 alternate ABI layout；源码还解释了 packed 与平台位域大小的兼容问题。64 位普通指针、空默认分配器条件下可推导 24 字节对象，`char` 短表示有 23 个缓冲字节，最多存 22 字节文本。其普通增长路径接近容量翻倍。[libc++ 源码](https://github.com/llvm/llvm-project/blob/llvmorg-20.1.8/libcxx/include/string)

**项目判断。** clang-cl 工具链使用 MSVC STL；编译器名称不意味着采用 libc++。两者只是工业参照，不构成项目 String 的 ABI。32 字节比旧版 24 字节 Array 包装每个多 8 字节，即固定体积增加三分之一；大量长字符串或空值的连续数组可能因此增加占用。收益是新建或复制不超过 15 字节的字符串无需堆分配。阈值按 UTF-8 字节计算，不能等同于 15 个汉字。

24 字节无 SSO 保留更小的固定体积，但非空短文本仍依赖分配。24 字节带标记的布局可同时压缩体积和提高短容量，却增加位编码、容量限制、表示切换和布局验证责任。显式 32 字节布局解决短文本分配和重复扩容；是否值得压缩到 24 字节，要由真实对象数量与长度分布判断。

## Qt：共享复制与借用视图

**官方事实。** Qt 的隐式共享采用带引用计数的数据块；复制和赋值共享数据，修改共享数据前 detach 并深复制。[隐式共享](https://doc.qt.io/qt-6/implicit-sharing.html) Qt 使用原子引用计数，但它只保护计数完整性，同一实例的并发修改仍需同步。[线程与共享数据](https://doc.qt.io/qt-6/threads-modules.html#threads-and-implicitly-shared-classes)

`QString` 存 UTF-16 码元，`fromUtf8` 将输入转码，遇到非法序列可以替换或抑制；这与项目拒绝非法 UTF-8 的合同不同。`assign` 可以在未共享且容量足够时复用缓冲。[QString](https://doc.qt.io/qt-6/qstring.html) `QStringView` 借用 UTF-16 连续存储，不延长数据寿命，主要作为函数参数。[QStringView](https://doc.qt.io/qt-6/qstringview.html)

**项目判断。** COW 对频繁复制且少修改的负载可能有收益，但引入共享分配、原子计数与 detach，并改变物理独占机制。String 保持深复制，通过 StringView 传参避免本来就不需要的复制。视图的借用寿命与编码合同显式保留。

## Unreal：持有文本与临时构造

**官方事实。** Epic 明确说明 `FString` 保存自己的字符数组。[字符串类型](https://dev.epicgames.com/documentation/en-us/unreal-engine/string-handling-in-unreal-engine) `TStringBuilderBase` 用于函数局部的临时文本构造，初始缓冲由模板参数指定，超出时可以动态分配；构造结果可传入函数或交给 FString 长期保存。其连续缓冲不要求始终 NUL 结尾；`ToView` 在 builder 修改后失效，`Reset` 保留分配。[StringBuilder API](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Core/TStringBuilderBase)

**项目判断。** 临时 builder 与拥有型字符串承担不同职责。String 已有 SSO、reserve 和 append；独立 builder 要由日志、格式化等真实业务中的固定栈缓冲收益证明必要性，而不是新增另一套拥有型文本合同。

## 扩容、复制与校验

**实现取舍。** 构造与复制依据内容长度准备容量，不继承源对象额外的预留容量；增长采用 `max(required, capacity + capacity / 2)`，为末尾 NUL 另留一字节，并在加法与分配前检查上限。1.5 倍在重分配次数与闲置容量之间折中；几何增长的累计搬移为线性量级，这是算法推断。已知最终大小的拼接先 reserve；赋值容量足够时复用，普通清空保留容量，显式释放再回到内联表示，不因变短自动收缩。

复制有效 String 可直接复制已验证字节；从任意 StringView 写入仍要验证，因为按字节切片可能截断码点。append 只验证输入片段，无需重扫已有效的前缀。有效序列拼接保持有效，这来自 UTF-8 的编码规则；拒绝过长编码、代理项、越界码点及残缺序列，不扩展为归一化、排序或完整 Unicode 处理。[Unicode 17.0，第 3.9.3 节及表 3-7](https://www.unicode.org/versions/Unicode17.0.0/core-spec/chapter-3/)

校验任意输入的最坏成本仍为线性扫描；SSO 消除分配并不消除校验与复制。校验和新分配成功前保留旧值；自赋值、子视图赋值和自追加必须处理别名，复用缓冲采用重叠安全的搬移，新分配完成复制前不能释放旧缓冲。ASCII 按完整 8 字节块校验；残余及非 ASCII 仍逐序列验证，不越过视图边界。

## 验收与测量边界

当前 String 缓冲验收只保留一次拥有型目录清空前后活分配字节严格相等的序列，随 `foundation_acceptance` 执行；源码拥有值另经 `source_acceptance` 验证生命周期。独立的 String 性能采样入口已移除。下文是历史采样，不代表当前功能覆盖，也没有证明 32 字节方案快于所有备选。


## 2026-09-30 Release 测量

2026-09-30，Windows x64，AMD Ryzen 9 3950X，锁定 clang-cl/MSVC 工具链，共享 mimalloc。当时的消费者为 `string_measure.cpp`；当前 [foundation_acceptance](../../acceptance/foundation/main.cpp) 只检查缓冲释放与契约正确性，不复现下表测量。旧实现的源码与可执行文件先冻结，再在同一工作树顺序运行旧、新消费者；测量驱动源码完全相同。每项先预热 1,000 次，再做 7 组，每组 200,000 次（4 KiB 复制为 50,000 次），下表取组内每操作耗时的中位数。分配统计在计时区间外显式汇总。

| 操作 | 旧 String ns/op | 新 String ns/op | MSVC STL 同校验 ns/op | 旧→新分配次数/op |
| --- | ---: | ---: | ---: | ---: |
| 短名称构造（6–9 字节） | 21.01 | 8.81 | 6.56 | 1 → 0 |
| 短名称复制（9 字节） | 18.39 | 4.00 | 3.18 | 1 → 0 |
| 容量复用赋值（128/192 字节 ASCII） | 149.54 | 15.98 | 14.97 | 1 → 0 |
| 预留后拼接（203 字节 ASCII） | 182.29 | 40.49 | 29.11 | 0 → 0 |
| 已验证 String 追加（192 字节 ASCII） | 145.96 | 9.01 | 5.83 | 0 → 0 |
| 已验证 String 追加（320 字节 UTF-8） | 419.89 | 10.06 | 6.73 | 0 → 0 |
| 外部视图赋值（320 字节 UTF-8） | 429.22 | 306.44 | 306.40 | 1 → 0 |
| 4 KiB 复制 | 2519.16 | 49.64 | 50.50 | 1 → 1 |

MSVC STL 对照为拥有 std::string 的适配器：外部输入调用与当前 String 相同的 UTF-8 校验，复制及完整拥有文本追加沿各自已验证路径执行。它不是裸 std::string 与严格文本类型之间的不同语义比较。当前实现仍在若干小操作上比该对照多约 1–12 ns；4 KiB 复制和外部 UTF-8 校验在本次样本接近。相对旧 String 的大幅改善主要来自消除短字符串分配、重复校验和逐字符构造，而非证明全局优于 STL。

合成的 20,000 项名称目录包含 75% 短名称和 25% 192 字节路径。String 对象区从 480,000 增至 640,000 字节，字符串堆分配从 20,000 降到 5,000 次，保留堆字节从 1,360,000 降到 1,120,000。对象逻辑字节加保留堆字节为 1,840,000 → 1,760,000，下降 4.35%；这说明固定体积增加确实抵消了部分 SSO 收益。清空后两种实现的活分配字节变化均为 0。

对象区按 sizeof×项数计算，堆字节采用分配器统计；上述总和不包括容器额外分配粒度、分配器保留页或整个进程峰值。计时未固定核心或关闭频率调节，微小差异受普通桌面负载影响；名称分布是明确选择的样本，不能推成编辑器帧率或所有字符串负载的保证。
