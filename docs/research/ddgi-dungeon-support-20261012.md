# 多层地牢 DDGI 支持与昏暗归因 — 2026-10-12

状态：定向研究，已联网复核 NVIDIA 官方文档/源码与作者论文。原生 ReSTIR DI、显式方向光和 DDGI 线性历史已完成本批实现及 Dev/Release 完整 GPU 组合验收；2026-10-13 另观察已保存地牢的独立副本，条件和限制见下文。当前能力以[Scene Lit 模块文档](../modules/renderer/scene-lit.md)为准，真实结果见[验收记录](../modules/renderer/acceptance.md)，不把旧截图或单帧计数当新实现证据。

**判断：暗部要先拆成“没有可用支持”“有支持但尚未收敛”“有支持且测得低能量”。规则网格、多volume和滚动解决有限覆盖组织；它们不能保证每个薄墙、走廊和楼层都存在同一自由空间内的有效八邻支持。** 此判断包含下列工业事实与针对本项目的设计推断，尚不是当前地牢的最终归因。

## 1. 固定网格与少量volume的能力边界

| 路线 | 一手事实 | 对当前地牢的推断 |
|---|---|---|
| 固定规则网格 | SDK 明确说明规则采样无法稳健覆盖所有内容；墙厚应与探针密度匹配，过薄会漏光。其2–3m间距只是典型场景建议。[1] | 同一AABB含多层薄楼板、窄走廊及大量实体时，许多格点可能在墙内或隔壁；volume内不等于receiver有支持。不能把典型间距当地图通用值。 |
| 少量局部固定volume | 作者提供不同密度volume混合；更密层的实际作用仍由空间范围、插值及遮挡决定。[3，§7.4] | 可以把预算移到有需求的房间/楼层，但四槽数量和4096总池是本项目现行工程边界，并非DDGI理论常数；盲目扩大全局bounds会稀释密度。 |
| 滚动volume | SDK只复用内部探针、失效新进入的边缘平面；它保持有限active space，不同时照顾整个世界。[1] | 适合维持近处密度，无法替代当前视野外仍参与反弹的空间支持；新切片也需要预热。多层拉远视图可能同时需要多个互不相邻的区域。 |
| 更密的同一网格 | SDK也提醒过密网格有时更显格子结构，不把探针数量当单调画质指标。[1] | 需要增加的是正确位置的有效支持，而非单纯提高总数；低更新预算下更多探针还会拉长响应周期。 |

本项目使用严格probe-to-receiver LOS时，薄墙造成的错误邻居会被拒绝，可能呈现“无支持的暗面”；这比漏光更诚实，但需要布置解决，不能降低遮挡标准换亮度。SDK关于墙厚的内容假设不是要求修改现有美术几何的理由。

## 2. Visibility / relocation / classification 各负责什么

- **Visibility事实**：SDK用方向距离矩与Chebyshev权重近似遮挡；官方gather仍将该权重限制为至少0.05，并另防止权重归零。[2] 因而SDK视觉结果不能直接证明严格LOS版本同密度下必有支持；该下限不能照搬为项目的穿墙回退。
- **Visibility推断**：真实LOS只能判定已有probe与receiver间的连接，无法创建墙内缺失的probe，也无法提高缓存方向/空间分辨率；仅修最终receiver连接还不能撤销历史中已混入的错误反弹。反馈和receiver必须遵守各自已声明的遮挡合同。
- **Relocation事实**：SDK根据固定射线背面比例和邻近几何调整位置，移动被限制在格子内，最大约45%格距。[1] 它是局部位置修正，不会增加探针、改变格网拓扑或任意寻找房间。
- **Relocation推断**：当走廊完全落在两排格点之间，或同一格子跨多个楼层时，有限移动不保证每个自由空间都有采样点。球变为active也不保证附近墙面能看到它，更不证明方向观测已充足。
- **Classification事实**：SDK通过固定射线判断inside及附近是否有表面，以停掉无贡献probe的昂贵工作。[1] 作者强调，对静态表面提供支持的离屏probe仍需更新，因为它传播多次反弹。[3，§6.2–6.3]
- **Classification推断**：inactive裁剪主要节省更新；若槽位/atlas仍驻留，它不节省容量，也不能把4096自动变成更高密度。不能把“相机看不见”或“几何静止”当作永久冻结条件。

## 3. 最小有效演进：先把固定预算放到需要支持的空间

**以下为项目建议，不是SDK已提供的自动布置功能。** 作者的sleeping/唤醒与多密度volume提供机制依据，但没有替我们实现可达区域分析或稀疏砖块分配。[3]

1. **先观察支持失败的空间分布。** 按房间、楼层、走廊收集volume外、pending、inside、LOS全拒、仅一个贡献邻居的receiver比例；同时记录有效零照度，避免把物理暗部当覆盖故障。
2. **优先复用现有固定volume描述。** 由已知关卡/程序化房间bounds确定需要照明的自由空间，分别校准水平走廊宽度与楼层高度的格距，保留共同atlas、身份、gather和总更新计划。无需先做任意volume编辑器。
3. **依据附近表面和照明传播需要配置。** 既考虑玩家可达区，也包括墙面、楼板、门洞及照亮可见区的离屏区域；NavMesh只可作输入，不能代表全部光传输域。仅标记实体占用也不够，probe应落在可连接接收面的自由空间侧。
4. **先做配置与局部密度的A/B，再决定是否突破槽数。** 若少量区域已明显提高有效支持，保留小方案；若多数容量仍落在厚实体/无关空域，才考虑由同一描述与查询机制生成更多固定区域。
5. **稀疏砖块是容量浪费的后续解法。** 只为需要支持的空间分配规则局部格网，保留逻辑坐标到共享槽位的映射；跨brick八邻、缺邻原因、边缘支持、世界身份及失效必须一致。它不是把active位当稀疏分配，也不是立刻换成任意散点插值。
6. **预算仍按整个场管理。** 新区/失效优先，离屏有效支持保留轮转；照明响应按真实全局评估进度推进。SDK允许宿主低频更新，但不提供应用调度器。[1] 布置更多probe不能隐含提高每帧总预算。

固定区域与稀疏砖块的选择门槛应是“有效支持/驻留probe比例、可覆盖的实际接收面积、重叠gather成本、初始化与变化响应”，而不是方案名字。砖块若不能在同一入口内保持这些合同，就超出了本轮最小增量。

## 4. 昏暗不一定能用散布解决

| 原因 | 应观察的证据 | 哪种动作有针对性 |
|---|---|---|
| 没有有效空间/可见性支持 | coverage失败、LOS全拒、inside或方向观测缺失 | 调整区域/密度/位置或解决初始化；增加bounce/曝光不能补建支持。 |
| 有支持、更新和多跳传播尚未收敛 | 有效观测次数、全局轮转进度、静止期间HDR照度仍持续变化 | 给实际评估与传播时间，排查调度/历史失效；仅增加probe反而可能延迟收敛。 |
| 第一跳注入不足 | 灯范围/强度、发光材质与采样来源、命中直接辐射很低 | 核对光源单位与能量归属、光照范围和采样；不能靠复制探针产生能量。 |
| 采样方差经过非线性历史产生下偏 | 少数强方向光混入大量弱局部灯时，经常为零、偶尔高值；线性估计均值与历史输出不一致 | 显式方向光、局部重要性采样和保持照度均值的线性历史；不是仅增加probe或最终增益。 |
| 表面确实吸收多数光 | 支持稳定，直接照明存在，但低反射率路径的间接能量弱 | 这是可能合理的光传输结果，需结合美术目标决定材质/灯光；不能先判为GI故障。 |
| 跳数、反馈衰减或历史合同限制 | 单跳与允许反馈的收敛结果差异；每轮输入/输出能量 | 校核反馈反射率、衰减、重复注入/遗漏；probe数量无法修复错误能量合同。 |
| 显示映射使画面暗 | 原始线性HDR与最终曝光/色调映射差异 | 核对显示链；曝光调整不修覆盖、漏光或照明估计。 |

作者明确由probe ray hit着色查询上一轮探针场，迭代传播多次反弹；不是在一帧内精确计算无限跳。[3，§2.3] **工程推断**：在非负、耗散的漫反射系统中，高阶反弹来自已有光源能量和路径，不能救活完全没有注入的光场；更高反馈系数也不能代替缺失连接，并可能改变稳态能量与稳定性。

应保留“光源发出多少、表面反射多少、DDGI估计多少、Compose乘什么、显示如何映射”的责任链。尤其发光材质、mesh NEE、探针命中着色和feedback不得因追求亮度而重复算同一次注入；缺失哪一项必须从实际调用与测量确定。

**旧实现的代码推断与本批修复**：超过四盏解析灯时只均匀抽两个，再对照度做五次根历史混合及编码域正冲击限制；强太阳在大灯池中会产生高方差输入。非负照度的此类幂均值不大于线性算术均值，夹取又压低稀有高值，因此“线性采样原本无偏”不能保证缓存稳态能量正确。本批改为方向光逐次显式评估、统一局部源独立RIS、FP32线性目标/显示历史；屏幕另有ReSTIR时空复用。它修复采样/历史合同，不证明现场昏暗已全部解决，也不补建缺失空间支持，详见[实现说明](restir-di-implementation-20261012.md)。

**SSGI/Local GI推断**：可见屏幕上的局部信息可改善近场细节，但不能可靠恢复屏幕外光源、门后传播或从未获得支持的世界空间缓存；它也不能证明基础DDGI已正确。开启SSGI后“看起来亮了”只是一个对照结果，不能结束归因。

## 5. 当前实景证据与后续归因边界

2026-10-13 在本批 Release 编辑器打开已保存 Dungeons 的独立副本：3617 Actor，96 个有效解析源（95 点光、1 方向光），无天光。场景文件 SHA256 为 `0F6006559DFF61F5989AF82583CE500B8677518C206FA12833F9F3461177C029`。此保存版本保留屋顶；用户后来的内存场景具有不同对象状态，不能把两者视为同一现场。原文件没有被保存或改写。

恢复原来记录的布局：2048 个跟随探针（`16×8×16`，间距约 `3.2×2.857×3.2` 米）和 1728 个固定粗层探针（`12³`，约 `15.27×4.55×23.18` 米）；每帧更新 64 个，每次 32 条照明射线，反馈 .85、显示增益 2、曝光 0，Local GI/GTAO 关闭。普通 Lit/关闭 DDGI/status/探针球均成功捕获，未报告设备错误。

室内相机从 `(0,3,0)` 看向 `(-5,1.4,-5)`，每个对照在第 192 个接受帧捕获。墙面 ROI `(720,370)..(1080,540)` 的绿色非零贡献覆盖约 99.93%，但 DDGI 相对直接光仅增加 RGB8 均值 `(.5283,.3638,.0007)`；地板 ROI `(300,730)..(950,855)` 约 36.97% 为粉红色的候选全遮挡。颜色分类只描述这些接收区域，RGB8 差值只描述显示结果，不是原始 HDR 能量或全地图覆盖统计。

这份保存场景的有效太阳强度为 .2，多数点光强度为 1、范围为 5 米；本项目的对应单位是 lux、cd 和米。已观察到直接光和 GI 增量，但“有支持却低能量”和“局部没有可见支持”同时存在，因此下一步仍应分别核对作者灯光/传输和实际楼层布局。不能通过无条件加环境光、提高最终增益或降低遮挡要求宣布问题解决。

证据入口为 `out/restir-dungeon-compare.json`、`out/restir-dungeon-interior-compare.json` 与 `out/restir-dungeon-observations.json`。当前 Control 的 full inspection 在该场景超过 4 MiB，summary 正常；应用负责人确认尚无有界对象查询，因此已有灯句柄的精确临时编辑对照受此边界限制。新候选的固定场景统计与实际地牢归因分别记录，不把接口限制误记为渲染失败。

| 项目 | 当前记录 |
|---|---|
| 实例版本、场景、分辨率、实际 volume | 上述捕获保存了 Release 二进制哈希、1920×1260 客户区、约 1126×648 视口、每帧实际 bounds/counts/spacing 与槽顺序。 |

| 注入与显示 | 保存的灯光单位、环境、反馈和曝光已记录；实际材质反射率与逐跳 HDR 能量仍须专项归因。 |

只有现场证据表明缺口集中在格网不能表达的自由空间，才将自动区域/稀疏分配升级为实施目标；若有效支持充分且HDR能量低，先追光源与传输，不扩建布置系统。
