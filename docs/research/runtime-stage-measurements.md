## 实测结论

当前链路在这些有限场景中正确执行并回收资源；没有发现需立即修改生产实现的确定问题。GC 根槽历史高水位和最后版本同步退休已从推测变成可观察成本，后续可以据实际负载决定是否优化。

机器为 **AMD Ryzen 9 3950X，16 核/32 逻辑处理器，操作系统报告物理内存总量 63.948 GiB**；Clang 23.1.1、mimalloc 3.5.3，计时器频率 10 MHz。主代理在其他编译/验收结束后串行运行，未固定 CPU 亲和性。参数为 7 批、每批 20000 次同步调用、1/64/1024 个任务。

独立资源采样中的 20000 次纯标量 Entry 调用，分配次数、累计分配字节及活跃字节差值均为 **0**。对象调用本轮只测耗时，不能据此宣称所有对象或原生方法调用都没有分配。

### 挂起资源与清理

以下为 **1024 个任务**的独立采样。每个任务带一个 `uint` 参数。字节按分配器规格取整，且基线已持有代码、Runtime、热身容量和宿主拥有者 vector。

| 模型 | 创建分配次数/任务 | 到挂起累计分配次数/任务 | 挂起活跃字节 | 取消后仍活跃字节 | 释放外壳并 GC 后活跃字节差值 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 标量 | 6 | 6 | 1,251,952 | 114,688 | 0 |
| 原生对象 | 7 | 8 | 1,327,120 | 122,880 | 0 |
| 描述型对象 | 7 | 8 | 1,327,120 | 122,880 | 0 |

标量任务首次挂起没有增加分配；对象任务首次挂起多了实际对象存储。这里统计的是整个操作的实际分配次数，未进行逐调用栈归因。1 和 64 任务场景也分别得到 6→6、7→8 次/任务；不同规模的取整字节略有差异，不把单一规模的字节数视为稳定 ABI 大小。

挂起的对象场景有 1024 个活对象和 1024 个执行根。取消后根为 0，1024 个对象等待显式 GC；114,688 字节对应仍被宿主持有的 1024 个标量终态控制块，对象场景另保留 8,192 字节对象存储。释放外壳并完成 GC 后，**所有 9 个规模/模型组合**的活跃字节差值、根数和活对象数均回到 0。这个结果支持本轮场景的回收闭环，不替代长期保留测试。

1024 标量/对象任务挂起时的进程私有内存差值分别为 1,179,648 / 1,245,184 字节，和活跃块统计不同。1 个任务则可增加 65,536 字节进程私有内存，体现页粒度和已有容量的影响。所有组最后的进程私有内存差值也回到 0，但这些快照执行过强制分配器收集，不能据此声称正常运行时自动立刻返还同样数量的内存。

### GC 根高水位

每行都只有 **1 个活对象、1 个活根**。

| 已释放的历史额外根数 | 根阶段工作单元 | 完整周期工作单元 | 完整周期中位数 / 最大值 |
| --- | ---: | ---: | ---: |
| 0 | 2 | 6 | 0.1 / 0.2 μs |
| 64 | 66 | 70 | 0.3 / 0.4 μs |
| 1024 | 1026 | 1030 | 3.0 / 3.1 μs |

工作单元包含阶段转换，不能把数字直接称为活根数量。结果清楚显示：释放根后，后续扫描仍受历史槽位高水位影响。在本次 1024 额外槽位规模下，完整周期约 3 μs；暂未出现必须立即改造根表的证据。若后续真实工作负载产生更高或反复突增的根容量，可以沿用同一活对象控制场景测量。

## 复现入口

```powershell
. .\tools\enter-dev.ps1
cmake --preset release -DATELIER_BUILD_JIT_ACCEPTANCE=OFF
cmake --build --preset release --target atelier_source_measure
& .\out\release\atelier_source_measure.exe --batches 7 --calls 20000 --max-tasks 1024
```

`atelier_source_measure` 为 `EXCLUDE_FROM_ALL` 目标，不加入普通构建或端到端验收。程序拒绝 Debug 运行。参数上限用于限制专项运行规模；默认任务规模为 1、64、1024。

运行应与编译、其他验收和另一份测量串行进行。程序不固定 CPU 核，不修改调度优先级；配置记录包含 CPU 型号、逻辑处理器数、物理内存、计时器频率、编译器和 mimalloc 版本。锁定构建工具以 [toolchain-lock.json](../../cmake/toolchain-lock.json) 为准。

输出为 JSON Lines：

- `configuration`：本次机器与参数。
- `validation`、`warmup`：分配器统计自检及首次编译，不纳入稳态样本。
- `sample`、`summary`：每批原始耗时、批次中位数和最大值；单位为纳秒，并提供每次操作的均摊值。
- `resources`：各状态的分配次数、累计分配字节、仍活跃字节、分配器提交内存、进程私有内存和工作集差值。
- `gc_work`：相同活跃根数量下的历史高水位与实际工作单元。
- `complete`：所有场景与结果检查完成；缺少此记录时不能把整轮视为成功。

七批中的最大值只是**这七批的最大值**，没有足够样本把它称为 P99 或生产尾延迟。批量调用的均摊值也不是单次调用的延迟分布。

## 场景与验证边界

| 场景 | 计时范围 | 结果检查 |
| --- | --- | --- |
| 首次编译 | 首次 request、prepare、publish | `uint` 循环累计 0..31，结果为 496；单列 warmup |
| 稳态 prepare | 已建立声明后的候选编译、链接与准备 | 新旧版本均返回 496 |
| publish | 发布新候选，旧版本由 Lease 固定 | 当前入口及旧租约可用，避免把旧代码退休混入发布 |
| 最后旧 Lease 释放 | 最后一个旧版本拥有者的析构 | 动态展开条目消失，旧代码地址变为 `MEM_FREE` |
| Entry / Lease 同步调用 | 各 20000 次公共调用、结果解码与校验累计 | 纯 `uint` 循环；原生与描述型对象的字段递增和校验和 |
| 协程 | 创建、首次恢复到 yield、恢复完成、挂起后取消分别计时 | ready/suspended/completed/cancelled 状态、结果 42、清理后的根及对象数量 |
| 挂起资源 | 相对已热身基线，分别采样 ready、suspended、取消后保留外壳、外壳释放并完成 GC | 对象协程的持有引用经过完整 GC 仍有效；取消释放所有执行根 |
| GC 历史根高水位 | 一直只保留 1 个活对象、1 个活根；预先创建并释放 0/64/1024 个额外根 | 单步统计根阶段工作，再计时完整 GC；存活对象不变 |

对象调用仅访问一个 `uint` 字段；协程对象场景用源码 `new` 创建同一绑定类型，并跨 yield 保留该对象。没有用伪造的 callback、替代编译器或手工状态机代替正式链路。新旧代码退休通过公共 Lease 的诊断地址观察，不把该地址当作可调用入口。

同步调用包含公共结果解码、错误检查及校验和累加；协程状态和最终结果在相应计时结束后核对。所有场景先完成一次可核验的执行，首次 LLVM 初始化和首次代码编译单独记录。任务拥有者 vector 在计时和资源基线前 reserve；每个规模先热身并清理，以避免把首次 Runtime 根表扩容误当成每任务固定成本。

## 资源统计口径

使用工程现有共享 mimalloc，不更改生产分配器或增加分配钩子。程序先通过真实全局 `operator new(4096)`、`mi_usable_size`、统计增长及释放下降确认计数可用；自检失败则整轮退出。

锁定 mimalloc 3.5.3 将分配/释放计数暂存在页中。每次资源采样先在**计时区间之外**调用 `mi_collect(true)`，再调用 `mi_stats_get`，确保近期变化进入统计。这也会回收分配器的空页，因此资源结果是**强制收集后的快照**，不能描述成未干预的内存保留峰值。

- 分配次数：`malloc_normal_count.total + malloc_huge_count.total` 的差值。
- 累计分配字节：`malloc_normal.total + malloc_huge.total` 的差值，按分配器规格取整，包含随后已释放的块。
- 活跃字节：`malloc_normal.current + malloc_huge.current` 的差值，同样按规格取整；不是精确的用户请求字节。
- 分配器提交内存：`committed.current` 差值，包括页管理和保留成本。
- 进程私有内存：Windows `PROCESS_MEMORY_COUNTERS_EX::PrivateUsage` 差值，可能包含 JIT 虚拟内存及其他堆；不能等同于 mimalloc 活跃字节。
- 工作集：`WorkingSetSize` 差值，受驻留、缺页和操作系统回收影响。

任务资源采样基线已经持有 Runtime、Program、已发布代码、热身后的内部容量以及宿主 vector。各阶段差值不包含这些固定基座。取消只释放帧与根；尚未经过 Runtime GC 的对象仍可占用存储，仍被保留的 Coroutine 外壳也可能继续持有终态控制块。最后阶段同时释放外壳并完成 GC，和单纯取消阶段不能混为一谈。

## 解释限制

- 本轮是单机、同线程、短时微型工作负载基线，不覆盖持续热更、帧时间竞争、异步 I/O、跨线程调度或长时内存保留。
- 每任务均摊创建/恢复成本有助于定位下一步，但不能直接推出游戏帧预算或最大承载量。
- GC 高水位只改变历史外部根槽数量，保持活对象和活根一致；测量反映当前槽扫描机制，不把后续可能的压缩、分块或其他方案当作已验证优化。
- 计时不减去时钟开销；规模为 1 的纳秒级操作对计时器和调度噪声更敏感。
- 资源统计的强制收集和时间测量分开；两类数据回答不同问题。
- 本轮不根据单个样本引入对象池、退休线程或新根表。若数据暴露明显问题，再以相同场景复核后决定修改。
