# 第一步记录：工程基础与共享运行时的最小闭环

状态：已实现，开发与发布配置的端到端验收均已通过。日期：2026-09-20。

本文保留首阶段的目标、实施选择和验收证据。日常操作与当前能力以 README 为准，长期协作与工程规则由 AGENTS.md 及其引用文档维护。

## 目标

从统一的构建入口产出一个无窗口的验收程序，完成：

```text
显式注册类型 → 创建实例 → 发现并修改字段 → 调用方法 → 销毁实例
```

验收必须覆盖原生 C++ 类型与运行时按描述创建的类型。两者使用同一个类型注册入口、类型身份空间和对象操作接口；后者用于验证未来语言编译器的接入方向，不引入临时脚本语言。

本阶段完成意味着核心契约可执行，不代表语言、热重载或编辑器已经实现。

## 已确定的方向

- Windows x64；固定使用 Clang。
- CMake 描述工程，Ninja 执行构建，clang-cl 编译，lld-link 链接；使用微软 STL/CRT 与 Windows SDK。
- CMakePresets.json 是共享构建配置。开发与发布使用独立构建目录，不维护另一份 MSBuild 工程。
- 核心运行时共同服务引擎和语言，编译器未来直接发布这里的类型与函数。
- 原生类型显式注册，由模板从成员指针推导字段类型、函数签名与访问适配。
- 只做端到端验收，不增加单元测试框架。

## 本阶段的实现默认值

以下是本阶段采用的实现选择，用于收敛首版范围；后续随实际需求演进，不视为永久语言规范。

- 首版使用 C++23 标准模式，不依赖实验性反射或命名模块。语言版本演进与现代 C++ 写法遵循 [工程指南](engineering.md)。
- 单线程运行时上下文，显式初始化与销毁，不使用全局自动注册。
- 类型定义发布后不原地修改；本阶段在首次成功创建对象后关闭注册，不实现重载版本管理。
- 先支持示例真正需要的标量、值记录、有身份的对象和原生实现的方法。
- 对象由所属运行时显式管理，引用不自动延长生命。句柄只在所属运行时有效，槽位复用必须可识别过期句柄。
- 当前动态操作以句柄为入口，内部指针只在受控操作期间使用，不承诺裸指针可跨越迁移或重载。未来的直接执行路径遵循共享生命周期规则，不要求逐次经由动态操作入口。
- 首版回调期间禁止创建/销毁对象和注册类型，允许字段操作及同步方法调用，确保借用期间的实例与类型有效。
- 不提前确定 GC、语言继承、闭包与协程的完整语义。

## 工作顺序

### 1. 固定工具链，打通构建入口

实施时选定一个正式发布的 LLVM 工具链版本，记录 Clang、LLD、CMake、Ninja、MSVC 工具集和 Windows SDK 的实际版本。

配置时验证 Clang、Windows x64 和指定工具链，明确使用 lld-link；禁止静默退回其他编译器或链接器。工具位置允许本机配置，版本与编译策略由项目统一管理。

先提供 `dev` 和 `release` 两个 preset，启用编译数据库。编译选项、包含路径、依赖均按 target 声明。Windows 构建环境初始化如需要辅助脚本，只负责定位工具和准备环境，不保存第二套构建规则。

产出：核心静态库和验收可执行程序可以通过相同的 CMake 入口构建。暂不引入第三方包管理器、LLVM 库依赖或动态插件。

### 2. 实现最小类型与函数定义

核心运行时负责类型身份、字段描述、函数签名及实例生命周期操作。注册时发现名称冲突、无效字段描述和不支持的签名，给出明确错误。

稳定的声明名称与进程内类型标识分开：本阶段使用显式限定名称标识声明，不把内存地址、C++ RTTI 名称或注册顺序当作持久身份。重命名兼容与存档协议留给后续真实需求。

原生注册适配与直接构造的类型描述都提交给同一个注册流程。原生注册适配不能再维护自己的权威类型表。

元数据按类型共享。字段查找与参数检查服务动态操作；不要求未来编译后的每次字段访问都走名称查找。

### 3. 实现实例、字段访问和方法调用

对象管理负责创建、查找与销毁。原生实例正确调用构造与析构；按描述创建的实例由运行时计算布局并初始化字段。原生字段通过成员指针生成访问逻辑，不手写或猜测 C++ 成员偏移。

值记录可以内联存储，不要求每个值都有对象身份。首版只实现验收需要的布局与生命周期规则；不为任意 C++ 类型承诺二进制兼容。

动态操作验证对象有效性、字段类型和函数参数。内部可缓存已解析的成员；本阶段不构建通用 Variant 容器库，也不定义未来 JIT 的最终调用 ABI。

### 4. 用两种来源的类型完成端到端验收

验收程序通过原生适配注册 `NativeMachine`，通过直接类型描述注册 `DescribedMachine`。两者都包含浮点进度字段和一个接收浮点增量的方法；第二种类型的方法在本阶段仍由原生函数实现。

相同的消费代码仅取得类型标识，完成以下流程，不按类型来源分支：

1. 查询字段和方法信息。
2. 创建实例，将进度设为 `0.25`。
3. 调用推进方法，传入 `0.125`，读取结果 `0.375`。
4. 验证错误参数被拒绝，已有状态保持不变。
5. 销毁实例，验证后续访问失败；复用对象槽位后，旧句柄仍然无效。
6. 确认原生生命周期回调执行正确；关闭运行时，释放其拥有的剩余实例。

程序输出明确的逐项结果，成功返回 0，失败返回非 0。使用检查分支而非可能在发布构建中禁用的断言承载验收。

两种类型是用来证明同一条注册和执行链路，不是两个平行的对象系统。描述型示例代码只存在于验收程序内，未来编译器直接使用同一注册入口。

## 首阶段工程形状

```text
CMakeLists.txt
CMakePresets.json
cmake/                         工具链选择与目标编译策略
src/runtime/                   唯一核心运行时模块
acceptance/runtime/            无窗口端到端验收程序
docs/first-step.md             本计划
```

初期只需要 `atelier_runtime` 与 `atelier_runtime_acceptance` 两个构建目标。不按类拆库，不预建空的 Renderer、Editor、Network 或 Language 模块。

当前构建及验收命令统一维护在 [README](../README.md#构建与端到端验收)。`acceptance` 依赖并执行验收程序；开发与发布配置使用相同验收流程。

## 完成标准

- 从记录好的工具链环境出发，能够配置、构建并运行上述验收。
- 实际编译与链接使用指定的 clang-cl 和 lld-link。
- 原生来源与描述来源的类型走同一注册、对象访问和函数调用链路。
- 对象失效、错误参数、初始化及清理具有明确行为。
- 只有一份权威类型定义，不依赖一个原生 C++ 类来代表每个未来语言类型。
- 无编辑器、渲染、网络、存档、JIT 或热重载的空实现与占位框架。

## 后续衔接

本阶段通过后，再计划最小语言前端与首个 JIT 方法：直接产生已经验证的类型定义，并对同一个对象实例执行行为。届时以真实编译和执行需求确定调用 ABI 与安全点，再扩展到方法体热重载。

自有语言是后续业务开发的主要投入方向，逐步承载游戏行为、编辑器工具、UI 和程序化算法。原生 C++ 负责核心运行时、编译工具链以及需要原生接入或底层控制的能力。不要先用 C++ 铺满业务再整体迁移，也不要为了表达未来语言的业务模式而扩建庞大的 C++ 宏或模板框架。
