# 编程范式与性能指南

本指南承接根目录 AGENTS.md，记录工程默认值。当前能力和阶段限制以 README 与实现为准；举例不是强制选用某个容器、分配器或语言特性。

## 编程范式

以语义、所有权和生命周期组织模块，以实际访问模式选择数据布局。对象表达身份、职责与不变量；值、连续容器和批处理表达计算。两者共存，不用 OOP、DOD、ECS 等标签替代具体设计判断。

- 优先值语义、组合、明确的拥有者，以及生命周期内有效的借用。RAII 用于资源管理，不意味着每个值都要单独堆分配。
- 使用小而完整的接口隐藏真正的实现复杂度。一个模块可以有多个内部实现步骤，调用方不应重复负责它的不变量。
- 模板用于静态约束、类型推导与消除重复；运行时多态用于实际需要在运行时变化的行为。选择依据是语义、调用频率和总代价，不预设禁止虚函数或追求零间接调用。
- 对简单数据允许直接结构体和函数。封装应保护真实不变量，而不是机械地为每个字段制造 getter/setter。
- 并行计算要求明确任务读写范围、同步时机与生命周期；不从“线程安全”口号推导出全局加锁、全量原子或无锁容器框架。

## 源码布局与依赖

产品代码按 `modules/<职责域>/<模块>/` 归属，进程入口在 `apps/`。目录表达责任，不要求一个目录对应一个库。CMake 目标与依赖仍由根构建文件及 `cmake/` 定义；`acceptance/` 保留跨模块端到端消费者，`docs/modules/` 按阅读主题组织，构建工具在 `tools/`，不机械复制产品层级或创建空目录。

模块内按编译可见性放文件：

- `include/<逻辑前缀>/` 放公开头及其完整编译闭包。消费者使用 `foundation/array.hpp`、`runtime/runtime.hpp` 等逻辑路径，不带物理职责域。
- `include/<逻辑前缀>/detail/` 放公开模板、内联或成员布局必须可见的实现；它仍是公开编译闭包，不是独立承诺的调用入口。
- `src/` 放实现，`src/detail/` 放只在模块内使用的头及实现片段。产品不得跨模块包含别人的 `src/`。
- 确有跨目标共享实现或既有验收观察需求时，使用 `internal/<逻辑前缀>/`，只向实际使用目标 PRIVATE 开放。根可见不等于其中所有头都是受支持接口；新增使用者须明确其合同和理由。
- 着色器、生成模板随拥有者放置；生成输出仍在构建目录，不能用旧生成文件或转发头维持第二套源码布局。

每个目标只公开自己的 include 根及必要的传递头依赖；实现依赖为 PRIVATE，不添加全仓 include 根。头用法与二进制链接分开：纯头需求用 INTERFACE 目标或明确的头根表达，不能为找到头而把宿主 Runtime 实现链接进 LLVM 后端。

下表约束直接产品依赖，允许项是上限而非整层默认可见；同域依赖也须声明并保持单向。公开头的必要传递闭包照常传播，不由此授权上层直接使用更多业务模块。

| 使用者域 | 可依赖的项目代码 |
| --- | --- |
| core | 本域底层能力，不依赖其他域 |
| execution | core、本域纯协议与执行能力；contracts 不依赖 Runtime 实现，runtime 不依赖语言前端、JIT 或 Source 宿主 |
| engine | core、execution、本域较低层的数据与业务能力；不依赖 GUI、设备渲染或 Editor |
| gui | core、本域 protocol/layout/ui；ui_language 可依赖 execution |
| render | core、engine 的 geometry/rendering/material、RHI，以及 gui/ui_protocol；不直接依赖完整 UI、World、physics 或 procedural |
| editor | core、execution、engine、gui、render 与本域能力；core 不反向依赖 application |
| apps、tools、acceptance | 入口所需模块；产品库不依赖应用入口或验收实现 |

`rendering` 是 CPU 天空与光照数据，归 engine，不能与设备 `renderer` 混为一层。数学计算归 core/math，数学类型的原生注册归 Runtime。共享参数和诊断纯值归 execution/contracts；language 与 JIT 读取必要的类型头，但 LLVM 后端保持独立 CRT/分配域，不链接宿主 Runtime/Foundation 实现。Source 负责组装与发布。具体文件归属及受限 internal 准入以现有目标定义为准，不能为绕过方向规则复制同一权威类型。

## 现代 C++

- 当前使用 C++23，原生编译器永久锁定为 Windows x64 下的 Clang（`clang-cl` + MSVC STL），不兼容 `cl.exe` 或 GCC。C++26 的具体特性有明确收益且固定 Clang/标准库组合支持时，统一升级；不维护旧标准或其他编译器/架构的回退分支。在有明确语义、编译期诊断或性能收益时（如 `constexpr` 内建函数、`[[clang::lifetimebound]]`、`#pragma clang fp` 等），可直接使用经 Windows x64 MS-ABI 验证的 Clang 编译器扩展。
- 优先 concepts、受约束模板、constexpr/consteval、RAII、标准容器与视图。宏保留给普通语言机制无法合理表达的用途。
- `auto` 用于类型由上下文清楚表达的位置；数值宽度、单位、所有权和接口语义需要明确时写出类型。简单循环可以优于复杂的 ranges 或模板表达式。
- 沿用现有命名：类型用 `PascalCase`，函数、变量、命名空间和枚举值用 `snake_case`，私有数据成员使用尾部 `_`。局部风格调整不附带全仓格式化。
- 格式以 `.clang-format` 为准。它不处理的两条由 `atelier_style` 检查：每条声明只声明一个变量，`for`/`if`/`switch` 的初始化语句除外；函数体外相邻的声明之间空一行，包括类成员、成员函数、嵌套类型、`using` 以及命名空间内的函数和变量。枚举项与函数体内的语句不受空行约束。
- 注释解释不变量、生命周期、代价或非显然的取舍；避免复述语句。公共接口说明失效条件、错误、所有权和必要的性能特征。
- 错误分类、显式结果和终止边界统一遵循下文[错误处理](#错误处理)。`noexcept` 应由实际保证支撑，不能通过吞错获得。
- 立即返回原错误的纯转发使用 `foundation/result.hpp` 的 `ATELIER_TRY`；后续还需要命名 Result 时使用 `ATELIER_TRY_BIND`，保留 Result 变量及 `*x`/`x->` 用法。添加上下文、包装或换码、回滚、回退及返回非 Result 的分支继续手写；已有 `const auto`、显式类型声明和 if-init 中复制已有左值 Result 的站点也保留。clang-format 后宏调用超过三行或参数包含 lambda 体时保留手写。不得为了使用宏改变求值次数、求值顺序、作用域或资源寿命；仅允许在即将返回时将错误复制改为移动，左值表达式不得被宏移走。`ATELIER_TRY` 是单条语句；`ATELIER_TRY_BIND` 含声明及判错，放在条件或循环下时必须有显式块。
- STL、智能指针、`std::function`、ranges 等都按实际成本选用。对复制、类型擦除、捕获、分配和间接访问保持可见性，不凭名称断言快慢。

## 错误处理

**W0 冻结的目标合同，尚未完成代码迁移。** 本节替代按模块自由选择 C++ 异常的旧约定；基线中仍存在的 throw/catch 和异常验收不表示另有长期错误模式。W2 迁移底层，W4 迁移上层与验收，最后 W5 翻转编译开关。模块文档明确标为当前实现的异常行为，在对应迁移完成时更新，不在 W0 文档提交中假称已实现。

### 错误分类

| 类别 | dev | release |
| --- | --- | --- |
| 可恢复的输入、业务、IO、编译、协议、预算拒绝，以及 GPU/设备失败 | 通过所属模块的 `Result<T>` / `std::expected<T, Error>` 返回；调用方处理或继续传播 | 相同，不靠断言、异常或空成功值传错 |
| 已由调用合同保证、仅用于发现程序错误的内部前提 | assert 失败走唯一 fatal 出口 | 可编译掉检查；前提仍有效，断言表达式不承担副作用或输入验证 |
| 已检测到不能安全继续的不变量破坏，如损坏的所有权状态、无法完成必要的关闭 | 直接 fatal | 相同，不能编译掉或降格为可恢复错误 |
| 宿主 CPU 内存耗尽、线程创建失败 | fatal | fatal |

只在 dev 诊断的 Runtime 任务体禁入检查属于第二类；保留其[既有覆盖边界](runtime-model.md#并行任务体禁入诊断)，不因本轮迁移扩展为全入口防御或 World 检查。外部数据无效不能归为程序断言。业务容量上限、长度溢出及用户预算必须在执行前显式验证并返回错误；它们不是已经发生的宿主堆耗尽。GPU 显存、设备丢失和资源 API 错误沿原 Result 通道，不用一个含糊的 “out of memory” 文本把所有失败归成 CPU fatal。

上述长度验证针对业务输入；验证后容器内部仍出现不可表示的容量或大小乘加溢出，属于调用前置条件违例，在 dev/release 均经唯一 fatal 出口终止，不作为可恢复的容器错误。

### 唯一 fatal 出口

项目控制的终止路径统一调用一个由基础层提供的 `[[noreturn]]`、`noexcept` fatal 出口，不能各模块再造 stderr/abort/exit 变体。出口只接受静态诊断或已有有效的借用字节，以固定格式尽力输出最小诊断，然后执行 `__fastfail(FAST_FAIL_FATAL_APP_EXIT)`；不再调用 abort，避免回到信号处理器。不分配内存，不格式化拥有型字符串，不取业务锁，不进入日志系统、Runtime、用户回调或正常关停流程。诊断输出失败、递归调用或多个线程同时失败也不能阻止终止。fail-fast 接入系统 WER/调试通道，是否生成 dump 取决于系统配置，不是项目保证。它不承诺析构、join、保存文档、刷日志或回滚；这些保证只属于正常返回的成功、失败与取消路径。

每个自有 exe 在开始业务工作前调用同一个安装函数，以 `signal(SIGABRT, ...)` 将所在 CRT 域的 abort 接入上述出口。处理器仅以固定原因 `abort` 调用 fatal，不解包异常、不调用 `what()`、不构造 Error，也不返回。安装失败直接 fatal；安装函数同时关闭 `_WRITE_ABORT_MSG`，避免 debug CRT 在发出信号前弹窗。debug CRT 的断言和错误报告也通过报告钩子携带原消息进入唯一 fatal 出口，不弹窗；警告报告保持原行为。此后项目与依赖不得覆盖或忽略该信号处理器。静态初始化不承担可能失败的业务启动；已有清理失败、任务关闭失败及 dev fail-fast 诊断直接归并到 fatal。

锁定 UCRT 的 SIGABRT action 按 CRT 域全局共享，不按线程保存。安装完成且 action 有效时，同一域任意线程调用 abort 都可接入：包括 `_HAS_EXCEPTIONS=0` 的 `std::terminate`、TBB 的终止路径、JSON_NOEXCEPTION 的 abort，以及预编译 STL helper 抛错后无人处理而经 CRT terminate 到 abort 的路径。TBB 与宿主采用匹配的 `/MD(d)`：release 共享 UCRT，dev 共享 debug UCRT；它们不是两个独立的静态 CRT。无需逐线程 set_terminate；无异常 STL 的 `std::set_terminate` 本身是空实现，不能作为安装入口。

LLVM 后端采用 `/MT`，其 CRT 信号状态独立：在现有后端初始化路径、开始 LLVM 工作前，在该域单独安装一次同一 SIGABRT 处理，并用 `llvm::install_fatal_error_handler` 接入同一 fatal 实现。LLVM handler 只使用固定原因 `llvm fatal error` 和相同 fail-fast 原因码，不复制或格式化 LLVM 传来的动态原因。LLVM 的显式 `Error/Expected` 仍正常传播，不能因此把可恢复编译错误升级为 fatal。

以下只保证致命退出，不保证经过统一诊断：直接 `__fastfail`、STL/GS 安全检查的快速终止、栈溢出与访问违例、尚未安装处理器的其他 CRT 域或初始化早期，以及第三方直接调用 TerminateProcess/ExitProcess。UCRT 的 raise 在调用处理器前将 action 重置为 SIG_DFL，因此并发 abort 也可能先由另一线程默认终止；不承诺每个故障均有诊断或逐条输出。这些不是第二种可恢复错误模式，不为补齐诊断新建线程包装、异常岛或第三方补丁。

普通 `new`、容器分配及第三方 CPU 分配适配必须保证“获得合法存储或 fatal”，不能在普通 new 失败后返回 null 继续执行。共享 mimalloc 使用 C 模式，避免其 C++ 异常实现；接入者仍须分别核对普通、对齐及可空分配路径。可空分配 API 的 null 在项目分配适配边界转 fatal，不包装为业务 Result，也不靠内存耗尽后的 Error/String 分配来报告。第三方自身不可接管的内部 abort 不构成第二种可恢复错误通道；不宣称闭源或原样保留的二进制内部都经过本项目出口。

线程启动沿既有标准库和第三方接口，不新写 Win32 线程包装。删除 RHI 与图片解码中“部分 worker 启动失败后仍继续”的降级；启动失败终止整个进程，不返回部分工作集或串行成功。标准库或二进制依赖抛出的未处理异常只作为进入 terminate/fatal 的最后保险，不能用来实现可恢复业务流程，也不保证经过无 EH 帧时执行清理。

### 显式结果与清理

可失败的操作在类型上返回结果，错误由所属模块拥有；不把所有模块的 Error 合并成一个全局错误总线。普通错误文本可以分配，但这不提供 OOM 恢复能力。所有正常失败出口说明目标是否未改变、仍可销毁但部分改变、或尚未成为活值；调用方按该保证清理。去掉异常不等于去掉 RAII：正常 return 仍执行析构；必须把过去靠 catch/退栈触发的补偿移到显式结果分支或覆盖该分支的作用域清理。

仅可能因 CPU 分配失败的构造函数不必改成虚假的可恢复工厂；有业务、IO、设备或注册失败的构造改为 `Result<T>` 工厂，在成功前不发布半成品。若 T 不可移动，用已有稳定存储的初始化入口返回 `Result<void>`，由创建者清理失败部分，不为搬运 Result 改变对象地址合同。原生值回调的精确签名与失败目标状态只在 [NativeLayout 目标合同](runtime-model.md#原生值生命周期目标)定义。任务错误及 join 只在 [tasks 目标合同](foundation.md#任务失败目标合同)定义。

源码、原生调用和 JIT 间用状态加显式清理传错，C++ 异常及 `exception_ptr` 不作为跨帧或延迟传输协议；Result 也不按 C++ 布局穿过私有 DLL ABI。业务返回值和操作失败分离，见[原生调用目标](runtime-model.md#原生调用与-evaluate-目标)。

### 标准库、第三方与编译边界

自有目标最终统一 `/EHs-c-` 与 `_HAS_EXCEPTIONS=0`，不留下长期开异常的自有包装目标或异常兼容层。两者分别控制编译器与 MSVC STL 头文件，不能相互替代，也不会改写预编译库；同一链接模块内的头文件配置一致，配置在 PCH 和首次 include 前生效。使用 CMake 目标级配置，不把自有禁异常选项全局泄漏给保持上游构建的依赖。oneTBB 的获准例外及所需边界只在 [oneTBB 二进制边界](foundation.md#onetbb-二进制边界)定义。

第三方源码依赖确有必要时允许修改。改动必须有实际收益：消除异常岛、兼容层、消费侧绕行或重复逻辑，或者修正影响本项目的缺陷。方案须写明上游版本、改动范围及升级时的重放方式，不为非必要的诊断或个人偏好修改第三方。

小而局部的改动沿用现有机制：锁定上游版本，在 `third_party/<库>/atelier.patch` 维护可重放补丁，参见 [quill](../third_party/quill/atelier.patch)、[gfx](../third_party/gfx/atelier.patch)、[mimalloc](../third_party/mimalloc/atelier.patch)。改动较大或需要长期维护时，在项目组织下建立 fork，由 [dependencies-lock.json](../cmake/dependencies-lock.json) 锁定 fork 的提交和下载内容校验值。补丁和 fork 均照常复制许可证并遵守其要求。

LLVM、DXC、Agility 等预编译二进制若需修改，必须具备可修改的源码并自行构建替代产物，单独评估源码可得性、许可、构建和维护成本；消费侧编译开关不能改写既有二进制。

仍有可恢复失败的标准库调用改用显式错误入口，例如 filesystem 的 `error_code` 重载、整数解析的 `from_chars`；路径转换和其他隐含分配另按 CPU 分配合同处理。不得用 `stoi` 或必抛的越界访问承载输入验证。`_HAS_EXCEPTIONS=0` 不保证预编译 STL 的 `_Xlength_error`、`_Throw_Cpp_error` 等变成不抛异常，需避开可恢复路径上的这些调用；无法继续的二进制故障才交给 terminate。

JSON 的非法输入通过公开无异常解析/校验通道返回错误，保留大小、深度、重名键及 UTF-8 约束，不能把 parser abort 当作输入拒绝。LLVM 的 `Error/Expected` 保持显式传递而非再包装成 throw；保留现有 `/MT` 隔离 DLL、固定 ABI、创建方释放规则和 Windows unwind 元数据。WIC、DXC、gfx 及系统边界沿各自 HRESULT、状态或句柄；其公开错误不自动等于宿主堆耗尽。不要求未知第三方二进制内部没有 EH，只要求本项目不借其异常恢复业务或跨自有模块传错。

### 迁移验收

每片实现与全部受影响调用方、反射生成代码、夹具同批升级，删除被替代入口；已有资源清理、旧发布保留和调用结果哨兵的代表序列改为注入 Result 失败，不复制成一套异常/非异常双矩阵。acceptance 的 `require` 在 dev/release 都检查，失败报告并经唯一 fatal 出口非零退出，不能改成 release 消失的 assert。各片移除自己负责的 throw/try/catch/exception_ptr；最终没有自有异常路径后，最后一片才翻转所有自有目标的编译设置。

W0 只检查文档与链接，不构建。W2/W4 每片做双配置 `all` 构建，只运行受影响模块的无窗口验收；行为不变的迁移不做旧/新逐字节对照或临时故障注入探针。窗口验收只在改到界面或渲染时运行，只跑 release；真实输入法只在改到输入法链路时运行。集成后在最终树上跑一次门禁即可推送，作者冻结前不另跑同一组。复审只读 diff 与最终门禁结果，不重核作者的中间证据；汇报写结果、提交和待决事项。W5 做双配置 Full，并核实有效编译命令、分配/线程启动/第三方未处理异常的 fatal 接线。终止接线可用临时子进程探针验证，不新增常驻拒绝矩阵；没有执行证据前不声称开关或 terminate 路径已经验证。

## 核心容器与工程工具

引擎可以拥有精简的核心容器接口与契约。以常用操作的表达、诊断质量、存储控制和性能为收益依据；不要求完整兼容 STL，也不为统一命名给所有标准设施套一层。容量、初始化、删除方式、拥有关系和引用失效条件要明确。

底层可以直接采用成熟实现、局部修改或自行实现。选取完整且适合工作负载的设计，再迭代真实需求；保持上游来源和修改可追踪。`ankerl::unordered_dense` 是紧凑字典的候选基础，实际选型须考虑遍历、查询、删除及引用稳定性，不把某项基准排名当作通用结论。

当前继续使用 CMake 作为构建规则的权威来源，原生编译器使用 Clang，优先投入精简游戏 kit 的核心运行时，业务语言随实际需求推进。C# 保留为有明确收益时的工程工具选择，暂不安排构建系统迁移。未来若其他工具接管模块与依赖定义，应完成对应规则的生成或迁移，保持单一权威来源。当前实际入口以 README 为准。

## C++ 工具与输出约定

- 在已定位的模块内，优先通过 clangd 驱动的语义入口查询符号、引用和诊断；按文件或符号限定范围，需要实现细节时才读取函数体。语义服务使用对应构建配置生成的编译数据库，避免另行维护包含路径、宏和语言标准。

- 静态分析按具体问题和受影响文件调用。需要 clang-tidy 时，安装与工程兼容的版本，使用对应构建目录的编译数据库和选定检查项；不默认运行全部检查、全仓自动修复或附加风格整改。
- 提交前对改动的 C++ 文件运行 clang-format 与 `atelier_style`。后者按需构建：`cmake --build --preset dev --target atelier_style`，再执行 `out\dev\atelier_style.exe -p out\dev <文件...>`；`--fix` 补空行并拆分声明，`.inl` 经包含它的源文件检查。

- 接入验收使用本仓库的真实符号、跨文件引用和诊断查询，不以连接成功代替可用性。零诊断不替代实际编译与端到端验收，尤其注意模板和宏相关修改。
- Compiler Explorer 等外部工具只处理独立最小例子或已获授权的代码；微型实验结论不能替代本机 Windows 工具链、ABI 与完整工程验证。第三方仓库解读用于定位线索，关键结论回到源码或官方文档核对。
- 工具按任务启用，同类语义、检索和执行功能保留明确的主入口。手册记录调用条件与结果要求，不维护容易过期的完整 MCP 清单或临时连接状态。

## 所有权、布局与校验

- 对每份可变状态和资源确定生命周期负责人。借用指针、引用、span、string_view 的使用期限不能超过底层存储的有效期。
- 可变容量容器、对象迁移、重载、任务挂起及 GPU 异步使用会改变有效期；在对应模块明确失效或同步规则，不把裸地址长期散布到调用者。
- 稳定句柄不等于对象可移动。原生对象只有满足明确的重定位契约才能迁移；否则使用地址稳定的存储。不能仅凭“有句柄”就对对象执行 memcpy 压缩。
- 类型元数据按类型共享，值尽量按语义内联或批量存储。可反射不等于堆对象化，也不等于每次访问都做字符串查找。
- 在输入或新信任边界进行相应校验。状态、代际、权限等会变化的条件须在使用时保证；只有验证结果在借用/执行期间仍成立，内部路径才可复用它。不要把“校验一次”解释成长期信任可失效句柄或不可信客户端。
- 描述型与原生实现可以有不同存储和调用适配，但必须遵守同一类型定义、身份和生命周期契约。直接执行路径承担相同的语义责任。

## 高效成型与深度优化

成型阶段先解决完整行为，避免已知无意义的重复计算、复制、热循环分配和逐元素动态调度。把布局细节留在负责存储的模块内；这种可演进性不要求提前创建分配器工厂、通用池或备用实现。

区分已知热路径、可能的热路径、冷路径和未知路径。已知热路径应能说明每次操作的分配、复制、查找和同步；冷路径优先直接与可维护，不为统一指标付出复杂的所有权成本。

热路径上不用 `std::min`/`std::max` 的 initializer_list 形式，改写成嵌套的两参数调用。在 clang-cl 和 MSVC STL 下，initializer_list 形式会调用不能内联、带 CPU 分派的向量化 `max_element`，每次约 50 ns；两参数嵌套约 2 ns。阴影缓存规划中的一处包围盒距离测试曾因此每帧多耗约 14 ms。

| 真实场景 | 优先考虑的机制 | 需要判断的代价 |
|---|---|---|
| 生命周期混杂的通用数据 | 成熟通用分配器 | 分配/释放延迟、线程行为、占用与回收 |
| 同一任务结束即释放的临时数据 | arena 或批量回收 | 逃逸引用、析构责任、峰值与复用 |
| 大量同类数据遍历 | 连续数组、分块、合适的 AoS/SoA | 实际访问字段、更新模式、同步和搬移 |
| 稳定规格且高频创建销毁 | 对象池或按类型/尺寸分块 | 内存保留、碎片、并发与生命周期复杂度 |
| 树或图的高频遍历 | 索引、分块或扁平布局 | 遍历顺序、动态编辑成本和标识稳定性 |

mimalloc 是原生进程的默认通用分配器，统一在构建与链接处接入，普通代码继续使用默认分配函数和容器。系统专用内存、GPU 资源及第三方指定释放接口遵循各自契约；默认分配器不改变所有权。专项 arena 或池可以采用 mimalloc 作为底层分配来源，不要求每个元素独立分配。

每帧都可能重写的 GPU 缓冲（实例表、绘制索引表、光源表、UI 实例等）一律使用 [`FrameSlots<T>`](../modules/render/renderer/src/detail/frame_slots.hpp)：每个在途帧一份持久的 CPU 可写缓冲，按录制帧序号选槽，只在容量不足时按 2 的幂重建。不要每帧调用 `gfxCreateBuffer`。原因是 D3D12MA 对 32 KB 以下的缓冲优先走 committed 分配，带初始数据的默认堆缓冲还会再建一个同样大小的暂存缓冲；每次都是独立的 committed 资源加延迟回收。A1 的绘制索引表和 UI 合批在 maximized 下的实例缓冲都因此每帧多出约 1 ms 的 upload 与 recycle。绘制索引表、工作室实例和 UI 实例由 GPU 直接读帧槽。Scene Lit 的实例表、光源表和阴影批次表被直接光、DDGI 和阴影光栅大量反复读取，改用 [`DeviceTable<T>`](../modules/render/renderer/src/detail/frame_slots.hpp)：把帧槽当暂存，只在内容变化时把变化区间拷入常驻的默认堆缓冲。光源表直接读帧槽时，Dungeon 的 direct_visibility 和 direct_initial 各慢约 2%。

分配器升级使用正式版本并验证覆盖、对齐和生命周期行为；性能收益在真实负载中测量。它不代替访问局部性、分配次数和生命周期设计，批量释放堆内存也不自动履行 C++ 析构或外部资源释放责任。具体接入方式、覆盖范围和依赖版本位置见 README。

进行性能专项时：

1. 固定有代表性的场景、数据规模、构建配置和机器条件，先得到当前基线。
2. 定位主要成本，再决定算法、布局、分配、批处理、SIMD 或调度上的改动；不同时堆叠多个无法归因的优化。
3. 在相同正确性与安全语义下比较，记录吞吐或帧/tick 耗时分布，以及相关的分配、内存峰值和长期占用。涉及池和持久服务时同时观察内存保留与尾延迟。
4. 只有收益抵偿复杂度且端到端行为保持正确，才保留优化；结果不足时明确记录未证实，不把候选方案描述为已获得的性能。

已知能简化实现并减少工作的改动可以直接做，不为每个局部选择建立 benchmark。新增性能测量服务具体性能问题，不成为普通任务的固定仪式。

帧阶段的 CPU 耗时只通过[帧阶段计时](foundation.md#帧阶段计时)采集：模块在自己的代码中声明阶段标记，由宿主组装进同一目录；不新增私有计时器、计时字段或自持时钟的测量。截止时间、超时、时间片预算和呈现/显示时钟属于行为契约，不受此限，需要时可以把耗时作为阶段上报。逐调用或逐对象的计时（如源码诊断的调用计时）保持按需开启，不做成常开。

## 方案与复审标准（A/B/C/D）

本节是各线方案与冻结复审的唯一权威判据；报告引用本节，不另维护一套规则。代码膨胀按责任、逻辑链和真实可达状态判断，不按行数或当前调用次数判断。

- **A：逻辑链冗余，按 P2 退回。** 同一不变量在多层重复验证；没有独立责任的多跳透传、包装或类型转换往返；两条路径重复实现同一行为，或替代路径落地后旧入口仍残留。应在所属边界验证并复用仍然有效的前提，合并重复路径，同片删除被替代入口。
- **B：过度防御，按 P2 退回。** 当前合同和真实使用下不可达的状态防御，以及为假想调用方、平台、并发、规模或仅为测试、“以防万一”添加的分支、参数、配置、检查和计数器。判别时要求作者给出能到达分支的具体输入或状态，并沿调用链核实；没有依据则删除，确需表达内部前提或损坏状态时，按[错误分类](#错误分类)选择 assert 或 contract-fatal。已发生的故障不能当作假想；状态、代际、权限或信任边界变化后的必要校验不能按重复检查删除。复审只报 P0/P1 及上述 A–D 的 P2，不列措辞、证据格式类意见。
- **C：功能函数库与业务边界不属于膨胀。** 容器、字符串、数学、Unicode/数值转换等功能函数可以为将来预留，不要求已有消费者；前提是语义清楚、实现正确、有代表验收且不重复已有能力。新增抽象层仍须承担真实不变量、生命周期或行为，不能借函数库之名增加透传层。外部输入、业务容量和预算等真实可达失败的 Result 校验保留，不改为断言或 fatal。
- **D：基础设施缺口导致的绕路，按 P2 退回。** 为实现 B，在消费方集中堆 helper、多处各自实现同一种变通，或多跳转换凑出缺失能力，而在所属模块 A 补一项常用必备能力即可解决时，应在 A 补齐并删除消费方绕路。不是禁止消费方 helper，而是检查能力与责任是否放错位置。

方案阶段先明确功能由哪个模块负责、缺哪项基础能力、应补在哪里；没有缺口也应说明复用路径。归属或落地方式不清楚时不进入实施，不用消费方适配掩盖问题。

冻结报告写明基线与冻结身份、增删行数及净行数、增长理由、被替代旧路径的清理情况，以及本片以外的已知残留清单和负责人；没有残留则明确写无，不用本片通过宣称整条迁移完成。

UI 外观片（不限 Editor、Renderer）集成前，须把设计参考图（如有）及代表状态的改动前后截图放在 `.amp/in/artifacts/`，随冻结报告交付路径，由总负责人亲自使用 `view_media` 逐项比对，通过后才能集成。作者仍负责渲染、交互和适用的 DOM 检查；构建或代码检查不能替代视觉比对。

## 阶段选择的演进

当前单线程、回调期间禁止结构变化、标量种类、线性成员名称查询、每对象分配和动态调用签名都是首阶段实现选择。演进时维护已有消费者的明确契约，必要的语义改变先形成方案，再同时更新实现、调用方、验收和文档。

## 验收保留标准

只保留用于发现不会自行报错、抛异常或进入日志的错误，且属于以下类别的验收：

- **K1**：当前格式持久化往返的静默数据错误。
- **K2**：撤销与重做的正确性。
- **K3**：布局与数学计算结果。
- **K4**：每个渲染特性一张代表图，不展开组合矩阵。
- **K5**：JIT 与 ABI 正确性。
- **K6**：特定操作序列下的 UAF、泄漏、死锁或关闭顺序错误，包含故障注入后的清理序列，每种一份。故障本身已报错不替代对清理正确性的验证。

同一行为只保留一个最必要的代表用例，期望值必须来自独立真值。删除从被测实现输出反抄期望的用例、重复覆盖、放大规模和参数矩阵，不靠扩大样本或组合保留重复测试。

保留的测量入口仅为 `--profile-render-performance`、`--profile-ui-reload`、`--profile-scene-cpu`、`--profile-physics-cpu`、`--profile-procedural` 和 `--scene-lit-benchmark`。它们独立运行，不进入验收清单或 `-Full`，测量数值不作通过条件；其他 measure/profile 入口列为删除候选。

其余列为删除候选，包括已能报错、抛异常或进入日志的拒绝、错误文本、边界与防御矩阵，以及 CPU 验收在窗口中的重复检查。删除前提交逐项清单，审批后再改；无法判定的单列，不能把候选当作删除授权。窗口验收删除前须先有日志零错误的冒烟通过证据。只剩测试调用、没有产品消费者的观察接口，随对应测试删除后清理，不删除仍服务产品诊断的接口。以上是已裁定的保留规则，不表示现有用例及目标清单已完成清理。执行模式与命令只在 [README](../README.md#构建与端到端验收) 维护。
