# 引擎资源首增量：语言、UI 与 RHI 的连接方案

日期：2026-09-28。设计依据：三线共同代码基线 `4dc4c0a` 已集成正式语言宿主与 UI 布局基础，并通过 dev/release 总验收。资源首增量仍为未实现提案；已有模块总验收不代表第 7 节资源贯通验收完成，具体新增接口仍待共同接入任务确认。

当前优先级：先完成首个可操作编辑器的窗口、场景方块、文字与控件贯通；共同任务由应用负责人维护在 `docs/first-editor-plan.md`。本图片资源方案顺延，不作为该编辑器增量的前置。编辑器通过共同 CPU UI 帧交给 renderer，由同一 RHI 执行域绘制和呈现；这不代表已实现 Runtime Texture 业务类型或本方案的图片资源设施。

## 1. 本次要交付的可观察结果

宿主加载一张图片，建立共享 Runtime 中的 Texture 对象；自有语言把这个对象的真实持有引用共享给两个 UI 图片使用位置，并修改显示参数；UI 从同一内容版本取得尺寸、计算几何；渲染侧消费匹配的几何和设备表示，在现有离屏目标上产生可核对的像素。

更新图片、替换业务代码、清空业务引用或销毁对象后，仍能解释每个内容版本、布局结果、CPU 绘制任务和 GPU 使用的寿命。模块分别 PASS 不能替代这条共同执行链。

首例使用图片，暂不同时扩展 Mesh、字体排版、通用材质、窗口呈现、资源包、后台加载、显存流送或完整 renderer。几何和 GPU 结果通过真实离屏读回验收；文件来源与程序化 RGBA8 内容都经过相同的内容发布与消费路径。

本地依据：[Runtime 公开入口](../../../src/runtime/runtime.hpp)、[原生注册](../../../src/runtime/native.hpp)、[现行语言规范](../../../LANGUAGE.md)、[正式源码宿主](../../../src/source/program.hpp)、[布局入口](../../../src/ui_layout/layout.hpp)、[RHI 契约](../rhi/contract.md)。这些文件均已位于当前主线。

两个不能被笼统“语言绑定”掩盖的事实：

- 当前源码仍一次最多绑定一个业务对象类型，且尚无引用字段访问；`UiState` 持有 `Texture` 的场景已超出当前源码子集。负责人指出新提交的 `src/source/detail/bridge.cpp::bind_type` 仍跳过非 inline 字段，语言 `Environment` 仍只有一个 `object_type_name`。
- Runtime 的字段路径只遍历 inline 层。`UiState.texture.width` 必须读取类型化引用、检查并保持目标，再更换接收者访问；不能把它伪装成一个扁平字段路径。

### 原生资源载荷的初始化与访问

Texture 需要由宿主注入解码后的原生内容，并在生成 UI 消费数据时取得其内容版本。当前公开 `NativeLayout` 只提供无参数构造/析构等操作，`Runtime::call` 的参数仍是标量，未提供直接可用的任意载荷初始化接口。

Runtime 负责人确认需要补齐宿主用的同步类型化访问回调，候选名称为 `with_native<T>`，最终名称和函数形状尚未确定。访问前校验 Runtime/代际、活身份及准确 C++ representation，复用 `CallbackScope` 的借用保护与错误传播，区分 const 与明确可写访问；对象地址不得逃逸。沿用现有创建、销毁、GC、遍历与生成执行的重入规则，不扩大成“禁止一切嵌套调用”。

首例沿用默认空 Texture：在借用外准备完整不可变内容，在受保护访问中用不抛出的拥有权交换发布；成功前不把候选放入业务字段。捕获时复制独立的原生内容拥有者，例如 `shared_ptr<const ImageContent>`，结束借用后由 UI/RHI 使用。内容拥有者不能暗藏未登记的业务引用；任何 `ReferenceSlot` 修改仍经过 `Runtime::write_reference`。无需同时引入任意构造参数协议，也不在资源侧突破私有存储、放入全局临时指针或把地址编码为 `uint`。

引用参数/返回、字符串和泛型加载接口不是本首例的必要前置。宿主负责建立初始资源，源码通过类型化字段共享和使用它；未来源码主动发起加载时，再由实际调用形状驱动对应语言增量。

## 3. 建议采用的最小语义

以下是可审查的建议默认值，不代替其他模块负责人对其公共契约的确认。

| 项目 | 建议 |
| --- | --- |
| 业务身份 | Texture 是共享 Runtime 的普通对象，C++ 与自有语言共用定义、对象身份和引用规则；不新增脚本包装身份 |
| 内容 | 一份版本化、发布后不可变的原生图像内容，包括像素尺寸、像素格式和数据；它是内部存储，不要求独立 GC 对象身份 |
| 引用更新 | 业务引用默认观察该对象最近成功发布的内容；一次布局/绘制捕获固定内容版本，直到消费结束 |
| 初始状态 | 尚无内容的 Texture 明确不可消费；第一次加载失败不伪造成功内容或零尺寸 |
| CPU 保留 | 首例保留当前解码内容与仍被 CPU 消费者持有的旧版本；无使用者的旧内容释放。暂不做预算换出和自动重建 |
| 来源与共享 | 宿主维护来源记录和到活资源对象的弱观察；重复取得活对象可共享，缓存的存在本身不默认阻止 GC。来源路径不宣布为永久存档身份 |
| 线程 | 首例由同一个宿主线程驱动 Runtime、布局、资源发布与 RHI owner；文件解码在规定准备阶段同步完成，不引入后台任务协议 |
| 错误 | 内容准备失败保留旧内容；布局/绘制准备失败保留上一完整呈现结果及其原版本。RHI 执行域失败仍遵守既有终态，不能宣称旧资源可继续绘制 |

公开名称、函数形状和静态目标名在实现时沿项目习惯确定。这里先固定使用者必须知道的行为，避免通过类名提前固化尚无用例的抽象。

## 4. 模块职责与唯一拥有者

### 资源侧：内容和业务对象

本线负责来源解析/加载、内容准备与发布、Texture 类型和必要的 Runtime 适配。类型和业务引用走 Runtime；文件来源、版本及原生数据管理由资源设施完成。所有含业务引用的原生成员都必须进入现有字段/隐藏字段追踪。

CPU 资源能力应能在不创建设备的宿主中使用。渲染表示的实现依赖 RHI，资源的业务类型定义不因没有 GPU 就无法成立。是否拆成两个静态目标根据真实依赖确定，不预设多套 manager。

### Runtime/JIT 侧：可用的共同执行接口

该线已完成正式业务宿主入口及既有验收消费者迁移。后续最小范围由负责人确认是两项：引用字段/跨类型访问的编译执行，以及受保护原生载荷访问；资源首例直接使用现有 Program。

编译目录从 UiState 及其引用目标捕获已注册类型，为 AST、绑定与执行槽补齐目标类型；兼容代码发布同时核对 Texture 等实际成员目录依赖。保持空值/失效引用、求值顺序、错误清理、执行根和 GC 屏障语义。首例可以用 Texture 的 const 标量方法提供尺寸，不开放任意内容写入。

需要的最小业务关系为：UI 状态对象有两个 Texture 持有字段；源码能把其中一个字段的引用赋给另一个，读写允许的标量显示参数，并经 Texture 的实际成员取得信息。先以语义用例约束实现，不把本文伪造为新语法规范。

### UI 侧：内容绑定与一致消费

布局核心继续只拥有结构、测量缓存和几何。UI 内容绑定拥有者在业务阶段后捕获内容，将局部 key 映射到本次固定内容版本；布局 key 不直接替代 Runtime 身份或持有关系。

测量时只读取捕获的数据，不执行文件加载、资源发布或业务回调。图片像素尺寸转换为逻辑尺寸的政策属于 UI 消费方；确定宽度下如何保持宽高比也由这个具体图片测量实现负责。资源变化推进适用的 content/provider revision，不能只替换指针而继续使用旧缓存。固定尺寸、没有触发 Measure 的图片叶也要捕获内容和必要资源，测量回调是否发生不承担持有关系。

成功的布局结果与它实际测量的内容版本共同形成一次呈现输入。跨布局发布消费时拥有几何副本；它同时持有必要原生内容和设备表示，不能误以为 `LayoutSnapshot` 自动保活资源。

UI 负责人已确认愿负责图片绑定/测量 Adapter、逻辑尺寸和宽高比政策、revision 接线、完整呈现输入组装/失败保旧，以及跨模块验收中的 UI 部分；本线提供不可变内容捕获、设备表示和最小绘制接口。生产 composition 的模块位置与唯一拥有者由主持协调确认，不另建业务 Widget 树。

已合入的 TextFrame/VirtualInspector 消费者验证了几何 snapshot 与内容版本共同持有、旧帧在内容变化/布局失败/节点回收后仍有效、完整帧才替换。这是可复用的验收机制，尚无生产图片 composition。已交付的布局支持按需 first_baseline/可选基线，原有 key/revision、同步测量和几何借用契约保持；图片首例不依赖文本基线能力。

### RHI 侧：单一设备资源与执行机制

设备表示由明确的渲染拥有者管理，经 `Context::borrow()` 调用现有 gfx；帧推进和关停继续走 Context。设备表示按执行域与内容版本匹配；这只是上层关联关系，不复制 gfx 的 barrier、descriptor 或退休账。

当前 raw texture/buffer 不保持 Context 寿命。首例由渲染拥有者保证 Context 包住全部设备表示和 CPU 消费期；它停止新请求后，必须等未编码任务释放/结束，清理表示与 Pipeline，再调用 `Context::close()`。若还有上层消费持有，先返回明确未完成状态，不能提前关闭 Context。

## 5. 宿主中的完整执行顺序

1. **初始化**：批量注册业务与资源类型，建立资源设施、UI 绑定和 RHI owner，随后创建对象。类型注册封闭规则保持不变。
2. **业务执行**：通过正式 JIT 宿主入口运行真实源码，使用共享 Texture 引用、更新 UI 参数。沿现有执行根与错误清理机制返回。
3. **内容提交**：在无活动业务调用的规定阶段处理已准备内容；只发布完整候选。内容 revision 与代码版本分别记录。
4. **内容捕获与布局**：捕获相关业务状态和内容版本，调用同步测量并计算布局；此次计算期间输入不变。
5. **呈现准备**：取得或创建设备表示，安排上传，结合对应几何形成完整绘制输入。上传与读取在同一 queue 上正确排序，不为正常更新逐次 `finish()`。
6. **编码与提交**：尚未编码的数据/资源由上层保持；编码后由 gfx 负责实际 GPU 使用期，Context 统一推进帧。
7. **安全点与回收**：在许可阶段推进 GC；CPU 不再使用的表示在 owner 上发起释放，gfx 处理在飞退休。

内容发布、布局几何发布与完整呈现发布是三个明确事件。`compute` 成功只承诺几何 publication 已推进；随后绘制准备失败时，由 composition 持有上一完整呈现输入，不回退布局核心 publication。不能拿旧几何配新内容，也不能把旧呈现结果标成新 revision。这不声称渲染、碰撞等所有消费方存在全局原子切换。

业务对象被显式销毁后，后续访问按 Runtime 规则失败；已经捕获的呈现数据按自身持有关系结束使用，不能继续借业务裸指针。撤去最后一个根不等于立即析构或 GPU 完成。

**退出顺序**：停止新业务/加载/呈现请求 → 结束同步调用与未编码消费 → 释放 UI 绑定中的业务根和呈现持有 → 在资源设施仍有效时完成业务资源销毁/Runtime 退出 → 释放设备表示与 Pipeline → 排空并关闭 Context。代码租约及运行时之间也继续遵守 JIT 的现有寿命要求。

### 共同实施前需确定

1. 确定生产图片 composition 的目录、唯一拥有者和公共构建接线；按上述分工复用各模块，避免出现两个呈现入口。
2. 确认最小图片测量政策：固有像素尺寸到逻辑单位的换算、受限宽度下保持比例的规则、DPI 的消费位置。建议首例由明确的逻辑缩放输入提供尺寸，DPI 只在输出侧消费；实际影响度量的提供者变化才推进 provider revision。

这些是下一共同实施任务的接入决定，不重新打开已完成的工业选型，也不要求本节提前实现。

## 7. 端到端验收终点

| 场景 | 必须观察到的结果 |
| --- | --- |
| 真实语言共享 | 编译并执行真实业务源码；两个 UI 使用位置引用同一个 Runtime Texture 对象，来源共享不靠裸整数模拟 |
| 布局到像素 | 图片固有尺寸及宽高比得到预期逻辑几何；固定尺寸未测量叶也具有有效内容持有；正式绘制读取图片，GPU 回读与期望像素相符 |
| 更新成功 | 改变图片尺寸与内容后，缓存失效；新呈现输入中的几何、像素和内容 revision 对应 |
| 更新失败 | 坏内容不替换旧内容；测量或呈现准备失败保留上一完整呈现结果；几何成功但绘制准备失败不回退核心 publication，恢复后能继续发布 |
| CPU 消费与在飞使用 | 旧内容在尚未编码任务存活期间可用；替换/撤引用后旧已编码 GPU 工作仍正确完成；两种持有分别结束 |
| GC 与显式销毁 | 撤根后按 GC 规则回收；显式销毁后旧业务引用拒绝访问；捕获数据不复活对象，不留下永驻缓存根 |
| 来源与代码独立 | 程序化图像经过同一消费链；兼容业务代码更新不替换 Texture 身份或无故重建资源，失败代码更新不破坏旧业务入口 |
| 安全退出 | 未编码消费未结束时不能关闭其依赖的渲染域；结束后所有拥有者按规定顺序释放并有界关停 |

开发/发布构建中的检查均须有效。保留现有 Runtime/JIT、布局、RHI 验收；新增以上一条跨模块正式消费者，不建立 mock 或单元测试框架。本方案未执行上述验收，也未声称性能收益。
