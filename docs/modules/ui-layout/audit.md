# 布局阶段审计与优化

本轮按首次审计、官方资料核对、真实场景复现、修复和交叉二审推进。范围是原生布局核心和既有端到端消费者；没有扩展为编辑器、浏览器 CSS 引擎或新的业务对象树。

## 发现与处理

| 发现 | 复现或依据 | 处理 |
|---|---|---|
| 容器向外传播基线时使用孩子自然高度，漏掉最终位置偏移 | Fixed 高 column 内 Expand 子盒，以及居中文字、wrap 行内居中；旧版真实验收失败 | 复用实际容器排列，按孩子局部 y 加实际基线传播；未确定的依赖继续明确拒绝 |
| Grid 跨行自动项没有推进所有覆盖行的 sparse 游标 | 双方向放置；旧版真实验收失败 | 推进覆盖的全部副轴轨道，保持游标单调 |
| 大跨度自动项反复扫描同一阻挡区域 | 四节点、256×4096 自动占位区域，位于默认容量内 | 占位查询返回冲突格；沿当前移动轴跳到其后，保留原位表 |
| 折叠树退出遍历，却仍初始化所有活节点工作数组 | 保留 100,010 节点，只发布 9 个节点，反复改宽 | 按实际参与节点建立工作数组；发布索引只扩容和覆写参与项，查询仍核验完整身份 |
| 无饱和 Expand 仍建立和排序断点 | 2,048 个等权 Expand 项反复改宽 | 比例候选全部满足边界时直接分配，否则保留平衡权重和的断点求解 |
| 已确定高度的 Grid 提前计算无人消费的行轨道 | 自底向上阶段和最终排列输入重复 | 只在自然高度确有消费者时提前求行高，其余统一在排列阶段求解 |
| 确定高度的纵向 Flex 重复分配同一空间 | 高度阶段和排列阶段再次进入同一求解 | 每行只在分配空间改变时重新求解，缓存随本次计算的行计划销毁 |

旧二进制在新增复现后得到 36 PASS / 2 FAIL；失败分别是基线传播和 sparse 放置。失败日志保存在 [before-acceptance.log](../../../out/review/ui-layout-audit/before-acceptance.log)。

交叉二审又发现比例快路径的触界舍入问题：大权重项目计算值舍入到 max，可能吞掉小权重项目原本应获得的剩余量。真实行布局把该差异放大到约 0.5 逻辑单位并复现；最终仅严格位于边界内部的候选进入快路径，触及 min/max 时回到原断点求解。新增 `allocation_rounded_saturation` 已通过两配置。

## 核验和二次审计结果

**Dev/Release 各 39 项正式场景及最小消费者通过，两个正式目标退出码均为 0。** 新增数值触界、双方向 sparse、碰撞边界/容量保旧和折叠索引场景，并扩展原有真实基线验收。旧身份、缓存、失败回滚、文字资源保有、虚拟列表及深树场景继续执行。

Grid 作者交叉核对共享分配和基线修改；结构作者交叉核对 Grid 跳跃与索引。二审发现的数值问题已复现并关闭，未留下已知阻塞项。没有逐个核心分配点的失败注入、全进程内存分析或一般并发证明。

最终日志与源码、构建输入、二进制哈希：[dev](../../../out/review/ui-layout-audit/dev-acceptance.log)、[release](../../../out/review/ui-layout-audit/release-acceptance.log)、[environment.json](../../../out/review/ui-layout-audit/environment.json)。

## 同场景性能

保留修改前二进制，与最终 Release 二进制交错运行三轮，顺序为前/后、后/前、前/后。表中是三轮中位数的中位数及三轮 p95 的中位数，不是合并样本分位数。AMD Ryzen 9 3950X、项目锁定工具链、无窗口/GPU；真实文字显式使用 Microsoft YaHei UI。针对性场景各预热 4 次、采样 60 次，计时只含重排调用；创建节点不在计时内。

|---|---:|---:|---:|---:|
| 2,048 个 Expand 项改宽 | 186.0 | 147.3 | 230.7 | 222.3 |
| 四节点大跨度 Grid，行向自动放置 | 13,097.5 | 69.5 | 14,239.0 | 72.1 |

| 43 节点真实文字 Flex/Grid 改宽 | 60.7 | 60.3 | 89.2 | 101.1 |

针对性算法开销明显下降；真实文字复合场景中位数接近，滚动略增，不能宣称整套编辑器普遍提速。三轮样本只说明本机这些输入的观测，没有硬帧时限保证。四个针对性场景采样期间内部缓冲新增分配均为 0。

行向大跨度 Grid 内部缓冲峰值从 257,232 降至 216,272 字节，列向从 322,768 降至 306,384 字节。十万折叠树的整个文档峰值仍为 140,498,456 字节，节点描述的保留与创建峰值没有被折叠优化消除。43 节点复合场景仍为 64,064 字节；旧虚拟编辑器从 151,544 增至 152,364 字节（增加 820 字节），最多实例化 22 行及资源引用数量保持。统计口径仍排除 provider、拥有式快照和部分公开描述内存。

使用正式消费者的 `--audit-performance`、`--flex-grid-performance` 和 `--editor-performance` 复现。各轮原始数据在 `out/review/ui-layout-audit/{before,after}-{audit,flex-grid,editor}-{1,2,3}.jsonl`，摘要见 [performance-summary.json](../../../out/review/ui-layout-audit/performance-summary.json)。

## 研究核对

- [W3C 基线规则](https://www.w3.org/TR/css-align-3/#baseline-rules)：区分内容基线与盒边合成基线，不能把依赖最终高度的合成值提前固化。
- [W3C 自动放置](https://www.w3.org/TR/css-grid-1/#auto-placement-algo)与 [Taffy placement.rs](https://github.com/DioxusLabs/taffy/blob/main/src/compute/grid/placement.rs)：核对跨轨 sparse 前进及碰撞跳跃机制。这里保持项目自己的原生语义，不据此宣称 CSS 兼容。
- [Qt Grid](https://doc.qt.io/qt-6/qgridlayout.html)：隐藏控件退出布局；本实现的工作区成本仍由本地测量确认。
- [Yoga CalculateLayout.cpp](https://github.com/facebook/yoga/blob/main/yoga/algorithm/CalculateLayout.cpp)：已知尺寸与所需信息决定是否进入测量或完整求解；只作为条件短路的实现参考。
- [DirectWrite SetMaxWidth](https://learn.microsoft.com/en-us/windows/win32/api/dwrite/nf-dwrite-idwritetextlayout-setmaxwidth)：会修改排版对象。已有文字帧在共享资源更改前复制，旧帧持有对应版本的做法保持。

## 生命周期与执行链

编辑仍只改变描述和失效状态。计算准备本次工作区，先定宽、测量自然高度、分配和排列；全部成功后才在原提交点交换几何、查询索引和新测量缓存。提前为基线解析的排列也只写工作区。

发布索引可以保留未参与节点的旧序号，`LayoutView::find` 始终先检查范围，再核验 Document、slot、generation 的完整身份。双缓冲交换、失败后重试、折叠、删除与槽复用不能借此暴露旧节点。快照继续拥有几何和自身索引，内容资源由消费帧持有。

核心几何发布和完整呈现帧发布是两个事件。即使核心已成功计算，后续内容或绘制准备失败，composition 仍应持有上一完整帧；不能要求布局 publication 回退，也不能给旧几何换上新内容版本。固定尺寸、未发生测量的叶同样需要在呈现准备时捕获资源。

## 阶段边界

本轮完成后，原生布局基建这一节可以收尾：统一入口、明确依赖、失败保旧、内容消费寿命以及选定 Flex/Grid 能力均已有真实端到端证据。与 Runtime/JIT/RHI 的共同贯通属于后续协调阶段。

Grid 自动放置的代价仍受区域形状和跨度影响；跳跃消除已定位的重复扫描，不提供所有输入线性复杂度保证。折叠保留描述内存，展开后的工作缓冲保留高水位，拥有式快照还会复制发布索引。大型列表继续使用 VirtualList。

一般几何变化仍计算参与布局的实例树，没有通用局部调度、异步布局、完整绘制或输入系统。未开放的循环尺寸、Grid 基线组和 CSS 特性维持明确边界。下一阶段由真实 UI composition、资源和业务语言接线驱动，不以继续补浏览器特性作为本节完成条件。
