# 布局核心决策：自研垂直域库

**当前决策：用户已选择自行实现布局引擎库。** 面向本引擎的游戏 UI 与编辑器需求，参考 Godot 等工业项目的机制，不导入无关的框架责任。Yoga/Taffy/Clay 保留为研究证据与比较基线，不作为当前生产后端候选。

这确认的是自研方向与分增量实施方式。S01–S08 描述整体演进；**用户已授权并落地生产首增量**，当前行为与具体 Interface 以 [contract.md](contract.md) 和生产头文件为准，实际运行证据以 [acceptance.md](acceptance.md) 为准。共享轨道、换行与局部增量调度仍在后续阶段，不因首增量完成而视为已实现。页尾 D01–D08 保留历史。

## 已确定的范围

- 自研核心尺寸语义、容器算法、依赖失效和结果发布；不是给第三方 solver 再套一层，也不造三后端工厂。
- 主要服务游戏 UI，实际覆盖 HUD、物品格和复杂 Inspector；可扩展容器，而非完整浏览器兼容。
- 自研不等于重写成熟基础设施：继续使用项目的 C++、CMake 和分配器；文字排版、字体、图像与渲染不由布局库重新实现。
- 业务类型/对象/根仍服从共享 Runtime；布局资源身份不是第二套业务对象世界。

## S01：小内核，具体容器拥有具体布局规则

建议一个布局拥有者集中管理输入、局部资源身份、结构校验、工作队列、缓存和发布；容器算法只负责子项尺寸查询、空间分配与摆放。调用者不应手工修补 dirty 或在各行同步列宽。

统一的测量/安排协议是内部复用和后续定制的 seam，不等于所有节点都要经过虚调用、反射或一个任意约束求解器。先用行列、共享轨道这两类确有差异的算法检验协议，再决定最小的自定义容器扩展面。

## S02：测量必须知道约束，不照抄旧的最小尺寸协议

- 区分内容需求、父级实际分配和最终矩形；无界约束显式表达，不用随意的大浮点数假装无穷。
- 对宽度依赖高度的文字，先由容器解析实际可用宽度，再请求自然高度；共享列是先解析共享轨道，再测量各单元格。不能把 viewport 剩余高度均摊成自然行高。
- 只查询当前容器需要的信息，不一律同时计算 min-content、max-content、最终段落。最小尺寸查询与普通受限测量是否分开，须由实际容器证明需要。
- Measure 与 Arrange 是职责区分，不承诺任意布局都能用一次上行加一次下行完成。首版容器采用明确、可说明的有界步骤；不支持任意宽高反馈图，宿主滚动条/尺寸反馈必须有显式稳定策略。

## S03：空间分配和对齐分开

建议支持固定/内容尺寸、显式 min/max、带权扩展以及分配区域内的对齐/拉伸；不是照搬 CSS grow/shrink/basis 全套属性。Expand 获得多少区域与内容是否填满该区域是不同问题。

首增量提议采用**整池带权分配**：先从父内容区域扣除 Fixed/Content 项与间距，剩余池为 `P`；Expand 项满足 `s_i = clamp(λ × weight_i, minimum_i, maximum_i)`，在上下限允许时使总和等于 `P`。不是“先给每项 min，再按权重分剩余”。最小值总和超过池时保留硬最小值并溢出；全部达到上限时留下空白，不强塞给最后一项。槽内对齐/填满是后续步骤，不改变同一身份获得的槽大小；兄弟重排按浮点容差比较，不承诺跨平台 bitwise 一致。

保留 300 宽 `[120,150,30]` 饱和反例作为自己的验收输入。无界测量阶段不分配不存在的剩余空间，安排阶段使用确定矩形；不靠反复遍历直到“差不多稳定”。

## S04：先做好真实容器，不扩大成控件框架

| 算法族 | 真实用途 | 第一批应覆盖 |
|---|---|---|
| 行列与间距/对齐 | HUD 条、工具栏、面板 | 固定/内容/扩展组合，min/max 饱和，嵌套与溢出 |
| 覆盖与父矩形锚定 | HUD 角落、叠层 | 锚点/偏移、子项排除普通流、逻辑小数坐标 |
| 换行与等宽重复格 | 标签、物品/技能格 | 宽度跨阈值，间距、尾行、重排 |
| 共享轨道/表单容器 | Inspector、错误提示 | 全组列宽、约束下文本高度、最长项增删、折叠参与政策 |

这不是分别建设四个框架：算法共享同一拥有者与测量/安排机制。Padding、对齐、比例等优先作为明确的布局组合；是否需要独立节点以实际需求决定。完整 CSS Grid/subgrid、任意兄弟约束图、docking 拖放和控件皮肤不进入该批核心。

## S05：失效沿真实尺寸依赖传播

建议区分需要重测与只需重排；合并同一批输入变更，稳定输入直接复用已发布版本。颜色等纯绘制变化不进入几何失效。

固定外框只有在对祖先的尺寸贡献确实不依赖子内容时，才可截断向上的传播；其内部脏子树仍须处理。共享列、约束变化、结构编辑和字体版本变化分别记录依赖，不能用一个全树 dirty 掩盖遗漏，也不保证整帧 O(变更节点数)。

## S06：文字和虚拟化的拥有者必须清楚

叶测量 Adapter 拥有真实内容、字体/排版对象与测量缓存。布局库持有不保活业务对象的内容键/版本；缓存键覆盖影响结果的内容、提供者版本和约束。先复用真实排版工作，不用 ASCII 分词替代 Unicode 排版，也不预先承诺每叶只调用一次。

虚拟列表/树表的逻辑集合、共享宽度索引、滚动锚点和 extent 由集合视图拥有者负责，核心处理已实例化布局节点。必须公开精确扫描与估计政策的成本；逻辑 extent 与可见局部坐标分开，不靠巨大 float 坐标保证像素精度。布局库提供这些机制能协作的接口，不顺带实现完整列表控件。

## S07：可验证的资源、失败和结果寿命

- 建议同步、单写者起步；节点、遍历帧和临时队列采用可复用存储，调度显式化，避免布局树深度直接成为 C++ 调用栈深度。不承诺第三方测量内部也无递归。
- 节点/深度/数值与工作量限额在求解前检查；具体数值由真实边界实验确定，不将此前单链 depth64 变成产品保证。
- 测量期间拒绝结构修改和布局重入；拥有者销毁/关闭的生命周期前提及拒绝方式须在正式 Interface 中单独落定，不假称旧探针已经验证了回调销毁。
- 几何计算失败不发布半结果；本次写入的缓存要能撤销或可靠失效，不能仅丢输出。缺失内容与无效测量返回明确错误，不用零尺寸成功代替。
- 建议默认读取带版本的稳定结果视图，其有效期明确到下一次成功发布；跨版本消费显式取得拥有式快照或约定租期，而非每个静态帧都复制全树。最终 C++ 表示与租期机制尚未冻结。
- 几何保持逻辑精度，像素化与绘制包归 composition。旧几何的保留不自动保活旧文字/业务对象；失败时保留哪一版绘制包由 composition 拥有者负责。

## S08：按完整纵向增量落地

1. **先完成基础消费链**：原生库、局部身份/编辑/校验、行列与锚定、真实 DirectWrite 叶测量、失败发布和一个无窗口消费者。已有第三方探针的 PASS 不抵扣自己的验收。
2. **再完成有代表性的表达**：共享列 Inspector 与换行/重复格；覆盖英文、无空格中文、首次窄宽度、字体变化、饱和分配和 warm/fresh；用同一协议接入专门容器，不为每个控件扩通用属性。
3. **再做实际增量路径**：固定/自然外框失效、局部内容与结构编辑、虚拟视图协作、延迟结果消费；采集访问量、测量/排版、分配、发布与端到端成本。

每个增量均在开发/发布配置执行真实行为验收；性能比较仍用同语义、同真实提供者和明确计时范围。布局可独立于窗口/RHI 验收，但这不等于最终 UI 已具备渲染/交互能力。

## 借鉴依据与不照搬项

- **Godot 的容器机制**：父容器决定子项摆放，具体容器可定制；学习职责分工，不复制其整个 Control/Node、场景树、主题与事件体系。来源由 Exa 定位并核对官方 4.4 Container 文档；更具体的最小尺寸缓存/延迟重排依据此前固定源码审计，见 [工业游戏 UI 报告](../../research/ui-layout-reassessment/industry-game-ui.md)。不把旧 minimum-size 模式当成宽度依赖文本的一般解法。
- **其他工业机制**：按需借鉴尺寸查询与安排、共享轨道、失效合并和集合视图生命周期，见 [工业编辑器报告](../../research/ui-layout-reassessment/industry-editor-ui.md)。不能把任一框架的完整对象/输入/渲染层算作布局核心必需项。
- **我们自己的实测反例**：饱和分配、自然行高压缩、重复文字排版、虚拟 extent、失败缓存和栈边界均见 [验证结果](../../research/ui-layout-reassessment/validation-results.md)。自研尚无性能收益结论，必须用相同输入证实。

## 历史 D01–D08：旧 Yoga 方案，非当前实现要求

以下保留原有取舍和历史事实；其“已决定”“第一实现”等措辞仅属于当时阶段，已由上方自研方向取代。旧 [contract.md](contract.md)、[acceptance.md](acceptance.md) 和 [research.md](research.md) 同样是对照资料，不能机械续写为生产实现。

### D01：先做纯布局 Module

**已决定**：独立输入树/约束→未舍入逻辑快照；不等待RHI、窗口、一般业务语言或任务调度。真实无窗口求解与文字测量已通过Main探针，后来去掉Runtime/JIT库的精简链接也通过。

**理由**：有独立可观察输出，既能闭合树、测量、失效，又不需要第二套业务对象。独立不等于无需正式CMake接入；下一session仍须建立真实库target/consumer。

**重开条件**：近期目标改变成必须先交付可操作窗口，或布局输入无法离开业务对象/渲染设备，则重排模块，而非把窗口/RHI偷塞入本范围。

### D02：第一实现用窄Interface封装Yoga

**已决定**：复用research中固定Yoga源码，选择且显式配置支持子集；不公开原始style全家桶、Yoga指针或CSS兼容承诺。

| 对照 | 可取之处 | 当前未选理由 / 重开条件 |
|---|---|---|
| 自写窄算法 | 极小固定盒/stack可更少依赖、完全自主语义 | 测量模式、祖先失效、min/max及边界维护成本不能忽略；若真实需求永久无intrinsic/fill，可重新选择 |
| Yoga | C++/CMake与当前工具链相近，真实计算/缓存/测量入口已证 | 上游递归与分配并非零成本；若真实规模/深度或定制规则不适合，依据实测重评 |
| Taffy | 高低层Interface，可接自有树；可选Flex/Grid/Block | 当前C++路径引入Rust/FFI/额外锁定没有已证明收益；真实Grid/已有自有树需求成立时重审 |

这不是库流行度排名。没有比较吞吐/内存，不能说Yoga比Taffy快。第一实现不预建多求解器抽象；不泄露上游类型的小Interface已足够保留更换空间。

### D03：一份可变几何权威

**已决定**：Yoga拥有style/children/内部缓存；Document的局部表只保护owner/generation与内容revision，快照是不可变输出。

**争议与修正**：WaveModuleMap指出“低依赖封装”可能再复制一套Widget/style/cache，得不偿失。接受反例；Interface应集中安全句柄、校验、失效与结果发布，而不是同步两套树或改名setter。

**证伪条件**：实现出现两份可独立修改的style/children/cache，或调用者必须手工修补Yoga dirty；此时需收缩/重构，而非增加同步层。

### D04：测量是独立Adapter，不是核心内置文字引擎

**已决定**：核心只懂模式化约束和内容尺寸；真实文本/图像由同步Adapter提供。DirectWrite属于本轮真实probe及可选Windows验收Adapter，不进入核心依赖。

**证据**：真实内容改变而不MarkDirty保留旧缓存；MarkDirty后重新度量，内容、字号、父约束与直接DWrite结果相符。measure可能被多次调用或被确定尺寸跳过，不是资源事件。

**未覆盖**：所有脚本、fallback、固定字体文件、ink bounds、baseline、shaping缓存、provider错误恢复。现有probe以进程失败处理实际错误，不代表Module已经能恢复测量失败。

### D05：逻辑快照不舍入，composition选择目标政策

**已决定**：核心默认禁Yoga舍入；同一逻辑结果可生成多个surface/DPI视图。composition按目标选择snap/不snap，RHI不回头持布局节点。

**争议与修正**：本席初稿“布局快照唯一舍入”可能被理解为全树只保留一个DPI结果；WaveRhi用双DPI/离屏目标反驳，并指出viewport=float、scissor=整数。接受修正，唯一的是每个输出政策的转换责任，不是强制所有坐标同一种round。

**本机观察**：两个局部0.4在Yoga内部舍入后相加得到0；未舍入绝对坐标是0.8，选择一次绝对最近像素政策得到1。该观察支持分离政策，不是上游Yoga错误结论。文本ink/clip/hit-test不能被box snapping代替。

### D06：业务身份与布局资源身份分开

**已决定**：NodeId是局部计算资源句柄，不是Runtime ObjectId或永久Widget身份。核心没有业务root/JIT地址。业务绑定owner负责事件时取得/验证或明确长期ObjectRoot；现有私有Business Entry不被当作通用UI接口。

**理由**：统一业务类型/身份契约不要求每份几何数据都进入GC；反过来局部句柄也不能创建一套业务对象生命期。GPU在飞资源由RHI管理，不通过保活Node/业务对象代替fence。

### D07：首版同步、有界，不追CSS与调度全家桶

**已决定**：单写者同步布局；先证明完整冷布局、warm=fresh及内容失效，再谈优化。只公开contract的有限规则，未知属性明确拒绝。

**未承诺**：异步任务、跨帧预算、并行求解、任意树深、零分配或跨平台bitwise一致。上游源码中的new/临时vector/递归是成本线索，不是目标负载已出现性能问题。

### D08：正式集成有唯一修改者

**已决定**：模块owner可实现约定目录；根CMake/依赖锁/工具链/全局验收由Main或明确集成owner串行处理。不让两个session同时编辑共享构建与锁文件。本轮probe与vendor仍是out内实验，不能直接当生产依赖交付。

正式入口须依照现有CMake、mimalloc和开发/发布配置习惯；无需为布局另建包管理权威。升级Yoga必须同时复核subset、错误行为、几何goldens、dirty与许可，不只换tag。

### 当时实现前还需落定的三个局部决定

这些不是本次入选已冻结的C++ ABI，也不是可省略的任务：

1. **句柄/快照表示**：采用怎样的局部代际编码与不可变结果存储，使旧ID拒绝、旧快照可读且不泄漏第三方对象；用实际create/remove/重排消费者证明。
2. **测量失败桥接**：Yoga measure无错误返回通道；选定方案必须阻止失败快照、处理缓存污染并证明合法后续路径，不用0尺寸成功返回掩盖错误。
3. **有界支持规模**：公开节点数/深度/数值限制并用真实边界输入证实；根据具体用途设定，不由本轮微型probe捏造安全上限。

局部决定完成后写回本页与contract，再实现对应验收；不重开已确认的共享业务身份/语言语义。pixel snap/hit-test政策属于后续composition工作，不作为完成纯布局核心的前置。
